## 1. 같은 페이지, 따로 쓴 두 언어
- en·ko는 **같은 질문에 답하는 같은 범위의 페이지**다(hreflang 짝). 번역하지 않는다 — 같은 개요로 각 언어 독자에게 맞게 따로 쓴다(`docs/04` §6, 장문 기계번역 금지).
- **데이터 블록(표 컴포넌트)의 종류·순서·prop 은 두 언어가 똑같다**, `##` 섹션 수도 같다(테스트가 강제). 문장·예시 설명·어순은 자유.
- ko: 합니다체. 번역투 금지(“~하는 것이 가능합니다”, “당신”, “~에 대해” 남발, 과한 피동). 용어는 `messages/ko.json`을 따른다 — 판정 **쾌적·원활·겨우 가능·불가**, 신뢰 라벨 **실측·보정된 추정·이론 추정**, 실행 방식 **풀 GPU·부분 오프로드·MoE 전문가 RAM 배치·CPU 전용**, 양자화 등급 **준무손실·균형·손실 체감·손실 큼**. ko 독자 맥락(흔한 카드 RTX 4060·5060 Ti 16GB, 한국 모델)은 작은 보강으로.
- en: plain, direct; verdict names **Runs great / Runs well / Runs slowly / Won't run**.
- **ko 사람 말투 규칙**(09-30 사용자 지적 — "AI가 쓴 티"):
  - 판정 이름을 서술어로 쓰지 않는다. “판정은 쾌적입니다”, “쾌적입니다”, “불가입니다”, “겨우 가능 판정을 받습니다”, “원활 판정을 유지합니다” ✗ → “쾌적하게 돌아갑니다/돌릴 수 있습니다”, “원활하게 돌아갑니다”, “겨우 돌아갑니다(느립니다)”, “돌릴 수 없습니다”. 명사 라벨은 표·배지·“판정: 쾌적” 같은 라벨 자리에서만.
  - 제목·소제목의 “ — ”는 괜찮다. 본문에서 대시로 문장을 여러 번 이어 붙이는 것만 피한다.
  - 로컬 LLM 사용자가 이미 아는 용어(양자화, 컨텍스트, 오프로드, 리즈닝, VRAM, GGUF, Q4_K_M 등)는 풀어 쓰지 않는다 — 과하게 풀면 오히려 어색하다(09-30 사용자 지적). 풀어 쓸 것은 개발 쪽 은어뿐: 라이브, 개방, 게이트, 헤드라인, 베이스라인, 폴백.
  - “이 칸”, “이 행”처럼 문장만 봐서는 무엇인지 모를 지칭 금지 — 가리키는 대상을 이름으로(“이 조합의 속도는 …”). “표의 128k 칸”처럼 위치가 분명하면 괜찮다.
  - “실측값”, 문장 속 명사 “실측”(“이 가이드의 실측은”) 금지 → “공개 벤치마크 결과”, “실제로 잰 속도”. 신뢰 라벨 이름(‘실측’)을 가리킬 때만 그대로.
  - 명사로 끝나는 개조식 문장(“~ 기준 16k.”)을 본문에 쓰지 않는다. 주어와 서술어가 맞는 완결된 문장으로.
  - 한 문장에 정보 하나~둘. 70자를 넘기면 나눈다.
  - 소리 내 읽었을 때 한국 사람이 실제로 하는 말인지로 판단한다.

## 2. 숫자는 컴포넌트만 (CLAUDE.md 규칙 2·3, D43)
- 산문에 **tok/s·소수 GB·가격(달러·원)을 쓰지 않는다.** 속도는 표(`ComboGrid`·`QuantLadder`·`CtxTable`·`Measured`)가 밴드와 신뢰 라벨을 붙여 그린다. 단일 수치는 `<Num kind=… />`, 가격은 `<Price gpu=… />`(기준일 동반).
- **외부 도구 사실은 `<RuntimeFact id="…" />`**(출처 링크·확인일이 함께 붙는다 — 레코드 `lib/runtime-facts.ts`, 10-19). 새로 쓰는 문장에서는 도구 문서에 적힌 버전·임계값(GiB 등)·요구 사양을 산문에 직접 쓰지 않고 이 컴포넌트로 넣는다. 이미 게시된 산문(예: `cpu-only-llm` 의 LM Studio AVX2 문장)은 분기 재확인(PROGRESS §3) 때 옮긴다. 테스트는 산문 속 GiB 숫자만 거부한다. 지금 id 와 렌더되는 문장(`messages` `GuideData.<키>`):
  - 완결된 절 — 문장 하나로 쓴다(`<RuntimeFact id="ollama-default-ctx" />.`): `ollama-default-ctx`(VRAM 별 기본 컨텍스트) · `ollama-kv-cache-type`(KV 캐시 양자화 조건)
  - 짧은 명사구 — 문장 안에 넣는다(“Ollama 문서가 밝힌 Windows 요구 사항은 <RuntimeFact id="ollama-windows-req" />입니다.”처럼 주어·서술어는 직접 쓴다. 렌더 결과는 “… (Ollama 문서, 2026-10-19 확인)입니다.” — 출처 줄이 괄호로 붙으니 문장 키는 괄호나 마침표로 끝내지 않는다): `ollama-windows-req`(Windows 버전·NVIDIA 드라이버) · `ollama-macos-req`(macOS 버전·칩) · `ollama-nvidia-req`(Compute Capability·드라이버 — `/gpu` 문서. `/windows` 문서의 드라이버 하한과 숫자가 다르니 두 사실을 섞어 한 문장으로 쓰지 않는다) · `lmstudio-windows-req`(AVX2·권장 RAM·VRAM) · `lmstudio-mac-req`(Apple Silicon·macOS 버전·권장 RAM)
  - **더하는 법**: 1차 문서를 직접 읽고 ① `lib/runtime-facts.ts` 에 레코드 한 줄(`source` https · `checked` 읽은 날 · `tool` · `message` 키, 위에 문서 원문을 짧게 주석으로) ② `messages/{en,ko}.json` `GuideData` 에 그 키의 문장(문서가 말하는 것만, 값 끼워 넣기 `{…}` 없음) ③ 여기 목록에 한 줄. 새 도구면 `RUNTIME_FACT_TOOLS` 와 출처 줄 키(`GuideData.factSource<도구>`, en/ko)도. id 목록은 레코드 키에서 나오고 MDX 스캔·유닛 테스트(`test/runtime-facts.test.ts`)가 나머지를 검사한다. 분기 재확인(PROGRESS §3)은 `checked` 가 90일을 넘긴 레코드를 다시 읽는다.
- 산문에 써도 되는 숫자: 하드웨어 등급(8GB·12GB·16GB·24GB·32GB·64GB 같은 정수 용량), 컨텍스트 이름(4k·8k·32k·128k), 양자화 이름(Q4_K_M 등), 연도, “두 배·절반” 같은 비율 표현.
- 산문에서 특정 조합의 판정을 말하면 **바로 뒤에 `<Expect model="…" gpu="…" verdict="S|A|B|F" />`** 를 붙인다(렌더 안 됨 — 데이터가 바뀌면 빌드가 실패해 문장을 고치게 한다). fit 만 말하면 `fits="true|false"`.
- 단정 금지: en “guaranteed / definitely / will run / runs perfectly / no problem / best GPU / fastest / future-proof”, ko “무조건 / 확실히 / 완벽하게 / 문제없이 / 최고의 / 끝판왕 / 사세요”. 추정은 “we estimate / expected / 추정 / 예상”. 조건(8k 컨텍스트·f16 KV·시스템 RAM 32GB DDR5·Windows)을 밝힌다. 조언은 “메모리 N GB 이상을 목표로”처럼 메모리 기준으로 — 특정 제품 구매 권유 금지.
- **제목 예외 “추천/Recommended”(10-15 D75)**: 가이드 **제목**에는 사용자가 채팅으로 승인한 슬러그에 한해 “추천”/“Recommended”를 쓸 수 있다(지금 `gpu-by-budget` — 승인 목록은 `test/guides.test.ts`). 조건은 본문이 그 질문에 메모리·fit 데이터로 답하고 특정 제품 구매를 권하지 않는 것. 예외는 제목에만 — 설명(description)에는 쓰지 않는다. “best / 최고의 / 사세요”는 제목·설명에서도 금지다(제목·설명도 산문과 같은 금지어 검사를 받는다).
- 제목·요지(첫 문단)·설명·FAQ 답은 **메모리·fit 같은 결정적 사실과 보정·실측 값만**. 이론 추정(±30%) 셀은 표·예시에서만, 라벨과 함께.
- 엔진 한계를 정직하게: MoE 전문가를 시스템 RAM 에 두는 경로(cpu-moe)는 VRAM 에 들어가는 만큼 전문가를 GPU 에 두는 배치로 계산한다(10-01 D56 — llama.cpp `--fit`·Ollama 0.30+ 기본과 같은 방향). 공개 실측 대비 평균 오차 ~10% 지만 40% 가까이 벗어난 구성이 있어 **이론 추정(±30%)** 이다 — “보수적”·“실제는 더 빠르다”로 쓰지 않는다. RAM 힌트 용량(예: gpt-oss-120b 가 몇 GB 부터 되는지)은 카드마다 다르다 — 산문에 쓰면 `<Expect>` 로 고정되지 않으니 데이터가 바뀔 때 직접 다시 확인한다.
- 미출시·루머 하드웨어(RTX 50 Super·B770 등) 언급 금지. 외부 벤치 표 전재 금지 — 공개 실측은 `<Measured>`로 1~2점만.

## 3. 링크
- 내부 링크는 컴포넌트로: `<HubLink gpu="…" />`·`<HubLink model="…" />`, `<GuideLink slug="…" />`(초안이면 텍스트만), `<ComboLink model="…" gpu="…" />`(공개 콤보만 링크). 마크다운 `[..](/..)` 내부 링크 금지.
- 외부 링크는 `https://` 만, 권위 있는 1차 출처(Ollama·llama.cpp 문서, Hugging Face 모델 카드, 제조사 스펙 페이지).

## 4. MDX 문법 제약 (플러그인 없음)
- `#` 제목 금지(h1 은 템플릿). 섹션은 `##`, 하위는 `###`.
- 파이프 표·`<table>`·HTML 주석·frontmatter·`import`/`export`·중괄호 `{ }` 금지. 산문의 `<` 는 “less than/미만”으로 쓴다.
- 블록 컴포넌트(표 — `ComboGrid`·`GpuTierSummary`·`ModelMemoryTable`·`KvPerTokenTable`·`QuantSizeTable`·`QuantLadder`·`CtxTable`·`UnifiedTierTable`·`ModelFacts`·`MemoryBreakdown`·`Measured`·`Threshold`)는 **앞뒤 빈 줄을 둔 자기 줄**에만. 인라인(`Num`·`Price`·`RuntimeFact`·`HubLink`·`GuideLink`·`ComboLink`·`Expect`)은 문장 안에.
- prop 은 따옴표 문자열만. 목록은 쉼표 구분(`gpus="rtx-4060,rtx-3090"`). id 는 `data/*.json` 의 id.
- 코드(명령)는 백틱 코드 스팬/블록. 명령 속 숫자는 산문 검사에서 빠진다.

## 5. 구성 (권장 골격)
1. 요지 2~4문장 — 질문에 바로 답(메모리·fit 기반)
2. 핵심 데이터 블록(자체 데이터 — 가이드마다 ≥1, 테스트 강제)
3. 원리 설명 `##` 2~4개 (각 섹션에 근거 블록이나 `Num`)
4. 예시 — 그리드·사다리·ctx 표
5. “이 숫자는 얼마나 확실한가” — 신뢰 라벨 뜻, 엔진 한계, `<Threshold />`(판정 기준표)
6. 다음 단계 — 허브·다른 가이드 링크(계산기 위젯은 템플릿이 붙인다)
7. `## FAQ` / `## 자주 묻는 질문` — `###` 질문 3~5개(개념형, 카드별 질문 금지 — 허브·콤보 몫)
8. `## Sources` / `## 출처` — 외부 1차 출처 목록

분량: 필러(`vram-requirements`) en 2,500~3,500단어 / ko 7,000~9,500자, 나머지 en 1,200~2,500단어 / ko 3,500~7,000자. 표를 뺀 산문이 절반 이상.

## 7. 감수와 게시
초안(`status: 'draft'`)은 noindex·미링크로 배포된다(URL 로만 열림). **게시(`published`) 전환은 사람이 채팅으로 승인한 슬러그만** — `reviewedAt`·`datePublished`·`dateModified` 갱신과 함께(D40).

## 8. 파일럿 교훈 (`ollama-context-length` 검사 지적 — 반복 금지)
- **주장 범위 = 확인한 셀.** 한 모델·한 카드에서 본 결과를 “32GB 카드는”, “dense 32B 모델은”처럼 넓히지 않는다. 같은 급의 반례(EXAONE 4.0 32B, RTX 5090 등)가 브리프에 있으면 그 주장은 틀린 것이다. 문장마다 모델·카드를 특정하고 `guide-brief` 로 확인한다.
- **`<Expect>` 는 그것이 뒷받침하는 절 바로 뒤**(8k·f16 기준 판정 절)에 둔다. 다른 컨텍스트 주장 뒤에 붙이면 그 주장을 보증하는 것처럼 읽힌다. 16k·32k·64k 결과는 판정 이름 대신 필요량 대 사용 가능 메모리 + “표 참고”로.
- **정도 부사는 수치와 맞춘다.** 필요량이 사용 가능 메모리를 넘으면 “slightly/살짝”을 쓰지 않는다(표 셀이 부분 오프로드로 떨어진다). 여유가 1GB 미만이면 “with little margin — check `ollama ps`”/“아슬아슬하게 — `ollama ps` 로 확인”.
- **CanRun 계산 ≠ 런타임 실제 동작.** Ollama·llama.cpp 가 실제로 어떻게 배치하는지는 “in our model/CanRun 계산으로는”으로 한정하고 `ollama ps` 확인을 붙인다.
- **ctx 표 모드는 브리프로 확인.** 한도를 넘는 셀은 부분 오프로드만이 아니라 CPU 전용(KV 캐시만으로 사용 가능 메모리 초과)도 있다. 산문이 표와 다른 모드를 말하지 않게 한다.
- **컴포넌트가 렌더하는 문구를 알고 쓴다.** `HubLink` = 카탈로그 전체 이름(예: “GeForce RTX 5060 Ti 16GB”) — 뒤에 “(16GB)”를 붙이지 않는다. `ComboLink` = en “{model} on the {gpu}”, ko “{gpu}에서 {model}” — 앞뒤에 같은 모델·카드 이름을 반복하지 않는다. 카드 이름은 한 문단 안에서 전부 `HubLink` 또는 전부 평문으로 통일한다.
- **`ComboLink` 는 배치 1(`data/publish.json`) 조합에만.** 배치 1 밖 조합은 앞으로도 링크가 되지 않으므로 `HubLink`(모델 또는 GPU 허브)를 쓴다. 배치 1 조합도 지금(currentBatch 0)은 평문이라, 링크가 없어도 자연스러운 문장으로 쓴다(“our page for …”는 가능, “(조합 페이지: …)” 같은 라벨 금지).
- **출처는 정확히.** 소스·문서가 실제로 말하는 것만(예: 디버그 로그는 “잘라 낸 개수”를 남길 뿐 내용이 아니다). 도구 동작의 숫자 임계값(GiB 등)은 산문에 쓰지 않고 `<RuntimeFact>` 로(테스트가 산문 `GiB` 숫자를 거부).
- **명령은 Windows 우선.** 한국 독자 대다수가 Windows 다. POSIX 명령(`VAR=… cmd`, `curl -d '…'`)에는 “macOS·Linux”를 명시하고 PowerShell 형태(`$env:VAR="…"; cmd`)를 함께 준다. PowerShell 5.1 의 `curl` 은 다른 명령의 별칭이다. Windows 환경 변수는 “계정의 환경 변수 편집”(관리자 권한 불필요).
- **섹션은 단독으로 읽혀도 성립.** 목차에서 바로 들어온 독자를 위해 섹션의 핵심 사실(예: 기본값 구간)은 그 섹션 안에서 다시 컴포넌트로 보여 준다. 전문 용어(Q4_K_M, KV 캐시, 연산 버퍼)는 처음 나올 때 한 구절로 풀어 쓴다. 요지 문장은 en 30단어·ko 100자 안팎.
- **FAQ 는 첫 문장이 답.** “Should I…?/해야 하나요?”에는 첫 문장에서 조건부 답을 준다.
- **ko 용어·문체**: “한국 모델”(국산 X), “dense 모델”, “컨텍스트”(‘창’ 단독 X — 다른 뜻과 겹친다), “CanRun 계산”(‘우리 모델’ X — LLM 으로 읽힌다), deterministic = “공식으로 계산한 값”(‘결정적’ X). 문어체(예컨대·견주다)·구어체(알아서)·중의적 수식(“작거나 중간 정도로 긴 컨텍스트”) 금지. “오류 없이”처럼 출처가 보증하지 않는 단정 금지.

- 산문 숫자 규칙(§2)은 여기도 같다: tok/s·소수 GB·가격 금지(가이드와 같은 검사 `apps/web/test/prose-rules.ts`). 내부 링크는 `<SiteLink to="/…">` — 대상은 정적 페이지·계산기·목록 페이지(`/models`·`/gpus`)·카탈로그에 있는 모델/GPU 허브·게시된 가이드만(테스트가 id 를 확인한다).

## 10. 허브 소개글 (`content/{en,ko}/hubs/{gpu,model}/<id>.mdx` — 10-14 D74)
- 대상은 레지스트리 `content/hubs.ts` 의 GPU 10·모델 10(고른 기준은 파일 주석과 PROGRESS §4 D74). 레지스트리에 없는 허브는 소개 없이 지금처럼 그린다. 하나 늘리려면 레지스트리 + `lib/hub-intros.ts` 로더 맵 + en·ko MDX 세 곳(유닛 테스트가 대칭을 본다).
- 허브 머리말 아래에 템플릿이 h2(`GpuHub.introTitle`·`ModelHub.introTitle`)를 붙인다. 본문은 **제목·목록 없이 문단 2~3개**, en 220단어·ko 공백 뺀 600자 이하(`apps/web/test/hub-intros.test.ts`).
- 가이드 §1~§4 규칙이 그대로다: 숫자는 컴포넌트, 판정·fit·실행 방식을 말한 절 바로 뒤에 `<Expect>`(파일마다 1개 이상, `<Num>`·`<Price>` 도 1개 이상). 표 같은 블록 컴포넌트는 쓰지 않는다 — 허브가 이미 표를 그린다. 자기 허브로 가는 `HubLink` 는 금지(테스트), 자기 카드·모델은 평문이나 "이 카드/this card".
- **모델 묶음 전체를 말하는 판정·fit 문장 금지**(10-14 리뷰 — "32B급까지는 24GB 에 전부", "30B~35B급 MoE 는 전부 올라간다"가 카탈로그의 Nemotron 3.5 Lightning 30B-A3B 와 어긋났다). `<Expect>` 는 이름을 댄 모델만 지킨다 — 매일 신모델이 추가돼 예외가 생겨도 빌드는 초록이다. "Qwen3 14B·Gemma 3 12B 같은 dense 모델"처럼 고정한 모델을 이름으로 쓰고, 아는 예외는 이름과 `<Expect>` 로 밝힌다. 한 모델의 VRAM 구간 주장("24GB 카드에 전부 올라간다")은 쓸 수 있다 — 같은 구간 카드는 쓸 수 있는 몫이 같고, 대표 카드에 `<Expect>` 를 붙인다.
- `<Expect>` 조건 prop(D74): `quant`(기준 대신 그 양자화 행) · `ram`(dGPU = 시스템 RAM 계단 16·32·64·96·128, 통합 메모리·CPU = 메모리 옵션) · `ctx`·`kv`(콤보 ctx 표의 칸 — 표시 양자화 기준) · `mode`(`full-gpu`·`cpu-moe`·`partial-offload`·`cpu-only`) · `confidence`(`measured`·`calibrated`·`theoretical` — "공개 벤치마크가 아래 표에 있다", "이 구성은 이론 추정이다"). "IQ4_XS 면 GPU 에 전부", "RAM 64GB 면 전문가를 RAM 에", "32k 도 GPU 에" 같은 문장은 조건까지 고정한다. 통합 메모리 칩을 `ram` 없이 쓰면 "가장 좋은 판정이 나는 가장 작은 메모리" 구성이라, 용량을 말하는 문장에는 `ram` 을 꼭 붙인다. 대조 함수는 `lib/expect-claim.ts`.
- ctx 표는 콤보 페이지 구성으로 계산된다: 시스템 RAM 32GB(페이지 기준)에 안 들어가는 콤보(예: RTX 3090 의 gpt-oss-120b)는 **RAM 힌트 구성(64GB 등)의 표**다. 그런 콤보의 `ctx` 주장은 `ram="64"` 처럼 그 용량을 밝혀야 하고(없으면 빌드 실패), `ram` 을 주면 ctx 표의 RAM 과 같아야 한다.
- 고정 규칙(유닛 테스트): 조건(`quant`·`ram`·`ctx`)이 붙은 `<Expect>` 는 `verdict`(어떻게 돌아가는지) 나 `fits`(올라가는지) 를 꼭 밝힌다 — `mode` 만 고정하면 같은 문장의 "느리다"가 고정되지 않는다(Qwen3.8 27B IQ4_XS 를 "느리다"고 썼는데 실제로는 원활하던 사례). `verdict` 가 이론 추정(±30%) 칸이면 그 문장이나 바로 다음 문장에 라벨(en "theoretical", ko "이론 추정")을 쓴다.
- `<Price>` 는 "$250 street (as of …)"·"… 기준 실거래가 $250"처럼 라벨까지 그린다 — en 산문에 "street price"를 또 쓰지 않는다("Our data lists it at <Price/>"). 출시가로 바뀌면 "launch MSRP"가 그려지므로 그쪽으로도 맞는 문장이어야 한다.
- 쓸 내용은 표만 봐서는 모르는 것: 메모리 경계(어디서 갈리는지), 어떤 양자화 파일이 들어가는지, MoE 전문가 RAM 배치, 생각 모드 1.5배 기준 때문에 한 단계 낮게 나오는 경우, 노트북용·8GB판처럼 이름이 비슷한 다른 하드웨어. 허브 FAQ·요약이 이미 말하는 숫자(판정 개수, 전부 올라가는 가장 큰 모델)는 되풀이하지 않는다. 판매 문구·과장 금지(§2 단정 금지 그대로).
- 데이터 밖 사실은 1차 출처 링크(모델 카드·제조사 사양 페이지). `<Expect>` 로 고정되지 않는 문장 — 예: rtx-5090 소개의 "아래 표의 공개 벤치마크가 추정보다 한참 낮다"(이론 추정이라는 점만 `confidence` 로 고정) — 은 그 데이터가 바뀔 때 직접 다시 확인한다. "속도 기준 1.5배 때문에 한 단계 낮다"처럼 원인을 말할 때는 엔진으로 확인한다: 기준선에 걸친 이론 추정 차이(예: RTX 4060 과 Laptop 의 gpt-oss-20b, 3% 차이)는 "기준에 걸쳐 있어 한 단계 갈린다"로 쓰고 실제 성능 차이처럼 쓰지 않는다. CPU 전용 구성은 속도와 관계없이 B 상한이다 — "느리다"가 아니라 "CPU 전용이라 상한"으로.
- ko 조사: 컴포넌트가 그리는 이름 뒤 조사는 렌더된 이름의 끝소리로 고른다(“GeForce RTX 4060과”, “Apple M4 Pro가”, “GeForce RTX 4060 Laptop은”). `ComboLink` 는 ko 에서 “{gpu}에서 {model}” 이라 “… 페이지에 있습니다”처럼 뒤에 명사를 붙인다.

- 쓸 내용은 표만 봐서는 모르는 것: 어느 메모리 경계에서 판정이 갈리는지(이름을 댄 모델과 `<Expect>` 로), 속도 차이가 어디서 오는지(대역폭 — 배율은 페이지 요약이 이미 말한다), 같은 이름의 다른 제품(8GB판·노트북판), 통합 메모리는 GPU 가 약 70%만 쓴다는 점처럼 단순 비교가 틀리는 지점. 요약·FAQ 가 이미 말하는 숫자(배율, 판정 수, 가장 큰 모델)는 되풀이하지 않는다. "어느 쪽을 사라"는 단정 금지(§2) — 쓰임새별로 무엇이 갈리는지만.
- ko 조사는 렌더된 이름의 끝소리로 고른다(§10). 페이지 제목·머리말의 기기 이름은 그래픽카드가 짧은 이름("RTX 5060 Ti 16GB"), 통합 메모리·CPU 기기가 짧은 이름 + 비교 구성 메모리("M4 Pro 64GB"·"Ryzen AI Max+ 395 128GB" — D107)로 그려진다. 본문의 `HubLink` 는 메모리 없이 허브의 표시 이름 그대로다.
