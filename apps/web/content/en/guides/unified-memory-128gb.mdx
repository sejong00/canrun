## How much of the 128GB the GPU can use

CanRun uses one figure for every unified-memory machine: about 70% of the pool. The real limit depends on the operating system and its settings, and the three makers handle it differently.

### Mac Studio

macOS caps how much unified memory the GPU may take. According to code quoted in llama.cpp discussion #2182, macOS keeps back about a quarter of the memory on Macs with more than 32GB. A 128GB Mac therefore gives its GPU about three quarters by default, more than CanRun counts. The limit can be raised in macOS Terminal with `sudo sysctl iogpu.wired_limit_mb=` followed by a value in megabytes. <GuideLink slug="mac-local-llm" /> covers the default, the command and the risk of leaving macOS too little memory.

### Strix Halo

On Windows, AMD's Variable Graphics Memory turns part of system RAM into dedicated graphics memory; you set it in AMD Software: Adrenalin Edition. AMD's FAQ says a 128GB Ryzen AI Max+ 395 system can dedicate up to 96GB. With that setting the GPU can address 112GB in total by also using shared memory, though AMD says performance is highest when workloads stay within 96GB.

On Linux, AMD's ROCm documentation describes a different pool. By default, the kernel driver lets the GPU map about half of system RAM, a limit called GTT, so it applies whether llama.cpp runs through ROCm or Vulkan. AMD recommends keeping the dedicated reservation in the BIOS small and raising the shared limit instead. Its `amd-ttm` tool, from the `amd-debug-tools` package, shows the current limit and sets a new one, and the change applies after a reboot. `amd-ttm` counts binary gigabytes, so its figures read about 7% lower than CanRun's. Half of 128GB leaves little room above the <Num kind="needGB" model="gpt-oss-120b" gpu="amd-strix-halo" /> that gpt-oss-120b needs, so raise the limit before loading it.

### DGX Spark

NVIDIA lists the DGX Spark with 128GB of unified system memory and gives no separate figure for the GPU. Its known-issues page explains that `nvidia-smi` shows total memory use as Not Supported, because the GPU has no dedicated framebuffer memory, though it still lists each process's GPU memory. The same page warns that the free memory a CUDA program reads can be lower than what it can actually allocate.

### Where CanRun's 70% sits

On a 128GB Mac, CanRun's figure is below the macOS default. On the Strix Halo it sits between the Linux default and the Windows maximum. On the DGX Spark it is an assumption, not a published limit. The difference matters only for models whose need lands between those lines. The Q2_K file of Solar Open 2 250B, a 2-bit quant with heavy quality loss, needs <Num kind="needGB" model="solar-open2-250b" quant="Q2_K" gpu="amd-strix-halo" />. ## How sure are these numbers?

Memory figures are calculated with a formula: real GGUF file sizes, KV cache sizes from each model's configuration, and a compute-buffer formula. The approximation is the GPU share, the same 70% for every unified-memory machine, which the second section compares with each system's real limit.

Speeds are measured where a cell says so. In this guide, the other cells running fully on the GPU of these machines are calibrated estimates with a ±20% band; the ±12% band applies only to dense models on NVIDIA and AMD graphics cards. CPU-only cells and the RTX 5090 with experts in RAM are theoretical estimates (±30%).

CanRun turns bandwidth into speed with one efficiency factor per type of machine, fitted to public results. The DGX Spark factors come from the llama.cpp maintainers' results file: five models on one build, at the start of a conversation and 8k tokens in, and CanRun's estimates land within a fifth of each. They all come from one machine with mmap off, though, and the Strix Halo factors come from other public results. That is why CanRun puts the DGX Spark ahead of the Strix Halo on every model here by more than the same-build comparison above showed, so treat the size of that gap with caution. Public results on Apple silicon show the Ultra chips turning less of their bandwidth into speed than the Max chips, so CanRun uses a lower factor for them.

Software also moves these numbers. The Strix Halo runs llama.cpp through ROCm or Vulkan, the DGX Spark results changed with the llama.cpp build and the mmap setting, and Macs can also run MLX models. CanRun's estimates are for GGUF files on llama.cpp. Not modelled: prompt processing time, power modes, a raised GPU memory limit, other programs' memory, and more than one request at a time.

On your own machine, `ollama ps` shows what happened: SIZE, PROCESSOR (100% GPU) and CONTEXT. With llama.cpp, read the load log. On the DGX Spark, `nvidia-smi` shows total memory use as Not Supported but still lists each process's GPU memory.

Verdict names in this guide's text refer to the 8k context, f16 KV baseline. Models with a thinking mode, even one that is off by default such as Gemma 4 31B's, can spend extra tokens thinking before they answer, so CanRun makes their speed thresholds 1.5× stricter; the legend below does not show this.
