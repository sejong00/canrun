## How much of the 128GB the GPU can use

CanRun uses one figure for every unified-memory machine: about 70% of the pool. The real limit depends on the operating system and its settings, and the three makers handle it differently.

### Mac Studio

macOS caps how much unified memory the GPU may take. According to code quoted in llama.cpp discussion #2182, macOS keeps back about a quarter of the memory on Macs with more than 32GB. A 128GB Mac therefore gives its GPU about three quarters by default, more than CanRun counts. The limit can be raised in macOS Terminal with `sudo sysctl iogpu.wired_limit_mb=` followed by a value in megabytes. <GuideLink slug="mac-local-llm" /> covers the default, the command and the risk of leaving macOS too little memory.

### Strix Halo

On Windows, AMD's Variable Graphics Memory turns part of system RAM into dedicated graphics memory; you set it in AMD Software: Adrenalin Edition. AMD's FAQ says a 128GB Ryzen AI Max+ 395 system can dedicate up to 96GB. With that setting the GPU can address 112GB in total by also using shared memory, though AMD says performance is highest when workloads stay within 96GB.

On Linux with ROCm, AMD's documentation describes a different pool. By default, the GPU may map about half of system RAM, a limit called GTT. AMD recommends keeping the dedicated reservation in the BIOS small and raising the shared limit instead. Its `amd-ttm` tool, from the `amd-debug-tools` package, shows the current limit and sets a new one in GB, and the change applies after a reboot. Half of 128GB leaves little room above the <Num kind="needGB" model="gpt-oss-120b" gpu="amd-strix-halo" /> that gpt-oss-120b needs, so raise the limit before loading it.

### DGX Spark

NVIDIA lists the DGX Spark with 128GB of unified system memory and gives no separate figure for the GPU. Its known-issues page explains that `nvidia-smi` shows memory usage as Not Supported, because the GPU has no dedicated framebuffer memory. The same page warns that the free memory a CUDA program reads can be lower than what it can actually allocate. For debugging, it gives a command that flushes the Linux buffer cache, `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'`, after which you restart the application.

### Where CanRun's 70% sits

On a 128GB Mac, CanRun's figure is below the macOS default. On the Strix Halo it sits between the Linux default and the Windows maximum. On the DGX Spark it is an assumption, not a published limit. The difference matters only for models whose need lands between those lines. The Q2_K file of Solar Open 2 250B, a 2-bit quant with heavy quality loss, needs <Num kind="needGB" model="solar-open2-250b" quant="Q2_K" gpu="amd-strix-halo" />. That is more than CanRun's share, so on a 128GB machine CanRun computes it CPU-only and rates it Runs slowly, a theoretical estimate.<Expect model="solar-open2-250b" gpu="amd-strix-halo" ram="128" quant="Q2_K" verdict="B" mode="cpu-only" /> With a higher limit it may fit on the GPU, so check where it actually loaded with `ollama ps` or the llama.cpp load log.

## How sure are these numbers?

Memory figures are calculated with a formula: real GGUF file sizes, KV cache sizes from each model's configuration, and a compute-buffer formula. The approximation is the GPU share, the same 70% for every unified-memory machine, which the second section compares with each system's real limit.

Speeds are measured where a cell says so. In this guide, the other cells running fully on the GPU of these machines are calibrated estimates with a ±20% band; the ±12% band applies only to dense models on NVIDIA and AMD graphics cards. CPU-only cells and the RTX 5090 with experts in RAM are theoretical estimates (±30%).

CanRun turns bandwidth into speed with one efficiency factor per type of machine, fitted to public results. Our data has a single DGX Spark result, the gpt-oss-120b one above, and CanRun applies the factor fitted to it to dense models too. So where the grid's speeds put the DGX Spark below the Strix Halo on dense models, the gap comes from that factor, not from a dense-model measurement. Public results on Apple silicon show the Ultra chips turning less of their bandwidth into speed than the Max chips, so CanRun uses a lower factor for them.

Software also moves these numbers. The Strix Halo runs llama.cpp through ROCm or Vulkan, the DGX Spark results changed with the Linux kernel and llama.cpp build, and Macs can also run MLX models. CanRun's estimates are for GGUF files on llama.cpp. Not modelled: prompt processing time, power modes, a raised GPU memory limit, other programs' memory, and more than one request at a time.

On your own machine, `ollama ps` shows what happened: SIZE, PROCESSOR (100% GPU) and CONTEXT. With llama.cpp, read the load log. On the DGX Spark, `nvidia-smi` does not report memory use.

Verdict names in this guide's text refer to the 8k context, f16 KV baseline. Models with a thinking mode, such as gpt-oss and Qwen3.5, spend extra tokens thinking before they answer, so CanRun makes their speed thresholds 1.5× stricter; the legend below does not show this. The thresholds:
