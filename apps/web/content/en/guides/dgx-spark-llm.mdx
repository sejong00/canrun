## How much memory the GPU can use

The DGX Spark has no separate VRAM. Its CPU and GPU share one pool, and NVIDIA lists that pool as unified system memory without giving a separate figure for the GPU. On Linux the GPU takes its memory from the same pool as every other program, so CanRun counts what the system and the desktop leave free: <Num kind="usableGB" gpu="nvidia-dgx-spark" ram="128" /> on the 128GB model and <Num kind="usableGB" gpu="nvidia-dgx-spark" ram="64" /> on the 64GB model. A model fits when its GGUF file, its KV cache and a compute buffer, the runtime's working memory, add up to no more than that.

The 128GB figure starts from owners' kernel boot logs on NVIDIA's developer forum. The lowest of them comes from DGX OS 7.5.0, where a new kernel feature reserves several gigabytes more than earlier kernels did, and a reply in that thread says updates to address it are rolling out. CanRun takes that lowest log and subtracts what the desktop uses when idle, as another owner measured it. No boot log for the 64GB model has been published yet, so CanRun subtracts the same fixed amount from it. A press report puts the 64GB model's room for a model somewhat higher than CanRun does, and NVIDIA has not confirmed it.

Three habits help on a real system. NVIDIA's known-issues page warns that the free memory a CUDA program reads can be lower than what it can actually allocate, and that `nvidia-smi` shows total memory use as Not Supported while still listing each process. One owner reported that running out of memory locked up the whole machine, which then needed a hard reboot, instead of ending the program with an out-of-memory error, so leave some headroom. And turn mmap off in llama.cpp: `--load-mode none` in current builds, `--no-mmap` in older ones. Owners on the forum found loading with mmap much slower, and the llama.cpp maintainers ran their DGX Spark results file with it off. CanRun's dense speed factor for the DGX Spark comes from that file.

## Linking two or four units

### What NVIDIA supports

Each DGX Spark has ConnectX-7 networking with two QSFP ports. NVIDIA's clustering guide supports up to three units connected directly by cable and up to four through a switch, and its product page recommends a power-of-two count. Two units take a single QSFP cable; NVIDIA's cable guide says a second cable does not add performance. Three units are cabled in a ring. For four, NVIDIA's switch guide calls for a 200GbE switch, and a four-unit cable ring is possible only with manual setup.

NVIDIA's own multi-unit guides cover NCCL, the library for GPU-to-GPU communication across units, and vLLM across two to four units. NVIDIA's llama.cpp guide does not cover linked units. Linking units with llama.cpp RPC is a community setup. It is the one CanRun calculates, because it extends the llama.cpp commands this site already prints.

### What CanRun calculates: llama.cpp RPC

With llama.cpp RPC, the first unit runs `llama-server` and every other unit runs an RPC server that takes a share of the layers. Memory adds up, but each token still passes through every unit in turn, so bandwidth does not add up, and every hop between units adds time to each token. CanRun works out that time from public two-unit runs and adds it once per extra unit. A fast, small model loses the most, because the hop is a large share of its time per token.

The public runs agree on the direction. In the llama.cpp discussion on the DGX Spark, one participant ran gpt-oss-120b on one and two units on the same build over the default TCP connection, and two units generated about a fifth slower. Another tester, running over RDMA, saw DeepSeek V4 Flash 0731 lose only a few percent on two units, and loaded a 4-bit file on two units that was too large for one. The same discussion also has 4-bit files of MiniMax-M2 and Qwen3-VL-235B running on two units, files too large for one. We found no public llama.cpp RPC runs on four units, so CanRun's four-unit rows extend the two-unit hop time.

In the calculator, which the form below opens, pick the DGX Spark and then the number of linked units, and the result prints the commands for each unit. They follow this pattern, with each unit's ConnectX-7 address in place of the node addresses. On every unit after the first:

```
ggml-rpc-server -H <node2-ip> -p 50052 -c
```

Then on the first unit:

```
llama-server -hf <model> -c 8192 -ngl all -fa on --rpc <node2-ip>:50052
```

Build llama.cpp with `-DGGML_RPC=ON` and build the `ggml-rpc-server` target as well, because NVIDIA's llama.cpp guide builds only `llama-server`. Builds from before late June 2026 call the server `rpc-server`. When llama.cpp is built with libibverbs, the RPC link switches to RDMA by itself. The RPC server has no security of its own, so keep it on the private link between the units. Ollama does not split a model across machines this way.

### Tensor parallelism with vLLM can be faster

vLLM and TensorRT-LLM can split each layer across units instead, which is called tensor parallelism. Every unit then reads only part of each layer for every token, so bandwidth does add up. NVIDIA's technical blog reports Llama 3.3 70B in NVFP4 on TensorRT-LLM: the time per output token fell to about half on two units and to a little over a quarter on four. One tester ran DeepSeek V4 Flash 0731 with vLLM on two units and generated about four times as fast as llama.cpp RPC on the same two units, though with different weights and quantization, as the author points out.

CanRun does not calculate tensor parallelism. Every linked row on this site is a llama.cpp RPC estimate, so if you plan to run vLLM across units, read those rows as a llama.cpp baseline, not as a vLLM estimate. vLLM also uses its own weight formats and memory settings.

## How sure are these numbers?

Memory figures are calculated with a formula: real GGUF file sizes, KV cache sizes from each model's configuration, and a compute-buffer formula. The approximation is the GPU share, taken from the lowest public boot log for the 128GB model and worked out from it for the 64GB model. On linked units, CanRun checks the unit with the largest share of the model, using llama.cpp's default split of layers in proportion to each unit's free memory. That share is an approximation, because CanRun treats every layer as the same size.

Speeds on one unit are measured where a cell says so. The other one-unit cells are calibrated estimates with a ±20% band. Their factors are fitted to the llama.cpp maintainers' DGX Spark results file, run with mmap off, and to DGX Spark runs in a llama.cpp pull request; the prompt-processing factor comes from that pull request alone. Every linked verdict is a theoretical estimate (±30%), and it is never faster than CanRun's own one-unit estimate for the same model. A model that fits on one unit gets no linked verdict, as for Gemma 4 31B, whose one-unit cell shows a public benchmark.<Expect model="gemma-4-31b" gpu="nvidia-dgx-spark" ram="64" fits="true" confidence="measured" /><Expect model="gemma-4-31b" gpu="nvidia-dgx-spark" ram="64" nodes="2" oneUnit="true" /> If you pick linked units for it in the calculator, the linked estimate can come out higher than that benchmark, because the benchmark is below CanRun's own one-unit estimate. The hop time comes from public two-unit runs over the default TCP connection. Two-unit runs over RDMA lost less time per hop than CanRun assumes, measured against their own one-unit runs. There are no public four-unit runs to check against. Prompt processing on linked units is estimated as on one unit, with a rough ±40% band, and public two-unit runs moved both ways.

Not modelled: tensor parallelism, power modes, other programs' memory, and more than one request at a time. Verdict names in this guide's text refer to the 8k context, f16 KV baseline. Models with a thinking mode, even one that is off by default such as Gemma 4 31B's, can spend extra tokens thinking before they answer, so CanRun makes their speed thresholds 1.5× stricter; the legend below does not show this. ### Does linking two DGX Sparks make a model run faster?

Not with llama.cpp RPC: memory adds up, but each token passes through both units. CanRun's linked estimates are slower than its own one-unit estimates, and the public two-unit runs were no faster than one unit, or within a few percent of it. With tensor parallelism in vLLM or TensorRT-LLM, which NVIDIA's own guide and blog use, public results on two units were faster than one; in NVIDIA's test, Llama 3.3 70B generated about twice as fast. CanRun does not calculate that case.

### How many DGX Sparks can be linked?

Up to four, according to NVIDIA. Two or three connect directly with QSFP cables, and for four NVIDIA's guides use a 200GbE switch. NVIDIA recommends a power-of-two count. The <HubLink gpu="nvidia-dgx-spark" /> page lists two and four units; three can be checked in the calculator.

### Are the ASUS Ascent GX10 and other partner models the same machine?

They use the same GB10 chip and memory bandwidth and differ mainly in storage, so CanRun calculates them as the DGX Spark, and the calculator finds them by name. NVIDIA sells its own model only with 128GB; the 64GB size comes only from partner makers.

### Can a DGX Spark run 70B models?

It can hold them; it runs dense ones slowly.
