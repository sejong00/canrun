Ollama and LM Studio both run GGUF models on llama.cpp, the engine you can also run on its own, so the work done for each token comes from the same code. When one of them feels slower, the cause is usually a default: how long a context it reserves, how many requests share that memory, or who decides what goes on the GPU. On a 24GB card, for example, Ollama starts Qwen3 32B at 32k and pushes part of it into system RAM,<Expect model="qwen3-32b" gpu="rtx-4090" ctx="32768" fits="true" mode="partial-offload" /> while llama.cpp's own server shortens an unset context so the model stays on the GPU. CanRun's estimates are calculated for llama.cpp, and we have no side-by-side speed measurements of the three tools, so this guide compares settings, not winners.

## One engine, three front ends

llama.cpp is an open-source engine, under the MIT license, that loads a GGUF file and runs it on NVIDIA, AMD, Intel or Apple GPUs or on the CPU. It comes as a set of command-line programs. `llama-server` serves a chat page in the browser and an OpenAI-compatible API, and `llama-bench` measures speed. On Windows you download a ready-made build from its GitHub releases page and point it at a GGUF file, or let `-hf` fetch one from Hugging Face.

Ollama is a background service with a command-line tool, a desktop app and its own model library, also under the MIT license. Since version 0.30 it runs GGUF models by starting llama.cpp's `llama-server`, which it ships in its install folder, with a short list of flags. The llama.cpp build it ships is named in a file called `LLAMA_CPP_VERSION` in its source. On Apple Silicon it also has an MLX engine for some models. Its library names files by tag: on Ollama's tag list, `qwen3:14b` is the same file as `qwen3:14b-q4_K_M`.

LM Studio is a desktop app with a model browser, a local server and a command-line tool called `lms`. LM Studio says the app is free to use at home and at work. It runs GGUF models with its llama.cpp engine, in separate builds for CUDA, Vulkan, ROCm and the CPU, and on a Mac it adds an MLX engine. By default it updates these runtimes on its own, and you can switch between them in its runtimes tab or with `lms runtime`.

Changes made in llama.cpp reach Ollama and LM Studio when they update the build they ship. All three read the same GGUF files and offer an OpenAI-compatible API, so a chat app or coding tool that speaks that API can usually work with any of them. The memory a model needs at a given context length and KV cache type is also the same in all three; <GuideLink slug="vram-requirements" /> explains how it adds up. CanRun's numbers describe llama.cpp running a GGUF file. MLX models on a Mac take a different path and are outside this guide.

## The defaults that differ

With the same file on the same card, the three tools still start from different settings. These are the ones that change memory or speed:

- **Context length.** <RuntimeFact id="ollama-default-ctx" />. Its server log shows the value it picked on a line containing `vram-based default context`. `llama-server` started without `-c` takes the training context stored in the GGUF file, usually the model's maximum. Its fit option, on by default, then shortens that context if the model would not fit in free VRAM, down to a floor of 4k, before it moves any weights off the GPU. Passing `-c 0` asks for the full length and turns that shortening off. LM Studio takes the context from its load settings or `lms load --context-length`; its documentation does not give a default, so read the value in the load panel.
- **When the context fills up.** Ollama drops the oldest messages and keeps going, as <GuideLink slug="ollama-context-length" /> explains. `llama-server` has context shift off by default: a request longer than the context gets an error, and a reply stops when the context is full. LM Studio lets you choose between stopping at the limit, cutting out the middle of the chat and keeping a rolling window.
- **KV cache type.** All three start with f16, and all three can quantize it. <RuntimeFact id="ollama-kv-cache-type" />. In `llama-server` you set it per launch with `--cache-type-k` and `--cache-type-v`. LM Studio's load settings include a K cache and a V cache type, and its SDK reference notes that the V cache type needs flash attention.
- **Flash attention.** `llama-server` defaults to `auto`, and Ollama's FAQ says it uses flash attention automatically when the backend and devices support it. LM Studio has a flash attention switch in each model's load settings.
- **Parallel requests.** Ollama serves one request per model at a time unless you raise `OLLAMA_NUM_PARALLEL`. `llama-server` opens four slots that share one KV cache, and LM Studio 0.4 and later does the same. The section on parallel requests below shows what that means for memory.
- **GPU placement.** `llama-server` works out the number of GPU layers itself (`-ngl auto`). Ollama passes no layer count unless you set `num_gpu`, so llama.cpp decides there too. LM Studio picks the GPU offload automatically when you do not set it.

## Parallel requests and MoE models

### One context per request, or one shared cache

When several requests reach the same model at once, the three tools divide memory differently.

- **Ollama** gives each parallel request its own full context. It starts `llama-server` with the context length times `OLLAMA_NUM_PARALLEL`, and its FAQ says the memory needed grows with both. The default is one request, so a default install reserves one context.
- **`llama-server`** opens four slots by default with one shared ("unified") KV cache sized by the context. One request can use the whole cache, and requests that run at the same time share it, so the KV cache does not grow with the number of slots.
- **LM Studio** 0.4 and later works the same way: its Max Concurrent Predictions setting defaults to four, with Unified KV Cache on, which LM Studio says should add no memory overhead.

Raising `OLLAMA_NUM_PARALLEL` is where this matters. At 8k, Qwen3 14B's KV cache takes <Num kind="kvGB" model="qwen3-14b" ctx="8192" />, and the whole model fits on a 12GB RTX 3060, with less than a gigabyte to spare.<Expect model="qwen3-14b" gpu="rtx-3060-12gb" fits="true" mode="full-gpu" /> With `OLLAMA_NUM_PARALLEL=4` and the same 8k per request, Ollama reserves four of those, as much KV cache as one 32k context (<Num kind="kvGB" model="qwen3-14b" ctx="32768" />). In CanRun's calculation a 32k context no longer fits fully on that card, and part of the weights move to system RAM.<Expect model="qwen3-14b" gpu="rtx-3060-12gb" ctx="32768" fits="true" mode="partial-offload" /> CanRun's tables assume one request at a time.

### Who places the MoE experts

A mixture-of-experts (MoE) model reads only a few of its experts for each token, so the experts that do not fit in VRAM can sit in system RAM while the rest of the model stays on the GPU. <ComboLink model="qwen3-30b-a3b-2507" gpu="rtx-5060-ti-16gb" /> shows the split CanRun calculates. The model needs <Num kind="needGB" model="qwen3-30b-a3b-2507" />, more than the <Num kind="usableGB" gpu="rtx-5060-ti-16gb" /> the card can use, so the experts of some layers go to system RAM.

In this setup it Runs well, a theoretical estimate (±30%).<Expect model="qwen3-30b-a3b-2507" gpu="rtx-5060-ti-16gb" verdict="A" mode="cpu-moe" confidence="theoretical" /> llama.cpp's fit option makes the same kind of split by default. It puts the non-expert weights on the GPU first and moves experts to system RAM only as far as it has to. Ollama gets this split because it leaves the layer count to llama.cpp. A `num_gpu` value left in a Modelfile or a client changes that: Ollama then passes a fixed layer count, and llama.cpp splits whole layers instead of experts.

LM Studio's GPU offload setting moves whole layers. For MoE models it adds "Force Model Expert Weights onto CPU", which, as its release notes describe it, moves all expert weights to system RAM, like llama.cpp's `--cpu-moe`. On a card with room for some experts, that leaves VRAM unused, and CanRun's speed band does not describe that setting. LM Studio's documentation does not say whether its automatic offload splits experts the way llama.cpp's fit does. How much system RAM the larger MoE models need is covered in <GuideLink slug="moe-cpu-offload" />.

## Running all three on the same settings

To compare the tools on your own PC, take the defaults out of the picture. Use the same GGUF file, the same context and KV cache type, one request at a time, and the whole model on the GPU. The commands below load Qwen3 14B at Q4_K_M from the Hugging Face repository our combo pages use, at 8k. On a 16GB RTX 5060 Ti that fits fully on the GPU.<Expect model="qwen3-14b" gpu="rtx-5060-ti-16gb" fits="true" mode="full-gpu" />

**llama.cpp:** unzip a release build, open PowerShell in that folder and run the line below. On macOS or Linux, type `llama-server` instead of `.\llama-server.exe`. `-np 1` replaces the four default slots with one, like Ollama.

```powershell
.\llama-server.exe -hf unsloth/Qwen3-14B-GGUF:Q4_K_M -c 8192 -np 1 -ngl all -fa on
```

**Ollama:** quit the Ollama app from the taskbar, start the server with the context you want, then run the model from a second PowerShell window.

```powershell
$env:OLLAMA_CONTEXT_LENGTH="8192"; ollama serve
```

```powershell
ollama run hf.co/unsloth/Qwen3-14B-GGUF:Q4_K_M --verbose
```

`--verbose` prints timings after each reply, and "eval rate" is the generation speed. While the model is loaded, `ollama ps` should show `8192` under CONTEXT and `100% GPU` under PROCESSOR. The `hf.co/` name loads the same file as `llama-server`. A library tag such as `qwen3:14b` is a file Ollama packaged, so its size and contents can differ from another publisher's Q4_K_M.

**LM Studio:** open the Discover tab (Ctrl+2), search for `unsloth/Qwen3-14B-GGUF` and download the Q4_K_M option. When you load it, set the context length to `8192` and the GPU offload to the maximum, or do the same from a terminal, using the name `lms ls` lists for the model:

```powershell
lms load <model> --context-length 8192 --gpu max
```

Send each one the same prompt, skip the first run while things warm up, and compare generation speed. If the numbers still differ, two things are left to check:

- **The llama.cpp build.** Ollama ships the build named in its `LLAMA_CPP_VERSION` file, LM Studio shows each runtime's version in its runtimes tab (Ctrl+Shift+R), and llama.cpp's own builds are numbered. A newer build can be faster or slower for a given model.
- **The backend.** CUDA and Vulkan builds of llama.cpp can run the same model at different speeds. Ollama names the library it picked on the `inference compute` line of its server log, and LM Studio's runtimes tab shows which one is selected.

For a number that does not depend on any front end, `llama-bench` runs a fixed test on the same file: by default it times prompt processing (`-p 512`) and generation (`-n 128`) on an empty context. Adding `-d 8192` repeats the test with 8k already in the context, closer to a long chat.

## Which one fits how you work

The tool does not change how much memory a model needs. Pick the model, quant and context by memory first, then pick the tool for the way you work.

- **Ollama** suits you if you want a service that runs in the background and serves other apps, with models pulled by a short tag. Plan for its defaults: 4k below 24GB of VRAM, 32k on 24GB cards, and one KV cache type for every model on the server.
- **llama.cpp** suits you if you want every option and the newest build, and you are happy to manage files and command lines yourself. Its defaults lean toward keeping the model on the GPU, and it tells you with an error when a request is longer than the context.
- **LM Studio** suits you if you prefer a window to a terminal. You can browse Hugging Face, see a memory estimate and a warning before a load that is likely to run out of memory, and save settings per model. It runs four slots with a shared cache by default and adds MLX models on a Mac.

## How sure are these numbers?

The memory figures (weights, KV cache, compute buffer) are calculated from real GGUF file sizes and headers and each model's published configuration. They are the same whichever tool loads the file. The speeds are estimates with a band and a confidence label. Calibrated means ±12% for dense models fully on an NVIDIA or AMD card, and ±20% for partial offload, MoE models and other hardware. Theoretical means ±30%, and it applies here to Qwen3 30B-A3B (2507) with its experts split between VRAM and system RAM.

CanRun models llama.cpp, and nearly all the public benchmarks it calibrates against were run on llama.cpp directly, not through Ollama or LM Studio. gpt-oss-20b on the RTX 5060 Ti 16GB is one of them: it Runs great there, and its speed comes from a public measurement rather than an estimate.<Expect model="gpt-oss-20b" gpu="rtx-5060-ti-16gb" verdict="S" confidence="measured" /> That result comes from the llama.cpp project's own guide to running gpt-oss, measured with `llama-bench`.

## FAQ

### Is Ollama slower than llama.cpp?

Not because of the engine: since version 0.30, Ollama runs GGUF models through llama.cpp's own `llama-server`. When Ollama is slower with the same file, check the defaults first. The ones to check are a 32k context on a 24GB card, which pushes a dense model such as Qwen3 32B partly into system RAM,<Expect model="qwen3-32b" gpu="rtx-4090" ctx="32768" fits="true" mode="partial-offload" /> a leftover `num_gpu` value, a raised `OLLAMA_NUM_PARALLEL` and an older bundled llama.cpp build. `ollama ps` shows the context and the CPU/GPU split. CanRun has no side-by-side measurements, so it does not say which tool is faster.

### Why does LM Studio show a different speed from Ollama for the same model?

Usually because something other than the tool differs: the file (an Ollama library tag or a Hugging Face GGUF), the context length, the KV cache type, the GPU offload or the runtime (CUDA or Vulkan). Load the same file with the same settings, as in the section on running all three, and compare the generation speed after a warm-up run.

### Which one should I use on an 8GB or 12GB card?

Any of them, once you set the context yourself, because the memory a model needs is the same in all three. Ollama starts at 4k on these cards. That keeps a model such as Llama 3.1 8B fully on an 8GB card,<Expect model="llama-3.1-8b" gpu="rtx-4060" ctx="4096" fits="true" mode="full-gpu" /> but long chats lose their beginning quickly. `llama-server` shortens its starting context until the model fits, and LM Studio uses its Context Length setting. Pick the length from the context table on a combo page, such as our page for <ComboLink model="qwen3-14b" gpu="rtx-3060-12gb" />, and set it in whichever tool you use.

### Can the three tools share one model file?

Yes, with one catch for disk space. `llama-server` opens any GGUF file where it is, with `-m` and the path. LM Studio's `lms import` moves a file into its models folder by default; add `--hard-link` or `--symbolic-link` to leave the original in place. Ollama builds a model from a file with a Modelfile line `FROM` followed by the path, then `ollama create`, and keeps its own copy in its models folder. CanRun's combo pages print the Hugging Face name of the file they assume, so the same quant can be loaded in each tool.
