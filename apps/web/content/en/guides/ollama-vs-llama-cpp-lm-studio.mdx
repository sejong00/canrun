Ollama and LM Studio both run GGUF models on llama.cpp, the engine you can also run on its own, so the work done for each token comes from the same code. When one of them feels slower, the cause is usually a default: how long a context it reserves, how many requests share that memory, or who decides what goes on the GPU. On a 24GB card, for example, Ollama starts Qwen3 32B at 32k, which in CanRun's calculation pushes part of it into system RAM (`ollama ps` shows the split),<Expect model="qwen3-32b" gpu="rtx-4090" ctx="32768" fits="true" mode="partial-offload" /> while llama.cpp's own server shortens an unset context so the model stays on the GPU. CanRun's estimates are calculated for llama.cpp, and we have no side-by-side speed measurements of the three tools, so this guide compares settings, not winners.

## One engine, three front ends

llama.cpp is an open-source engine, under the MIT license, that loads a GGUF file and runs it on NVIDIA, AMD, Intel or Apple GPUs or on the CPU. It comes as a set of command-line programs. `llama-server` serves a chat page in the browser and an OpenAI-compatible API, and `llama-bench` measures speed. On Windows you download a ready-made build from its GitHub releases page and point it at a GGUF file, or let `-hf` fetch one from Hugging Face.

Ollama is a background service with a command-line tool, a desktop app and its own model library, also under the MIT license. Since version 0.30 it runs GGUF models by starting llama.cpp's `llama-server`, which it ships in its install folder, with a short list of flags. The llama.cpp build it ships is named in a file called `LLAMA_CPP_VERSION` in its source. On Apple Silicon it also has an MLX engine for some models. Its library names files by tag: on Ollama's tag list, `qwen3:14b` is the same file as `qwen3:14b-q4_K_M`.

LM Studio is a desktop app with a model browser, a local server and a command-line tool called `lms`. LM Studio says the app is free to use at home and at work. It runs GGUF models with its llama.cpp engine, in separate builds for CUDA, Vulkan, ROCm and the CPU, and on a Mac it adds an MLX engine. LM Studio calls these engines runtimes and by default updates them on its own; you can switch between them in its runtimes tab or with `lms runtime`.

A change in llama.cpp reaches Ollama and LM Studio only when they update the llama.cpp build they ship. All three read the same GGUF files and offer an OpenAI-compatible API, so a chat app or coding tool that speaks that API can usually work with any of them. The weights and KV cache a model needs at a given context length and KV cache type are also the same in all three; only the compute buffer, the runtime's working memory, depends on a batch setting that Ollama picks differently (see the list below and, for how memory adds up, <GuideLink slug="vram-requirements" />). CanRun's numbers describe llama.cpp running a GGUF file. Models that a Mac runs on the MLX engine do not go through llama.cpp and are outside this guide.

## The defaults that differ

With the same file on the same card, the three tools still start from different settings. These are the ones that change memory or speed:

- **Context length.** <RuntimeFact id="ollama-default-ctx" />. Its server log shows the value it picked on a line containing `vram-based default context`. `llama-server` started without `-c` takes the training context stored in the GGUF file, usually the model's maximum. Its fit option, on by default, then shortens that context if the model would not fit in free VRAM, down to a floor of 4k, before it moves any weights off the GPU. Passing `-c 0` asks for the full length and turns that shortening off. LM Studio takes the context from its load settings or `lms load --context-length`; its documentation does not give a default, so read the value in the load panel.
- **When the context fills up.** Ollama drops the oldest messages and keeps going (see <GuideLink slug="ollama-context-length" />). `llama-server` has context shift off by default: a request longer than the context gets an error, and a reply stops when the context is full. LM Studio lets you choose between stopping at the limit, cutting out the middle of the chat and keeping a rolling window.
- **KV cache type.** All three start with f16, and all three can quantize it. <RuntimeFact id="ollama-kv-cache-type" />. In `llama-server` you set it per launch with `--cache-type-k` and `--cache-type-v`. LM Studio's load settings include a K cache and a V cache type, and its SDK reference notes that the V cache type needs flash attention.
- **Flash attention.** `llama-server` defaults to `auto`, and Ollama's FAQ says it uses flash attention automatically when the backend and devices support it. LM Studio has a flash attention switch in each model's load settings.
- **Batch size.** `llama-server` processes prompts in chunks of 512 tokens (`-ub`) by default. Recent Ollama versions raise that to 1024 or 2048 for contexts above 4k when VRAM allows, unless you set `num_batch`. That speeds up prompt processing and takes a larger compute buffer.
- **Parallel requests.** Ollama serves one request per model at a time unless you raise `OLLAMA_NUM_PARALLEL`. `llama-server` opens four slots that share one KV cache, and LM Studio 0.4 and later does the same. The section on parallel requests below shows what that means for memory.
- **GPU placement.** `llama-server` works out the number of GPU layers itself (`-ngl auto`). Ollama passes no layer count unless you set `num_gpu`, so llama.cpp decides there too. LM Studio picks the GPU offload automatically when you do not set it.

## Parallel requests and MoE models

### One context per request, or one shared cache

When several requests reach the same model at once, the three tools divide memory differently.

- **Ollama** gives each parallel request its own full context. It starts `llama-server` with the context length times `OLLAMA_NUM_PARALLEL`, and its FAQ says the memory needed grows with both. The default is one request, so a default install reserves one context.
- **`llama-server`** opens four slots by default with one shared ("unified") KV cache sized by the context. One request can use the whole cache, and requests that run at the same time share it, so the KV cache does not grow with the number of slots.
- **LM Studio** 0.4 and later works the same way: its Max Concurrent Predictions setting defaults to four, with Unified KV Cache on, which LM Studio says should add no memory overhead.

Raising `OLLAMA_NUM_PARALLEL` is where this matters. At 8k, Qwen3 14B's KV cache takes <Num kind="kvGB" model="qwen3-14b" ctx="8192" />, and the whole model fits on a 12GB RTX 3060, with less than a gigabyte to spare.<Expect model="qwen3-14b" gpu="rtx-3060-12gb" fits="true" mode="full-gpu" /> With `OLLAMA_NUM_PARALLEL=4` and the same 8k per request, Ollama reserves four of those, as much KV cache as one 32k context (<Num kind="kvGB" model="qwen3-14b" ctx="32768" />). In CanRun's calculation a 32k context no longer fits fully on that card, and part of the weights move to system RAM.<Expect model="qwen3-14b" gpu="rtx-3060-12gb" ctx="32768" fits="true" mode="partial-offload" /> CanRun's tables assume one request at a time.

## Running all three on the same settings

To compare the tools on your own PC, take the defaults out of the picture. Use the same GGUF file, the same context and KV cache type, one request at a time, and the whole model on the GPU. The commands below load Qwen3 14B at Q4_K_M from the Hugging Face repository our combo pages use, at 8k. On a 16GB RTX 5060 Ti that fits fully on the GPU.<Expect model="qwen3-14b" gpu="rtx-5060-ti-16gb" fits="true" mode="full-gpu" />

**llama.cpp:** from the GitHub releases page, take the CUDA build and the matching cudart file for an NVIDIA card (the Vulkan build for AMD or Intel), unzip both into one folder, open PowerShell there and run the line below. On macOS or Linux, type `llama-server` instead of `.\llama-server.exe`. `-np 1` replaces the four default slots with one, like Ollama. Check that the startup log names your GPU; if it does not, the build is running on the CPU. After each reply, the console prints the generation speed on its `eval time` line.

```powershell
.\llama-server.exe -hf unsloth/Qwen3-14B-GGUF:Q4_K_M -c 8192 -np 1 -ngl all -fa on
```

**Ollama:** either set the context length slider in the app's settings to 8k and leave the app running, or quit the app from the taskbar and start the server with the context you want. Then run the model from a second PowerShell window.

```powershell
$env:OLLAMA_CONTEXT_LENGTH="8192"; ollama serve
```

```powershell
ollama run hf.co/unsloth/Qwen3-14B-GGUF:Q4_K_M --verbose
```

`--verbose` prints timings after each reply, and "eval rate" is the generation speed. While the model is loaded, `ollama ps` should show `8192` under CONTEXT and `100% GPU` under PROCESSOR. The `hf.co/` name loads the same file as `llama-server`. A library tag such as `qwen3:14b` is a file Ollama packaged, so its size and contents can differ from another publisher's Q4_K_M. Ollama may also pick a larger batch at this context, which changes prompt speed but not generation speed, so compare generation speed.

**LM Studio:** open model search (the search button at the top right, or Ctrl+Shift+M), search for `unsloth/Qwen3-14B-GGUF` and download the Q4_K_M option. When you load it, set the context length to `8192`, the GPU offload to the maximum and Flash Attention on to match `-fa on`. You can also load it from a terminal, using the name `lms ls` lists for the model:

```powershell
lms load <model> --context-length 8192 --gpu max
```

`lms chat <model> --stats` then prints the speed after each reply. Send each tool the same prompt, skip the first run while things warm up, and compare generation speed. If the numbers still differ, two things are left to check:

- **The llama.cpp build.** Ollama ships the build named in its `LLAMA_CPP_VERSION` file, LM Studio shows each runtime's version in its runtimes tab (Ctrl+Shift+R), and llama.cpp's own builds are numbered. A newer build can be faster or slower for a given model.
- **The backend.** CUDA and Vulkan builds of llama.cpp can run the same model at different speeds. Ollama names the library it picked on the `inference compute` line of its server log, and LM Studio's runtimes tab shows which one is selected.

For a number that does not depend on any front end, `llama-bench` runs a fixed test on the same file: by default it times prompt processing (`-p 512`) and generation (`-n 128`) on an empty context. Adding `-d 8192` repeats the test with 8k already in the context, closer to a long chat.

## Which one fits how you work

The tool does not change the weights and KV cache a model needs. Pick the model, quant and context by memory first, then pick the tool for the way you work.

- **Ollama** suits you if you want a service that runs in the background and serves other apps, with models pulled by a short tag. Set the context yourself on cards below 24GB, and remember that one KV cache type applies to every model on the server.
- **llama.cpp** suits you if you want every option and the newest build, and you are happy to manage files and command lines yourself. Its defaults lean toward keeping the model on the GPU, and it tells you with an error when a request is longer than the context.
- **LM Studio** suits you if you prefer a window to a terminal. You can browse Hugging Face, see a memory estimate and a warning before a load that is likely to run out of memory, and save settings per model. On a Mac it also runs MLX models.

## How sure are these numbers?

The memory figures (weights, KV cache, compute buffer) are calculated from real GGUF file sizes and headers and each model's published configuration. The weights and KV cache are the same whichever tool loads the file; the compute buffer depends on the batch size. The speeds are estimates with a band and a confidence label. Calibrated means ±12% for dense models fully on an NVIDIA or AMD card, and ±20% for partial offload, MoE models and other hardware. Theoretical means ±30%, and it applies here to Qwen3 30B-A3B (2507) with its experts split between VRAM and system RAM.

CanRun models llama.cpp, and nearly all the public benchmarks it calibrates against were run on llama.cpp directly, not through Ollama or LM Studio. gpt-oss-20b on the RTX 5060 Ti 16GB is one of them: it Runs great there, and its speed comes from a public measurement rather than an estimate.<Expect model="gpt-oss-20b" gpu="rtx-5060-ti-16gb" verdict="S" confidence="measured" /> That result comes from the llama.cpp project's own guide to running gpt-oss, measured with `llama-bench`.

## FAQ

### Is Ollama slower than llama.cpp?

Not because of the engine: since version 0.30, Ollama runs GGUF models through llama.cpp's own `llama-server`. Check `ollama -v` first; versions before 0.30 used a different engine, and the 0.30 release notes list faster performance on NVIDIA cards. When a current Ollama is slower with the same file, check the defaults. The ones to check are a 32k context on a 24GB card, which pushes a dense model such as Qwen3 32B partly into system RAM,<Expect model="qwen3-32b" gpu="rtx-4090" ctx="32768" fits="true" mode="partial-offload" /> a leftover `num_gpu` value, a raised `OLLAMA_NUM_PARALLEL` and an older bundled llama.cpp build. `ollama ps` shows the context and the CPU/GPU split. CanRun has no side-by-side measurements, so it does not say which tool is faster.

### Why does LM Studio show a different speed from Ollama for the same model?

Usually because something other than the tool differs: the file (an Ollama library tag or a Hugging Face GGUF), the context length, the KV cache type, flash attention, the GPU offload or the runtime (CUDA or Vulkan). Load the same file with the same settings, as in the section on running all three, and compare the generation speed after a warm-up run.

### Which one should I use on an 8GB or 12GB card?

Any of them, once you set the context yourself, because the weights and KV cache a model needs are the same in all three. Ollama starts at 4k on these cards. That keeps a model such as Llama 3.1 8B fully on an 8GB card,<Expect model="llama-3.1-8b" gpu="rtx-4060" ctx="4096" fits="true" mode="full-gpu" /> but long chats lose their beginning quickly. `llama-server` shortens its starting context until the model fits, and LM Studio uses its Context Length setting. Pick the length from the context table on a combo page, such as our page for <ComboLink model="qwen3-14b" gpu="rtx-3060-12gb" />, and set it in whichever tool you use.

### Can the three tools share one model file?

Yes, with one catch for disk space. `llama-server` opens any GGUF file where it is, with `-m` and the path. LM Studio's `lms import` moves a file into its models folder by default; add `--hard-link` or `--symbolic-link` to leave the original in place. Ollama builds a model from a file with a Modelfile line `FROM` followed by the path, then `ollama create`, and keeps its own copy in its models folder. CanRun's combo pages print the Hugging Face name of the file they assume, so the same quant can be loaded in each tool.
