## How MoE models differ from dense models

In a dense model such as <HubLink model="qwen3-32b" />, every token passes through every weight, so the speed of generation follows the size of the whole file. In an MoE model, most of each layer is split into many small feed-forward blocks called experts, and a router picks a few of them for each token. According to their configuration files, gpt-oss-120b has 128 experts per layer and uses 4 for each token, while Qwen3.6 35B-A3B has 256 and uses 8 plus one shared expert. The Parameters column below gives both counts: the total, which sets the memory need, and the active part, which sets most of the work per token.

The router can pick any expert, so every expert has to be in memory somewhere. An MoE model therefore needs as much memory as a dense model with the same total, as <GuideLink slug="vram-requirements" /> explains. What MoE changes is where that memory can be. Nearly all of an MoE file is expert weights: in the gpt-oss-120b file, the non-expert (shared) weights, such as attention, come to only a few percent. That small part and the KV cache (the memory that holds the context) should stay on the GPU for speed. The experts can sit in system RAM, and only the few that each token uses are read from there.

## How the experts end up in system RAM

llama.cpp, the engine behind Ollama 0.30 and later and many other local tools, has two options for this. `--cpu-moe` keeps all MoE weights in system RAM. `--n-cpu-moe N` keeps only the expert weights of the first N layers there, so the experts of the other layers stay on the GPU. Since build b7410 (December 2025), llama.cpp also makes this split by default: its `--fit` option puts the non-expert weights ("dense weights" in the PR) on the GPU first and moves expert weights to system RAM only as far as it has to.

CanRun's calculation follows the same order. It puts the non-expert weights, the KV cache and the compute buffer (the runtime's working memory) on the GPU first. It then fills the remaining VRAM with the experts of whole layers, keeps one layer's worth free as a margin, and leaves the experts of the remaining layers in system RAM. The expert and non-expert sizes come from each GGUF file's header, not from a formula. The N that results is the number our combo pages print in the llama.cpp command.

## RAM speed sets the pace

In this mode each token reads two things. The chosen experts of the layers in system RAM come from RAM, and everything on the GPU, including its experts and the KV cache, comes from VRAM. RAM is far slower. DDR5-5600 in dual channel moves <Num kind="bandwidth" gpu="cpu-ddr5-5600-2ch" />, against <Num kind="bandwidth" gpu="rtx-3060-12gb" /> on the RTX 3060 12GB. CanRun's formula counts on only half of the RAM figure for this part, a factor fitted to public measurements. The more experts sit in RAM, the more the RAM sets the speed.

Bandwidth is the transfer rate times eight bytes per channel times the number of channels. DDR4-3200 in dual channel gives <Num kind="bandwidth" gpu="cpu-ddr4-3200-2ch" />, a little over half of DDR5-5600. In CanRun's calculation, moving gpt-oss-120b from DDR5-5600 to DDR4-3200 lowers the estimate by a third to two-fifths on the 12GB to 32GB cards, where most of its experts are in RAM. For Qwen3.6 35B-A3B on the RTX 3060 12GB, where a larger share of each token's work happens on the GPU, it drops by about a fifth. The calculator's RAM type field (DDR4-3200, DDR5-5600 or DDR5-6000) shows the effect on your own setup.

Mainstream desktop processors have two memory channels. Intel's specification page for the Core Ultra 9 285K and AMD's for the Ryzen 7 9700X both list two. More sticks add capacity, not channels, and they can lower the rated speed: AMD lists the Ryzen 7 9700X at DDR5-5600 with two sticks but DDR5-3600 with four, about two-thirds of the bandwidth. When you add RAM for a large MoE model, check what your processor and motherboard support with four sticks before you count on the full speed.

## Running it: llama.cpp and Ollama commands

On Windows, llama.cpp ships ready-made builds on its GitHub releases page; for an NVIDIA card, take the CUDA build together with the matching cudart file. Unzip both into one folder and open PowerShell in that folder; on macOS or Linux, run `llama-server` instead of `.\llama-server.exe`. With a build from December 2025 or later, the simplest command leaves the split to `--fit`:

```powershell
.\llama-server.exe -hf ggml-org/gpt-oss-120b-GGUF:MXFP4 -c 8192
```

To fix the split yourself, set `-ngl` and `--n-cpu-moe`; `--fit` leaves options you set alone. This is the command our page prints for gpt-oss-120b on the RTX 3060 12GB with 64GB of RAM (the N for other cards is on each combo page):

```powershell
.\llama-server.exe -hf ggml-org/gpt-oss-120b-GGUF:MXFP4 -c 8192 -ngl all --n-cpu-moe 32 -fa on
```

`-ngl all` puts every layer on the GPU, and `--n-cpu-moe 32` then sends the experts of the first 32 layers back to system RAM. If loading fails for lack of VRAM, for example after you raise the context, raise N by one or two: each step moves one more layer's experts to RAM.

With Ollama, quit the Ollama app from the taskbar, then start the server with the context you want and run the model from Hugging Face in a second PowerShell window:

```powershell
$env:OLLAMA_CONTEXT_LENGTH="8192"; ollama serve
```

```powershell
ollama run hf.co/ggml-org/gpt-oss-120b-GGUF:MXFP4
```

On macOS or Linux the first line is `OLLAMA_CONTEXT_LENGTH=8192 ollama serve`. Ollama decides the split on its own: unless you set `num_gpu`, it starts llama-server without a GPU layer count, and llama.cpp's `--fit` places the experts. For how to set the context permanently, see <GuideLink slug="ollama-context-length" />. In LM Studio, the "Force Model Expert Weights onto CPU" load setting keeps all expert weights in RAM, the same as `--cpu-moe`.

### Check where the model landed

Run `ollama ps` while the model is loaded: the PROCESSOR column shows the split between CPU and GPU. With llama.cpp, the startup log reports how much of the model went to each device. A model whose experts sit partly in RAM always shows a split; what matters is that the GPU share is as large as your VRAM allows.

On Windows, NVIDIA's driver can borrow shared system memory when VRAM runs out, so with N set too low llama.cpp may run far below the estimate without an error. NVIDIA's support article shows how to turn this off for one program: in the NVIDIA Control Panel, under Manage 3D settings and Program Settings, add llama-server.exe and set "CUDA - Sysmem Fallback Policy" to "Prefer No Sysmem Fallback". A split that is too tight then fails with an out-of-memory error instead.

## How sure are these numbers?

Fit is calculated by formula. CanRun reads each MoE file's expert and non-expert sizes from its GGUF header, adds the KV cache and the compute buffer, and compares the parts with the VRAM and system RAM the PC can use. Whether a model fits with a given amount of RAM is therefore a calculation, not an estimate. Results right at a RAM step, such as gpt-oss-120b on an 8GB card with 64GB, depend on the margins CanRun keeps: 4GB of RAM for the system and one free layer of VRAM.

All speeds here are generation speeds. With experts in system RAM they are theoretical estimates (±30%). Against 42 public measurements, the formula's average error was about 11%; on the 35 measured on NVIDIA cards it was about 10%, and 89% of them landed within ±20%. Some setups were off by close to 40%, depending on the OS, the backend and the RAM, so the label stays theoretical. Setups the formula does not describe well were left out of that check: the Vulkan backend, 8-channel server memory and very long contexts of 32k and beyond.

All of this assumes Windows with the card driving the display, DDR5-5600 dual-channel RAM, an 8k context, an f16 KV cache, one model loaded and one request at a time. llama.cpp's automatic split keeps its own margin of free VRAM on each GPU, so the N it picks can differ from CanRun's by a layer or so.

### Should I add RAM or get a card with more VRAM?

Add RAM first if the model does not fit at all; once it fits, more RAM does not raise CanRun's estimate. After that, more VRAM keeps more expert layers on the GPU and faster RAM speeds up the rest; the grid above shows each card. When you plan new RAM, aim for the smallest size at which your model fits, in a stick count your processor supports at full speed.

### Why is my MoE model slow even though it fits?

Usually because more of it sits in system RAM than needed, or the RAM is slower than you think. Check the split with `ollama ps` or the llama.cpp log; if Ollama's GPU share is far below your VRAM, look for a leftover `num_gpu` setting or try llama.cpp with `--n-cpu-moe`. `--cpu-moe` puts every expert in RAM even when some would fit, four sticks of RAM may run at a lower rated speed than two, and a long context moves more experts to RAM. On Windows, a split that is too tight can spill into shared GPU memory, as the commands section explains.

### Should I use `--cpu-moe` or `--n-cpu-moe`?

Use `--n-cpu-moe N` when you set the split yourself, because it keeps as many expert layers on the GPU as fit. `--cpu-moe` is the same as putting every layer's experts in RAM, which is slower whenever the card has room for some of them. With a llama.cpp build from December 2025 or later you can leave both out and let `--fit` choose, but keep `-c`: without it, `--fit` may shorten the context before it moves any weights. Our combo pages print the N CanRun calculated for each card.
