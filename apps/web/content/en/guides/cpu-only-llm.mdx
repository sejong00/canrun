## RAM bandwidth sets the speed: DDR4, DDR5 and dual channel

To write one token, the processor reads every weight the model uses for that token, plus the KV cache, the memory that holds the conversation so far. Memory bandwidth, how many gigabytes per second the processor can read from RAM, limits how often it can do that. CanRun's estimate is the RAM's rated bandwidth times an efficiency factor, divided by the bytes read per token. For a dense model on a CPU, CanRun counts on half of the rated bandwidth, a factor fitted to public benchmarks for processors with eight or more cores.

Going from DDR4-3200 to DDR5-5600 adds about three-quarters to the bandwidth, and CanRun's estimates rise by the same ratio. Llama 3.1 8B Runs slowly on both,<Expect model="llama-3.1-8b" gpu="cpu-ddr4-3200-2ch" verdict="B" /><Expect model="llama-3.1-8b" gpu="cpu-ddr5-5600-2ch" verdict="B" /> but its band on the DDR5 row sits well above the DDR4 one. A graphics card reads its own memory much faster: the RTX 3060 12GB reads <Num kind="bandwidth" gpu="rtx-3060-12gb" />, about four times dual-channel DDR5-5600.

### One stick or two

All three profiles assume dual channel. Mainstream desktop processors have two memory channels; Intel's specification for the Core Ultra 9 285K, for example, lists two. Corsair's guide to dual-channel RAM describes a single stick as single-channel and dual channel as twice its speed. With one stick, the bandwidth halves, and in CanRun's formula so does the estimate for every model. If your PC has one stick, a second matching stick in the slot your motherboard manual names doubles the bandwidth in CanRun's calculation. Four sticks can lower the rated memory speed on some processors; <GuideLink slug="moe-cpu-offload" /> covers that case.

## Integrated graphics, Macs and Strix Halo

Most desktop and laptop processors include integrated graphics. Microsoft's explanation of GPU memory in Task Manager says that on integrated GPUs, dedicated memory is system memory reserved for graphics, and that integrated and discrete GPUs alike can use shared system memory. So integrated graphics read the same dual-channel RAM as the processor. In a calculation driven by memory bandwidth, like CanRun's, they cannot generate faster than that RAM allows. CanRun has no profile for ordinary integrated graphics; for such a PC, pick the CPU profile that matches its RAM.

Some machines without a graphics card run models faster because their memory bus is wider. ## How sure are these numbers?

The memory figures are calculated by formula from real GGUF file sizes and each model's published configuration, so they carry no band. On a CPU, CanRun counts the whole file, the KV cache and the 4GB it keeps for the system.

The speeds are estimates with a band and a label. CPU-only cells are calibrated, ±20%, the band CanRun uses everywhere except dense models fully on NVIDIA and AMD graphics cards. Models with layer types CanRun's speed formula has not been checked against, such as LFM2.5 and Ling 3.0, are theoretical, ±30%. The CPU factor assumes a processor with eight or more cores and desktop DDR4 or DDR5 in dual channel. CanRun does not model core count, so a processor with fewer cores can land below the band.

CanRun's data has no CPU-only measurement with stated conditions for the models in this guide. The nearest public figure is a community result collected on hardware-corner.net: a range for a Q4 file of the original Qwen3 30B-A3B, which has the same architecture as the 2507 update, on dual-channel DDR5-5600. It names neither the processor, the runtime nor the context length, so CanRun does not count it as a measurement. Even the low end of that range is above CanRun's 8k estimate band for Qwen3 30B-A3B and above its 4k estimate, so for this model CanRun's CPU estimate may be on the low side.

CanRun gives no prompt-processing estimate for CPU-only setups. Reading the prompt depends on compute rather than bandwidth, so the rates here do not tell you how long a long prompt or a pasted document takes to read. `llama-bench` measures both: prompt processing with `-p` and generation with `-n`.

All of this assumes an 8k context filled to that length, an f16 KV cache, one model loaded, one request at a time and a llama.cpp-class runtime.
