## How fast is fast enough: CanRun's verdict lines

Local runtimes report two speeds. Generation speed (Ollama's `eval rate`, llama-bench's `tg`) is how fast the reply appears. Prompt processing (`prompt eval rate`, or `pp`) is how fast the model reads what you send, and it decides how long you wait before the first word. CanRun's verdicts use generation speed, estimated at an 8k context; prompt processing has its own section further down.

## What sets generation speed: memory bandwidth and bytes per token

To write one token, the GPU reads every weight the model uses for that token, plus the KV cache, the memory that holds the conversation so far. Memory bandwidth, how many gigabytes per second the card can read from its VRAM, limits how often it can do that. CanRun's estimate is the card's bandwidth times an efficiency factor, divided by the bytes read per token. For a dense model fully on an NVIDIA card, CanRun counts on about seven-tenths of the rated bandwidth; the factor differs by hardware class and was fitted to public benchmarks.

The rule of thumb follows from that division: double the bandwidth and the estimate roughly doubles; double the bytes per token and it halves. Bandwidth spans a wide range, from <Num kind="bandwidth" gpu="rtx-4060" /> on the RTX 4060 to <Num kind="bandwidth" gpu="rtx-5090" /> on the RTX 5090.

## Prompt processing: why the first word can take a while

Before it writes anything, the model reads the whole prompt: the system prompt, the chat history and your new message. It takes these tokens in large batches, so this step is limited by the GPU's compute rather than its memory bandwidth. Generation goes one token at a time and waits on memory.

llama.cpp's public scoreboard for NVIDIA cards, which runs Llama 2 7B at Q4_0 through llama-bench, shows the split. The RTX 4090 has only a little more bandwidth than the RTX 3090 (<Num kind="bandwidth" gpu="rtx-4090" /> against <Num kind="bandwidth" gpu="rtx-3090" />). In that scoreboard it generates less than a fifth faster but processes prompts more than twice as fast. The RTX 3060 (12GB) generates nearly a fifth faster than the RTX 4060 Ti (8GB), while the RTX 4060 Ti reads prompts about one and a half times as fast.

The wait before the first word is roughly the new prompt tokens divided by the prompt speed, plus loading time if the model was not in memory yet. In a chat it stays short, because runtimes reuse the part of the prompt they have already processed: Ollama reports those tokens as `prompt eval cached`, and llama-server as `cache_n`. It grows when you paste a long document or run an agent, whose instructions and tool descriptions alone are long; <GuideLink slug="local-coding-agents" /> covers that case.

CanRun's combo pages show a prompt speed as a rough estimate (±40%), calculated from the card's FP16 compute and shown only when the whole model is on the GPU. It is fitted to a 7B model and is the same for every model on a card, so larger dense models read prompts more slowly than it shows.

## Measuring speed on your own PC

### Ollama

Run a model with `--verbose`. The command is the same in PowerShell, macOS and Linux:

```powershell
ollama run llama3.1:8b --verbose
```

In a session that is already running, `/set verbose` turns on the same output. After each reply Ollama prints its timings:

- `eval rate` is the generation speed, the figure to compare with CanRun's tables.
- `prompt eval rate` is the prompt speed, counted only over the tokens it actually processed. `prompt eval cached` shows how many it reused.
- `load duration` is the time spent loading the model. It counts toward `total duration` but not toward either rate.

Ask for a reply of several paragraphs, since a very short reply gives a noisy rate. While the model is loaded, run `ollama ps` in a second window. If CanRun shows the model fully on the GPU, PROCESSOR should read 100% GPU, and a CPU/GPU split explains a low rate. For an MoE model that CanRun places partly in system RAM, a split is expected. The rate also drifts down as a chat grows, for the reason in the context table above.

### llama.cpp: llama-bench and llama-server

llama-bench ships with llama.cpp and runs a fixed test. By default it reads a 512-token prompt (`pp512`) and generates 128 tokens (`tg128`), five times each, and reports the averages. Those tests start from an empty context, so for most models `tg128` comes out above CanRun's 8k figure. The `-d` option fills the KV cache first: `-d 0,8192` prints the empty-context rows plus rows marked `@ d8192`, which are the closest to CanRun's baseline. On Windows, in PowerShell from the llama.cpp folder:

```powershell
.\llama-bench.exe -hf bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M -d 0,8192
```

On macOS and Linux, leave out `.\` and `.exe`; `-m` takes a local GGUF file instead of `-hf`. llama-bench puts every layer on the GPU by default. For a model larger than your VRAM, set `-ngl` to fewer layers or give `-fitt` a memory margin in MiB so it fits the model for you, and use `-ncmoe` for MoE models. llama-bench leaves tokenization and sampling out of its timings, so real use can be slightly slower than it reports.

llama-server returns a `timings` object with each response: `predicted_per_second` is the generation speed, `prompt_per_second` the prompt speed and `cache_n` the prompt tokens reused from the cache.

### LM Studio

LM Studio's REST API (`POST /api/v1/chat`) returns a `stats` object with `tokens_per_second`, the generation speed, and `time_to_first_token_seconds`. When the request had to load the model first, `model_load_time_seconds` appears too.

### Comparing your number with CanRun's

Match the conditions before you compare. Use the same quant (a Q4_K_XL file differs in size from a Q4_K_M, so its speed differs too), the same context depth (CanRun's verdicts assume 8k), the same backend (CUDA, ROCm, Vulkan or Metal) and nothing else loaded on the card. A laptop GPU is often a different chip from the desktop card with the same name, with less memory and bandwidth (the <HubLink gpu="rtx-4090-laptop" /> reads <Num kind="bandwidth" gpu="rtx-4090-laptop" />), so compare with its Laptop entry; power and heat limits can lower it further. If your rate is far below the band in CanRun's table, check `ollama ps` for a CPU/GPU split first, since that costs the most speed.

## How sure are these numbers?

Every speed on CanRun is an estimate with a band and a label. Measured means a public benchmark of that card, model and quant; it is shown first, with CanRun's estimate next to it. Calibrated means ±12% for dense models fully on an NVIDIA or AMD card and ±20% for MoE models, partial offload and other hardware. Theoretical means ±30%, used where real speeds vary widely, such as MoE experts in system RAM. Against 12 reference benchmarks, the speed formula's mean error is 4.7% and its largest 10.5%. For MoE models fully on the GPU, against 45 public results from 2026 llama.cpp builds, it is 8.9% and 19.9%. ## FAQ

### How many tokens per second is good for a local LLM?

For chat, CanRun's top verdict line, in the legend in the first section, sits above typical reading pace: a speed above it puts text on screen faster than you can read it, and the band between the two upper lines is usable if you read along. Thinking models need lines 1.5 times higher, because they write their reasoning before the answer. For agents and long documents, prompt speed matters as much as generation speed. On an 8GB RTX 4060, Llama 3.1 8B clears the top line and Runs great.<Expect model="llama-3.1-8b" gpu="rtx-4060" verdict="S" />

### Why is my local model slower than the benchmarks I see online?

Usually the conditions differ. Many published figures, including llama-bench's default `tg128`, start from an empty context, while a long chat makes each token read a larger KV cache. Other causes are a different quant, a different backend, a laptop GPU that is a smaller chip than its desktop namesake and, costing the most, a model that spilled into system RAM. Check PROCESSOR in `ollama ps`, then compare the `eval rate` from `ollama run --verbose` with the band in CanRun's table.

### Does more VRAM make a model run faster?

Only when the extra memory stops a spill into system RAM. Once a model fits, bandwidth sets the speed: Qwen3 14B Runs well on the RTX 4060 Ti 16GB<Expect model="qwen3-14b" gpu="rtx-4060-ti-16gb" verdict="A" /> and Runs great on the RTX 5060 Ti 16GB,<Expect model="qwen3-14b" gpu="rtx-5060-ti-16gb" verdict="S" /> two 16GB cards with different bandwidth.

### Why does the reply take so long to start?

The model reads the whole new prompt before it writes, and that step depends on the GPU's compute. A long pasted document or an agent's instructions take the longest, and loading the model counts too (`load duration` in Ollama's verbose output). In a chat, runtimes reuse what they processed before, so later turns start faster unless something near the start of the prompt changes.

### Why do MoE models like Qwen3 30B-A3B run faster than smaller dense models?

They read only the experts the router picks for each token, about a tenth of the weights for Qwen3 30B-A3B, so each token costs fewer bytes. The whole file must still fit in memory. On a 24GB RTX 3090 it fits and Runs great,<Expect model="qwen3-30b-a3b-2507" gpu="rtx-3090" verdict="S" /> and CanRun estimates it faster there than the dense Qwen3 14B.
