## Why agents need a much longer context than chat

An agent turn carries far more than a chat message: the agent's instructions, a description of every tool it may call, the conversation so far, the files it opened, the output of the commands it ran, and room for the reply, all in the context at once. OpenClaw's page on local models asks you to leave room for all of that, and warns that a model which handles a short prompt can still fail a full agent turn.

Ollama's context-length page says agents, web search and coding tools should get at least 64k tokens, and its integration pages repeat it for OpenCode, OpenClaw and Claude Code. Ollama documents a one-line setup for each (`ollama launch opencode`, `ollama launch openclaw`, `ollama launch claude`), but with a local model the context is still yours to set.

The runtime's own default is much smaller on most cards. <RuntimeFact id="ollama-default-ctx" />. A 16GB card therefore starts at 4k unless something sets the length, and a full window makes Ollama drop the oldest messages without an error (see <GuideLink slug="ollama-context-length" />). OpenClaw sends a context length with its requests to Ollama's native API, which its documentation says is normally capped at 32k for local models it discovers. OpenCode's Ollama example goes through Ollama's OpenAI-compatible endpoint, and Ollama's OpenCode page tells you to set the window yourself, so set it on the Ollama side.

Thinking models spend the same window on their reasoning. Qwen3.6 35B-A3B and Qwen3.8 27B think by default, according to their model cards, and the Qwen3.6 card advises at least 128k of context to preserve its thinking. ## Waiting time: the model reads the prompt before it writes

A local model has two speeds: prompt processing, how fast it reads what it is sent, and generation, how fast it writes the reply. CanRun's verdicts and speed bands are generation estimates. In an agent the prompt is long: the first turn of a session carries the agent's instructions and every tool description, and later turns can add a whole file or a long command output. The model reads all of it before the first word of the reply appears.

Reading goes much faster per token than writing, because the GPU takes the prompt many tokens at a time and writes the reply one token after another. In llama.cpp's scoreboard for NVIDIA cards, the prompt rate (pp512) is many times the generation rate (tg128), and the public gpt-oss-20b run listed on the <HubLink gpu="rtx-5060-ti-16gb" /> page shows the same pattern. CanRun estimates prompt speed from a card's FP16 compute and generation speed from its memory bandwidth. Prompt estimates are rough (±40%), and combo pages show them only when the whole model runs on the GPU; with experts or layers in system RAM, CanRun gives none.

Runtimes do not reread what has not changed. llama-server reuses the KV cache from the previous request for the part at the start that matches, so only the part that differs is processed (`cache_prompt`, on by default). Ollama's API reports `prompt_eval_duration` as the time spent on the uncached prompt tokens. In a session where the agent only adds to the end, each turn mostly reads what was just added. When something near the start of the prompt changes, everything after that point is read again.

To see your own numbers, divide `prompt_eval_count` by `prompt_eval_duration` (in nanoseconds) in Ollama's API response; `load_duration` shows how long loading took. llama-server adds the same timings with `timings_per_token`.

A reply that never comes may be a model that is still loading. OpenClaw's page on local models names a cold start as a common cause of what looks like a hang, and points to two timeouts for slow servers: `models.providers.<id>.timeoutSeconds` for the provider and `agents.defaults.timeoutSeconds` for the run. Ollama unloads a model after five minutes by default; its FAQ explains how `OLLAMA_KEEP_ALIVE` changes that. And if `ollama ps` shows a CPU/GPU split under PROCESSOR, every turn runs at the slower speed of the offloaded rows in the tables.

### Ollama

Set the server-wide context, then restart Ollama. On Windows, quit Ollama from its taskbar icon first, then in PowerShell:

```powershell
$env:OLLAMA_CONTEXT_LENGTH="65536"; ollama serve
```

On macOS or Linux the same line is `OLLAMA_CONTEXT_LENGTH=65536 ollama serve`. For a permanent setting, use the context slider in the Ollama app or an account environment variable, as described in <GuideLink slug="ollama-context-length" />. $env:OLLAMA_CONTEXT_LENGTH="65536"; $env:OLLAMA_FLASH_ATTENTION="1"; $env:OLLAMA_KV_CACHE_TYPE="q8_0"; ollama serve

### llama.cpp (llama-server)

The same line works in PowerShell, macOS and Linux:

```powershell
llama-server -m model.gguf -c 65536 -ctk q8_0 -ctv q8_0 -fa on
```

Set `-c` yourself. Left unset, llama-server starts from the model's own maximum (<Num kind="maxContext" model="qwen3.6-35b-a3b" /> for Qwen3.6 35B-A3B), and when memory runs short its automatic fitting (`--fit`, on by default) lowers the context first, down to a 4k floor set by `--fit-ctx`, before it moves any weights. The agent then gets far less context than it expects. With `-c` set, the context stays as given and `--fit` moves weights to system RAM instead, experts first for MoE models. The startup log shows the context it settled on. Leave out `-ctk` and `-ctv` to keep f16. Chat templates (`--jinja`), which the README names as what OpenAI-style tool calls need, are on by default.

## How sure are these numbers?

The memory figures are calculated by formula from real GGUF file sizes, each file's header and each model's published configuration, so they carry no error band. The speeds are estimates with a band and a confidence label. Calibrated means ±12% for dense models fully on an NVIDIA or AMD card and ±20% for MoE models, partial offload and other hardware. In this guide's three context tables, the cells with experts in system RAM are theoretical, gpt-oss-20b's 8k f16 cell on the RTX 5060 Ti 16GB is measured, and the rest are calibrated. ## FAQ

### How much context does a local coding agent need?

At least 64k tokens, by Ollama's documentation for agents and coding tools. OpenClaw itself normally sends 32k for the Ollama models it discovers, and the Qwen3.6 35B-A3B model card advises 128k or more for its thinking. Choose the longest context that still keeps the whole model on the GPU: at 64k with an f16 KV cache, Qwen3.8 27B needs <Num kind="needGB" model="qwen3.8-27b" ctx="65536" /> and gpt-oss-20b needs <Num kind="needGB" model="gpt-oss-20b" ctx="65536" />. A 24GB card can use <Num kind="usableGB" gpu="rtx-3090" /> and a 16GB card <Num kind="usableGB" gpu="rtx-5060-ti-16gb" />.

### Why does my local agent take so long to start answering, or time out?

Usually because the model is reading a long prompt or still loading. Compare `prompt_eval_duration` and `load_duration` in Ollama's API response, keep the model loaded with `OLLAMA_KEEP_ALIVE`, and raise the agent's timeout (OpenClaw documents `timeoutSeconds` settings). If `ollama ps` shows a CPU/GPU split, lower the context or use a q8_0 KV cache until it reads 100% GPU.

### Does a q8_0 KV cache hurt coding quality?

The Ollama FAQ calls the precision loss of q8_0 very small: it uses about half the memory of f16, while q4_0 uses about a quarter with a small-to-medium loss. CanRun does not measure output quality. A memory-based rule: use q8_0 when f16 does not fit the context you need, and q4_0 only when q8_0 still spills. On a 24GB card, q8_0 is what keeps Qwen3.6 35B-A3B on the GPU at 64k.<Expect model="qwen3.6-35b-a3b" gpu="rtx-3090" ctx="65536" kv="q8_0" fits="true" mode="full-gpu" />

### Why does the agent print tool calls as text instead of running them?

The connection, the context or the model can each cause it. OpenClaw's documentation says that pointing it at Ollama's OpenAI-compatible `/v1` URL breaks tool calling and that models may then write the call as plain text; use the native address instead. OpenCode's documentation suggests raising Ollama's `num_ctx` when tool calls fail. The model has to support tool calls too: the Qwen3.6 35B-A3B and Qwen3 30B-A3B (2507) model cards describe tool calling, and the gpt-oss-20b card lists function calling.

### Can I check a coding model that is not in CanRun's list?

Yes. Paste its Hugging Face id into the calculator, set the context to 64k, and it runs the same memory calculation for your card. Results for loaded models are theoretical estimates (±30%). The calculator cannot tell whether such a model has a thinking mode, so it does not apply the stricter thresholds for thinking models.
