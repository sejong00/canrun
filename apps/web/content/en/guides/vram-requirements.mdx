## How much VRAM a model needs: weights, KV cache and buffer

Three things share a graphics card's memory while a model runs: the model's weights at the quant you downloaded (Q4_K_M, a 4-bit GGUF quant, is the usual default), the KV cache, which holds keys and values for every token in the context, and a compute buffer, the runtime's working memory, which grows slightly with the context.

The weights on the GPU are the model file minus two parts that llama.cpp leaves off the graphics card. It always keeps the input embedding table, which turns tokens into vectors, in system RAM. Some newer models, such as Qwen3.5, also ship a multi-token prediction (MTP) block, which llama.cpp loads only when you turn MTP on. EXAONE 4.5 carries one too, but llama.cpp does not use it yet and never loads it. CanRun reads both sizes from each GGUF file's header; together they come to a few hundred megabytes for most models and around a gigabyte for the Qwen3.5 models. The largest, Qwen3.5 122B, passes two gigabytes even at Q4_K_M. Models that reuse the embedding table as their output layer, such as Gemma 3, keep a copy on the GPU, so for them the weights equal the file.

## MoE models: the whole file counts, but experts can sit in system RAM

In a mixture-of-experts (MoE) model, the bulk of each layer is split into many expert blocks, and a router picks a few for every token. Qwen3 30B-A3B has 128 experts with 8 active per token, according to its model card; <HubLink model="gpt-oss-20b" /> and <HubLink model="gpt-oss-120b" /> work the same way. Fit needs the whole file, because the router can pick any expert; speed depends mostly on the active part.

When the model does not fit fully in VRAM (weights, KV cache and buffer together), CanRun's calculation first keeps the shared and attention weights, the KV cache and the buffer on the GPU. It then fills the remaining VRAM with as many layers of experts as fit, leaving one layer's worth free as a safety margin, and keeps only the experts of the other layers in system RAM. CanRun reads the expert and non-expert sizes from each GGUF file's header. llama.cpp's `--n-cpu-moe N` option makes this split: it keeps the experts of the first N layers on the CPU, and our combo pages print the N that CanRun calculated. <HubLink model="qwen3-30b-a3b-2507" /> needs <Num kind="needGB" model="qwen3-30b-a3b-2507" />, against <Num kind="usableGB" gpu="rtx-3060-12gb" /> usable on the RTX 3060 12GB, so the bar shows the GPU filled and the remaining experts in system RAM:

## How quantization and context length change the answer

On a given card, two settings move a model across the lines above: the quant you download and the context you run it at.

### Quantization: a smaller file, at a cost in quality

## How sure are these numbers?

The memory figures are calculated by formula from real GGUF file sizes, each file's header (for the parts llama.cpp keeps off the graphics card), each model's published configuration and the compute buffer. Where a real file size is missing, CanRun falls back to a weight-size formula, which matched eleven real GGUF files with a mean error of 0.7%. CanRun's KV formulas matched the published values on seven architectures.

The speeds are estimates with a band and a label. Measured means a public benchmark for that card, model and quant. Calibrated means ±12% for dense models fully on an NVIDIA or AMD card and ±20% for MoE models, partial offload and other hardware. Theoretical means ±30%, for setups with few measurements or widely varying real speeds, such as MoE experts in system RAM; there the estimate keeps as many experts on the GPU as fit and only the rest in RAM. Against 12 public measurements, the speed formula has a mean error of 6.3% and a maximum of 17.1%.

In the grid, about half the cells are calibrated and several are measured; the cells with MoE experts in system RAM, including the RAM hints for gpt-oss-120b, are theoretical.

## FAQ

### Is 8GB of VRAM enough to run a local LLM?

Yes, for 8B-class models at Q4_K_M with an 8k context. Llama 3.1 8B needs <Num kind="needGB" model="llama-3.1-8b" /> against the <Num kind="usableGB" gpu="rtx-4060" /> an 8GB card can use, and it Runs great on the RTX 4060,<Expect model="llama-3.1-8b" gpu="rtx-4060" verdict="S" /> with about a gigabyte to spare. At Q4_K_M, the 12B to 14B dense models in the catalog do not fit fully: Qwen3 14B needs <Num kind="needGB" model="qwen3-14b" />, so part of it runs from system RAM and it Runs slowly.<Expect model="qwen3-14b" gpu="rtx-4060" verdict="B" /> Longer context makes it tighter: at 16k with an f16 KV cache, Llama 3.1 8B needs <Num kind="needGB" model="llama-3.1-8b" ctx="16384" />, about the same as what the card can use; in CanRun's calculation it goes slightly over, so part of it moves to system RAM. A q8_0 (8-bit) KV cache or a shorter context keeps it on the GPU.

### How do I work out how much VRAM a model needs?

Start from the GGUF file size at your quant, add the KV cache for your context and a small compute buffer, then compare the total with the VRAM your card can use: the number on the box minus what the OS keeps for the display. At Q4_K_M a file in gigabytes is about three-fifths of the parameter count in billions, at Q8_0 roughly one gigabyte per billion; the real file size is better still. The weights on the GPU are a little smaller than the file, because llama.cpp keeps the input embedding table in system RAM. For Qwen3 14B, <Num kind="gpuWeightsGB" model="qwen3-14b" /> of the <Num kind="fileGB" model="qwen3-14b" /> file goes on the GPU; with <Num kind="kvGB" model="qwen3-14b" /> of KV cache at 8k and the buffer, the total is <Num kind="needGB" model="qwen3-14b" />.

### Does a longer context need more VRAM?

Yes. The KV cache stores every token in the context, so for models with full attention on every layer, doubling the context doubles the cache. How much depends on the architecture: at 32k with an f16 cache it is <Num kind="kvGB" model="llama-3.1-8b" ctx="32768" /> for Llama 3.1 8B but <Num kind="kvGB" model="gpt-oss-20b" ctx="32768" /> for gpt-oss-20b, whose sliding-window layers keep only recent tokens. Mind the runtime default as well: <RuntimeFact id="ollama-default-ctx" />. A q8_0 or q4_0 (8-bit or 4-bit) KV cache shrinks it; see <GuideLink slug="kv-cache-context" />.

### Do MoE models like gpt-oss-20b or Qwen3 30B-A3B need less VRAM than dense models of the same size?

Not to fit. The whole file has to be in memory; the small number of active parameters reduces the work per token, not the file size. gpt-oss-20b needs <Num kind="needGB" model="gpt-oss-20b" /> at 8k, so it fits fully on a 16GB card such as the RTX 5060 Ti 16GB and Runs great there,<Expect model="gpt-oss-20b" gpu="rtx-5060-ti-16gb" verdict="S" /> in line with its model card. What MoE does allow is keeping part of the expert weights in system RAM (llama.cpp's `--n-cpu-moe`, a split that current llama.cpp and Ollama versions also make on their own); CanRun marks that setup's speed as a theoretical estimate.

### Can system RAM make up for too little VRAM?

Partly. Runtimes put whatever does not fit into system RAM, so the model still runs, but slower, and for dense models the drop is steep: Qwen3 14B on an 8GB RTX 4060 Runs slowly.<Expect model="qwen3-14b" gpu="rtx-4060" verdict="B" /> For large MoE models, system RAM itself becomes the limit. The gpt-oss-120b file is <Num kind="fileGB" model="gpt-oss-120b" />, and with 32GB of RAM it is rated Won't run even on the 32GB RTX 5090;<Expect model="gpt-oss-120b" gpu="rtx-5090" verdict="F" /> in CanRun's calculation that card needs 64GB of RAM, and an 8GB card needs 96GB. `ollama ps` or the llama.cpp log shows what your runtime did.
