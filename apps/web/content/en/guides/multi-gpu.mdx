A second graphics card adds memory, not memory bandwidth: a model that already fits on one card gets no faster, but one that spilled into system RAM can get several times faster once it fits. With llama.cpp's default split, two RTX 3060 12GB cards hold about what one 24GB RTX 3090 holds, but each token is generated at roughly one RTX 3060's speed.

## What splitting a model across GPUs does

llama.cpp, which Ollama 0.30 and later also runs on, splits a model across cards by layers unless you tell it otherwise (`--split-mode layer`). Each card holds a contiguous block of layers, and the KV cache (the memory that holds the context) for those layers stays on the same card. To generate a token, the first card runs its layers, then hands a small intermediate result to the next card, which runs the rest. The cards take turns, so for a single chat the time per token is the sum of the times the cards need to read their shares of the weights. Memory adds up across the cards; memory bandwidth, which sets the speed, does not.

In CanRun's calculation, a model that already fits on one card gets the same estimated speed on two identical cards. Public results point the same way. In one 2024 benchmark set, Llama 3 8B at Q4_K_M (a 4-bit quant) generated a few percent slower on two RTX 3090 cards than on one, and a little slower again on four and six. What the extra cards changed was what fit: Llama 3 70B at Q4_K_M ran out of memory on one RTX 3090 and ran on two.

Llama 3.1 8B on an RTX 3060 12GB has a public benchmark. It fits with room to spare and Runs great, measured on real hardware.<Expect model="llama-3.1-8b" gpu="rtx-3060-12gb" verdict="S" mode="full-gpu" confidence="measured" /> For two of these cards, the calculator shows the 8k estimate printed under the measurement, not the measured speed, because public results exist only for single cards. In CanRun's calculation the second card does not raise it.

<Measured model="llama-3.1-8b" gpu="rtx-3060-12gb" />

Prompt processing is the exception. Layer split works on many prompt tokens at once, so the cards can be busy at the same time. In the same 2024 benchmark set, an 8k-token prompt was processed faster at each step from one to six RTX 3090 cards. llama.cpp's multi-GPU guide recommends the layer mode when fast prompt processing matters. CanRun does not estimate prompt speed for several cards (only single-card combo pages show it), so this guide sticks to generation speed. A newer, experimental mode splits every layer across the cards instead; it is covered in the setup section below.

## Mixing different cards

Cards do not have to match. Without other instructions, llama.cpp splits the layers in proportion to each card's free memory. ## What each extra card costs in memory

Adding cards adds VRAM, but not all of it holds the model.

- **A compute buffer per card.** In CanRun's calculation each card holds its own compute buffer, about half a gigabyte at 8k, growing slowly with the context. Two cards pay it twice, four cards four times.
- **The display share, once.** Windows keeps some VRAM on the card that drives your monitor (the note under the memory table gives the amount). With several cards, CanRun takes it from the first card only, which then gets slightly fewer layers in llama.cpp's free-memory split.
- **A margin on every card.** llama.cpp's automatic fitting, on by default since December 2025, keeps some VRAM free on each card (`--fit-target`) and adjusts the settings you leave unset, such as the context size and the number of GPU layers. The margins add up with the number of cards, so a model that only just fits in CanRun's numbers, such as Qwen3 32B on two RTX 3060 12GB cards, may start with a shorter context or with a layer in system RAM. Check the llama.cpp log or `ollama ps`.
- **Whole layers.** llama.cpp gives each layer to one card and puts the output layer on the last card. A card's share is rounded to whole layers, so some VRAM on each card can stay unused. CanRun counts the cards' memory as one pool and does not model this.

Room for context grows with the cards too, because each card keeps the KV cache for its own layers. Qwen3 32B at 32k with an f16 KV cache needs <Num kind="needGB" model="qwen3-32b" ctx="32768" />, more than the <Num kind="usableGB" gpu="rtx-3090" /> one 24GB card can use, and comfortably within two RTX 3090 cards. How the KV cache grows is explained in <GuideLink slug="kv-cache-context" />.

## Setting it up in llama.cpp and Ollama

### llama.cpp

llama.cpp spreads a model across every GPU it can see, so for two cards you usually change nothing. The options below come from llama.cpp's multi-GPU guide. The commands are written for PowerShell on Windows; on Linux, write the model path as `./Qwen3-32B-Q4_K_M.gguf`.

```powershell
llama-server --list-devices
llama-server -m .\Qwen3-32B-Q4_K_M.gguf -c 8192
llama-server -m .\Qwen3-32B-Q4_K_M.gguf -c 8192 -dev CUDA0,CUDA1 -ts 3,1
llama-server -m .\Qwen3-8B-Q4_K_M.gguf -c 8192 -dev CUDA0
```

The first command lists the cards with their names, such as CUDA0 and CUDA1, and their memory. The second uses the default: layers split across all visible cards by free memory. `-c 8192` matches the 8k context CanRun assumes; without it, llama-server starts from the model's full context and its automatic fitting shrinks it. The third command sets a custom split, three parts to the first card and one to the second; `-ts` (`--tensor-split`) takes proportions in the order of `--device`. Use it when the automatic split leaves one card too full, for example the card that drives the display, and give that card the smaller number. With `-ts` set, the automatic fitting no longer moves layers for you. The last command runs on one card only.

For CUDA builds, the environment variable `CUDA_VISIBLE_DEVICES` hides cards from llama.cpp altogether: `$env:CUDA_VISIBLE_DEVICES="0"; llama-server ...` in PowerShell, or `CUDA_VISIBLE_DEVICES=0 llama-server ...` on Linux. `--device` picks among the cards llama.cpp can see and works with every backend.

### Ollama

Ollama decides on its own. According to its FAQ, it loads a model onto one GPU when the model fits on any single GPU, and spreads it across all GPUs only when it does not. Whether a model fits depends on the context Ollama starts with. <RuntimeFact id="ollama-default-ctx" />. To pick that default, Ollama adds up the memory of every card it finds, and its server log records the result on a `vram-based default context` line. Two RTX 3060 12GB cards therefore start at 32k, where one card alone gets 4k. At 32k Qwen3 14B needs <Num kind="needGB" model="qwen3-14b" ctx="32768" />, more than one RTX 3060 12GB can use,<Expect model="qwen3-14b" gpu="rtx-3060-12gb" ctx="32768" fits="true" mode="partial-offload" /> so by the FAQ's rule Ollama spreads it across both cards. An RTX 3090 with an RTX 3060 12GB also starts at 32k, where Qwen3 32B needs <Num kind="needGB" model="qwen3-32b" ctx="32768" />, more than the RTX 3090 alone holds.<Expect model="qwen3-32b" gpu="rtx-3090" ctx="32768" fits="true" mode="partial-offload" /> To match CanRun's 8k basis, set `OLLAMA_CONTEXT_LENGTH` as below; other ways to set the context are in <GuideLink slug="ollama-context-length" />.

The environment variable `OLLAMA_SCHED_SPREAD` makes Ollama always spread across all GPUs. To limit Ollama to certain NVIDIA cards, set `CUDA_VISIBLE_DEVICES`; Ollama's GPU documentation recommends the card UUIDs that `nvidia-smi -L` prints, because numeric order can vary. AMD cards use `ROCR_VISIBLE_DEVICES` instead.

```powershell

```

Quit Ollama from its taskbar icon before running the second line; the settings apply only to the server started from that PowerShell window. For a lasting setting on Windows, add the variables under "Edit environment variables for your account" and restart Ollama from the Start menu. After loading a model, `ollama ps` shows whether it sits fully on the GPUs (PROCESSOR reads 100% GPU), and `nvidia-smi` shows how much memory each card uses.

### Tensor split: faster generation, experimental

Since April 2026, llama.cpp has an experimental `--split-mode tensor` that splits each layer across the cards, so they work on the same token together. In the tests in the pull request that added it, run on two RTX 4090 cards, dense models generated faster than with layer split, while some MoE models generated slower and prompt processing was often slower. It needs flash attention and an unquantized KV cache, does not work with automatic fitting or every model architecture, and depends far more on the link between the cards. For good speed it also needs NVIDIA's NCCL library, which llama.cpp's guide says is not shipped with CUDA and may need installing separately; NVIDIA provides it for Linux. llama.cpp's guide says its performance should be good for NVIDIA cards with CUDA, with no guarantees for other setups. CanRun does not model this mode; all estimates here assume layer split. The older `--split-mode row`, which older guides mention, was removed from the CUDA backend in July 2026.

## How sure are these numbers?

Multi-GPU results are a beta shown only in the calculator. GPU pages, model pages, the combo pages and the grid above all assume one graphics card. Multi-card results are never matched to public benchmarks, so their speeds are labeled theoretical (±30%), and the verdicts this guide gives for pairs come from the calculator, not from the grid.

For identical cards, CanRun checked its formula against ten public results with two to four cards: nine NVIDIA setups and one pair of AMD RX 7900 XTX cards. Every measured speed was equal to or faster than CanRun's estimate, by up to 28% (CanRun's estimate was at most 22% low). All ten used dense models at short context. None used an MoE model or kept experts in system RAM, so the MoE pair results above (Qwen3 30B-A3B, gpt-oss-120b) have no public check, and with experts in RAM CanRun may place too many experts on the GPUs. For mixed cards there are three checks. The only one with cards from the catalog, an RTX 5070 Ti with an RTX 3060 12GB, measured about 7% above the estimate. The other two used an older datacenter card and checked only the split formula. CanRun has no checks for MoE models on mixed cards, for mixed AMD cards or for more than two mixed cards.

The memory figures (weights on the GPU, KV cache, compute buffer per card, display share) are calculated by formula from real GGUF files, as on every CanRun page. What the formula leaves out is listed in the memory section above: the fitting margin on each card, whole-layer rounding and the output layer on the last card. Results assume Windows with the first card driving the display, 32GB of DDR5 system RAM, an 8k context, an f16 KV cache, one request at a time and llama.cpp's default layer split. Verdicts for single cards assume that setup. Models with a thinking mode, such as Qwen3 32B, face speed thresholds 1.5× higher than the legend shows.

## FAQ

### Does a second GPU make a model generate faster?

Not if the model already fits on one card. With llama.cpp's default layer split the cards take turns on each token, so two identical cards generate at about one card's speed. With the default split, a second card speeds things up only when it keeps a model out of system RAM: Gemma 3 27B on one RTX 3060 12GB Runs slowly,<Expect model="gemma-3-27b" gpu="rtx-3060-12gb" verdict="B" mode="partial-offload" /> and two of those cards hold it entirely in VRAM.

### Are two 12GB cards the same as one 24GB card?

For memory, almost: both have 24GB and lose the same display share, but the pair holds one more compute buffer, so it has about half a gigabyte less for the model at 8k. For speed, no: the pair generates at about the speed of one 12GB card. Against an RTX 3090, two RTX 3060 12GB cards read memory about two and a half times slower, and the estimates follow that.

### Do the cards need NVLink or a fast PCIe slot?

Not for llama.cpp's default layer split. Only a small intermediate result moves between the cards for each token, and llama.cpp's multi-GPU guide says this mode can tolerate slow links between GPUs. The experimental tensor split is much more sensitive, and the same guide suggests more PCIe lanes or NVLink when several cards run slower than one.

### Can I mix NVIDIA and AMD cards?

Only with a different setup, and CanRun does not estimate it. NVIDIA cards run through CUDA and AMD cards through ROCm, so one llama.cpp process needs a backend that drives both. The simplest route is llama.cpp's prebuilt Vulkan release for Windows (`win-vulkan-x64`), which sees both cards. llama.cpp's build guide also notes that you can build several backends together and choose devices with `--device`. CanRun's calculator only mixes cards from the same maker, because too few public results exist to estimate the other setups.
