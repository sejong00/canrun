CanRun changes often. New models arrive, the calculator gains features, and now and then we find part of the calculation was wrong and fix it. This page lists the changes you would notice, newest first, followed by the date each model joined the catalog. How the calculation works today is explained on <SiteLink to="/methodology">How we calculate</SiteLink>.

## Changes to the site

<Update id="dgx-spark-cluster">

### DGX Spark: two and four linked units

The <SiteLink to="/gpu/nvidia-dgx-spark">DGX Spark</SiteLink> page and each model's DGX Spark page now also show verdicts for two and four units linked over ConnectX-7, and the calculator lets you pick one to four units and shows the llama.cpp command to start on each one. These verdicts are worked out for llama.cpp RPC, which splits the layers across the units: memory adds up, but each token still passes through every unit, so the speed stays close to one unit's and drops by a little for every hop, a cost measured on two units linked over TCP. They are theoretical estimates, and vLLM tensor parallelism, which NVIDIA's own guides use, can be faster. That day at an 8k context, gpt-oss-120b, which does not load on one 64GB unit, came out as Runs great on two of them, and GLM-5.3-Flash at Q4_K_M, too big for one 128GB unit, as Runs well on two.

</Update>

<Update id="dgx-spark-64gb">

### DGX Spark: a 64GB configuration, partner models and the memory its GPU can use

The <SiteLink to="/gpu/nvidia-dgx-spark">DGX Spark</SiteLink> is now calculated in two configurations, 64GB and 128GB, and typing a partner maker's name for the same GB10 machine, such as the ASUS Ascent GX10 or the Lenovo ThinkStation PGX, now finds it in the calculator search. Instead of the 70% CanRun counts for Macs and the Strix Halo, its GPU share is now what Linux and the desktop leave free, starting from the lowest figure in owners' public boot logs, and the same limit applies when a model falls back to the CPU. That day at an 8k context, the Q2_K file of Solar Open 2 250B on the 128GB model moved from Runs slowly on the CPU to Runs well on the GPU, while the Q2_K file of DeepSeek V4 Flash 0731 went from Runs slowly on the CPU to not fitting at all. On the 64GB model, Llama 3.3 70B at Q4_K_M was calculated to fit fully on the GPU at an 8k context. Where the 64GB configuration gets the same verdict as the 128GB one, the model pages and each model's DGX Spark page now use 64GB.

</Update>

<Update id="sparse-linear-hybrid">

### A hybrid of sparse and linear attention is now calculated

CanRun now calculates <SiteLink to="/model/glm-5.3-flash">GLM-5.3 Flash</SiteLink>, which mixes linear-attention layers with sparse-attention layers. CanRun counts KV cache only for the sparse ones, so a long context adds little memory; that day at an 8k context its Q4_K_M file was calculated to fit fully on the GPU of an M3 Ultra with 512GB, and with 256GB only the Q2_K file fit on the GPU. Its GGUF files call the Q4_K_M quantization Q4_K, a short name the llama.cpp quantizer accepts for the same format, so a file without Q4_K_M in its name is read as the Q4_K_M row after its header confirms the format, and the commands use the tag written in the file name. The llama.cpp commands for this model add `-np 1`, because llama.cpp sets aside memory for the model's sparse-attention indexer in proportion to the number of request slots, so the four slots llama-server opens by default would need more memory than the estimate counts. The speed formula does not count the extra work this model does in every layer, and public results from recent llama.cpp builds were all slower than the estimate, so every combination for it carries the theoretical label and its rating is based on a speed about 8% below the estimate shown.

</Update>

<Update id="compressed-attention">

### Models with compressed attention are now calculated

CanRun now calculates <SiteLink to="/model/deepseek-v4-flash-0731">DeepSeek V4 Flash 0731</SiteLink>, whose layers keep their KV cache in compressed blocks of several tokens each, and its model page lists the attention type as compressed. The cache is counted the way llama.cpp allocates it for one request slot, so a long context adds little memory on top of the weights; that day its MXFP4 file was calculated to fit fully on the GPU of an M3 Ultra with 256GB at an 8k context. llama.cpp keeps a separate cache for every slot, so the llama.cpp commands for this model add `-np 1` in place of the four slots llama-server opens by default. GGUF repositories without a Q4_K_M file now use MXFP4 as the baseline, for this model and when the calculator loads a model from Hugging Face. The speed formula does not count the extra work this model does in every layer, and the one public result from a current llama.cpp build was slower than the estimate, so every combination for it carries the theoretical label.

</Update>

<Update id="looped-layers">

### Models that run their layers more than once are now calculated

CanRun now calculates <SiteLink to="/model/nanbeige4.2-3b">Nanbeige4.2 3B</SiteLink>, whose 22 layers run twice for every token on the same weights. llama.cpp keeps a separate KV cache for each pass, so at long contexts this small model needs as much memory for that cache as a much larger one; that cache is why Q4_K_M with a 32k context on an 8GB RTX 4060 was calculated as partial offload. llama.cpp also counts each pass as its own layer, so when part of the model stays on the CPU, the `-ngl` value in its command is higher than its layer count. The speed estimate reads the repeated layers twice for every token. Only one public measurement backs it, so every combination for this model carries the theoretical label.

</Update>

<Update id="k2-horizon-mova">

### K2-Horizon and its Mixture-of-Values attention are now calculated

Now that llama.cpp supports K2-Horizon, CanRun calculates <SiteLink to="/model/k2-horizon-7b">K2-Horizon 7B</SiteLink> and <SiteLink to="/model/k2-horizon-mova-36b-a4b">K2-Horizon MoVA 36B-A4B</SiteLink>. In its MoE layers, all but the first three, the MoVA model builds the attention values from a few of many value experts, and llama.cpp keeps those value experts on the graphics card even when it moves the MoE experts to system RAM. CanRun places them the same way, so when we checked, Q4_K_M with an 8k context did not fit an 8GB RTX 4060 even with the experts in RAM and was calculated as CPU only, while a 16GB RTX 5060 Ti came out as Runs well with the experts in RAM. When the model runs on the graphics card, the speed estimate counts only the value experts each token picks, but there are no public benchmarks yet and the small cost of picking them is not counted, so every combination for this model carries the theoretical label.

</Update>

<Update id="gemma4-e-series">

### Gemma 4 E2B and E4B are now calculated

Gemma 4's two edge models give each layer its own embedding table, and many of their layers reuse the KV cache of earlier layers, so CanRun had left them out. It now reads the size of that per-layer table from each GGUF file's header, keeps the table in system RAM instead of on the graphics card as llama.cpp does, and counts KV cache only for the layers that store their own. When we checked, <SiteLink to="/model/gemma-4-e4b">Gemma 4 E4B</SiteLink>, which `ollama run gemma4` downloads, and <SiteLink to="/model/gemma-4-e2b">Gemma 4 E2B</SiteLink> both fit fully at Q4_K_M on an 8GB RTX 4060 with an 8k context. Their speed estimates add a small fixed delay per token that public benchmarks showed, and they carry the theoretical label except where a benchmark matches, as on the RTX 5090. <SiteLink to="/guides/gemma-4-models">The Gemma 4 guide</SiteLink> now covers both.

</Update>

<Update id="prompt-speed-model-size">

### Prompt speed estimates now depend on the model

The prompt-processing estimate on combo pages was one figure per graphics card, fitted to a 7B model, so a 1B model and a 70B model showed the same prompt speed on the same card. It is now divided by the model's size, and mixture-of-experts (MoE) models count as more than their active parameters, because each expert gets only a slice of every batch of prompt tokens. We fitted it to 91 public benchmarks from recent llama.cpp builds and refitted the NVIDIA, AMD and Strix Halo factors with it; Radeon cards now use AMD's FP16 matrix figure, which is twice the usual FP16 figure on the RX 9000 series. On an <SiteLink to="/gpu/rtx-4090">RTX 4090</SiteLink>, Qwen3 32B now shows a little under a quarter of the old figure and Llama 3.2 1B about five times as much, and the <SiteLink to="/gpu/nvidia-dgx-spark">DGX Spark</SiteLink> now gets a prompt estimate too. Generation speeds and verdicts did not change.

</Update>

<Update id="strix-halo-speed">

### Faster estimates for the Strix Halo

Our efficiency factor for the <SiteLink to="/gpu/amd-strix-halo">Ryzen AI Max+ 395 (Strix Halo)</SiteLink> was an older value without a clear source, and it ran low for dense models on current llama.cpp builds. We refitted it to public Vulkan results from current builds, and refitted the fixed per-expert cost for MoE models with it. Dense models now come out about a quarter faster, and 8B models such as Qwen3 8B moved from Runs well to Runs great. MoE estimates moved both ways, by up to about a fifth: gpt-oss-20b rose, and Qwen3 30B-A3B fell a little. The factors follow the Vulkan backend; in public comparisons on the same machine, ROCm ran about 3% to 12% slower.

</Update>

<Update id="moe-fixed-cost">

### More accurate speeds for MoE models

Our speed estimate for mixture-of-experts (MoE) models used a separate efficiency factor for each class of hardware and a rough count of the bytes each token reads, which left out most of the shared layers. We now count those bytes from each file's header and add a fixed cost that each token pays for every expert it runs in every layer, fitted to public benchmarks from recent llama.cpp builds. Small MoE models on top-end NVIDIA cards are no longer held under a fixed ceiling, and large MoE models on Macs came out faster than before. At Q4_K_M, gpt-oss-20b on a 24GB <SiteLink to="/gpu/apple-m4">Apple M4</SiteLink> moved from Runs well to Runs great. A few 8GB-card combinations that keep MoE experts in system RAM moved from Runs slowly to Runs well.

</Update>

<Update id="apple-gpu-compute">

### Corrected compute figures for Apple chips

Apple does not publish its chips' GPU compute, and the figures we showed were double the theoretical FP32 compute, on the assumption that the GPU runs FP16 at twice that speed. Apple GPUs run FP16 at the same rate as FP32, so GPU and model pages now show the theoretical figures from Wikipedia's Apple silicon table as they are, about half the old ones. The prompt-processing factors were refitted to the same public benchmark with these figures, so prompt estimates moved by 7% or less, and the <SiteLink to="/gpu/apple-m5-ultra">Apple M5 Ultra</SiteLink>, which had no figure, now gets a prompt-processing estimate too. Generation speeds and verdicts did not change.

</Update>

<Update id="apple-prompt-speed">

### Prompt speed estimates for Macs

We had estimated prompt processing on every Apple chip with one factor per unit of GPU compute. M5-series chips have a matrix accelerator in each GPU core, and in llama.cpp's public Apple benchmark they read prompts about three times as fast for their compute as earlier chips, so one factor ran too low for the M5 series and too high for the rest. M5-series chips now get their own factor, which raised their prompt estimates by about 70%; for M4-series and Ultra chips the estimates fell by about 40%. On an <SiteLink to="/gpu/apple-m5-max-40c">Apple M5 Max (40-core GPU)</SiteLink> the estimate is now close to that benchmark's result. Generation speeds and verdicts did not change.

</Update>

<Update id="mixed-gpus">

### Mix different graphics cards

"Add a different GPU" combines desktop cards from the same maker, up to four in total, such as an RTX 3090 with an RTX 3060 12GB. Memory adds up across the cards, but each token passes through them one after another, so the slower card holds the whole run back. If the model would fit on the faster card alone, the result tells you. Results for mixed cards are always labeled theoretical (±30%).

</Update>

<Update id="manual-model">

### Calculate a model from its numbers

For a model you can't load from Hugging Face, you can type the numbers from its model card or config.json: total parameters, layers, KV heads and head dimension, plus active parameters and expert counts for MoE models. The file size is estimated from the parameter count, so these results are labeled theoretical. The calculation stays in your browser, and nothing is requested from Hugging Face.

</Update>

<Update id="combo-ram">

### System RAM on model-and-GPU pages

When a model doesn't fit entirely on the graphics card, the verdict depends on how much system RAM you have. Those pages now list the verdict for 16GB to 128GB of RAM. Pick an amount and the verdict sentence and the llama.cpp and Ollama commands change to match. Pages where RAM makes no difference say so instead. If you come from the calculator, the page keeps the RAM you chose there.

</Update>

<Update id="gpu-weights">

### Graphics card memory counts only what goes on the card

llama.cpp keeps a model's input embedding table in system RAM. It also leaves out the multi-token prediction (MTP) block some newer models carry unless you turn MTP on. We used to count both against graphics card memory; now we read their sizes from each GGUF file's header and leave them out. Some models now fit on the card with longer contexts, and a few verdicts went up: HyperCLOVA X SEED Think 14B on the GeForce RTX 2080 Ti, for example, moved from Runs well to Runs great. On a Mac, the whole file still counts.

</Update>

<Update id="hybrid-models">

### Models with Mamba and other hybrid layers

Some newer models mix ordinary attention layers with Mamba2, short convolution or KDA layers. Those layers keep a small state of fixed size instead of a KV cache that grows with the context. The calculation now handles them, for models in our list and for models loaded from a Hugging Face link. Nemotron 3.5 Lightning 30B-A3B, LFM2.5 2.6B and the two Ling-3.0 models joined the catalog the same day.

</Update>

<Update id="thinking-mode">

### Stricter speed thresholds for every model with a thinking mode

A model that thinks before it answers makes you wait for many more tokens, so its speed thresholds are 1.5 times higher. This used to apply only to models we had tagged as reasoning models. Now it follows each model's official card and chat template: every model with a thinking mode gets the higher thresholds, including models where you can switch thinking off, while models without one, such as Phi-4, keep the normal thresholds. Some verdicts dropped a level as a result: Qwen3 14B on the GeForce RTX 3060 12GB, for example, went from Runs great to Runs well.

</Update>

<Update id="krw-prices">

### Won prices on the Korean pages

On the Korean GPU, model and model-and-GPU pages and in the Korean calculator, US dollar prices now come with an amount in Korean won. It is a plain conversion at the European Central Bank reference rate, updated weekly, so it can differ from what a card actually costs in Korea. Guides and the English pages show dollars only.

</Update>

<Update id="multi-gpu">

### Two to four of the same GPU

A "Number of GPUs" setting in the calculator covers two to four identical cards, and memory adds up across them. With llama.cpp's default layer split the cards take turns on each token, so our calculation doesn't make generation faster. When the setting arrived, our calculation at 8k context fit Llama 3.3 70B at Q4_K_M entirely on two GeForce RTX 3090 cards, while at 16k part of it spilled into system RAM. Multi-card results aren't matched to public benchmarks, so they are labeled theoretical (±30%). GPU, model and model-and-GPU pages still assume one card.

</Update>

<Update id="hf-models">

### Models that aren't in our list

Paste a Hugging Face model link or id, such as Qwen/Qwen3-4B, under "A model that isn't listed", and the calculator runs the same calculation for it. Your browser reads the model's configuration and file list from Hugging Face directly. For some models, MoE models among them, it also reads the start of a GGUF file to measure its parts. If the model is already in our list, you are pointed to its card instead. Loaded models are labeled theoretical (±30%).

</Update>

<Update id="moe-expert-placement">

### MoE models: experts on the GPU when there is room

When a mixture-of-experts (MoE) model is too big for the graphics card, llama.cpp can keep its expert weights in system RAM. We now put as many experts on the GPU as fit and only the rest in RAM, the same direction current llama.cpp and Ollama take on their own. The `--n-cpu-moe` value in our commands follows the same split, using expert sizes read from each GGUF file's header. gpt-oss-20b on 8GB to 12GB cards such as the GeForce RTX 4060, for example, moved from Runs slowly to Runs well. These results are still labeled theoretical (±30%).

</Update>

<Update id="moe-speed">

### MoE speed estimates corrected

For MoE models with their experts in system RAM, our speed estimates had been about two and a half times too low. The old formula read the shared weights at system RAM speed as well. Now only the experts each token is routed to are read from RAM, and the new estimate was checked against public benchmarks. Common setups such as Qwen3 30B-A3B on 8GB to 16GB cards moved from Runs slowly to Runs well.

</Update>

<Update id="gemma4-kv">

### Gemma 4 KV cache sizes corrected

We had been sizing the KV cache of Gemma 4 12B four times too large, and that of Gemma 4 26B-A4B twice too large. In these models the layers that attend to the whole context have their own KV head count and head size in the configuration file, and we had used the values of the sliding-window layers instead. With the right values their KV cache shrank to a quarter and a half of the old size, so both models need less memory at long contexts.

</Update>

- Every day, we look for new models, as described above.
- The exchange rate behind the won amounts on the Korean pages is updated weekly.
- Every page shows its data date at the bottom. It is currently <DataUpdated />.
