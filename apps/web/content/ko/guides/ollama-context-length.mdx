<RuntimeFact id="ollama-default-ctx" />. 그래서 8GB·12GB·16GB 카드는 4k로 시작하고, 대화가 이 길이를 넘으면 Ollama는 가장 오래된 메시지부터 아무 표시 없이 버립니다. 24GB·32GB 카드는 32k로 시작합니다. 24GB 카드에서 dense 모델인 Qwen3 32B Q4_K_M은 8k라면 <Num kind="needGB" model="qwen3-32b" ctx="8192" />로 사용 가능 메모리 <Num kind="usableGB" gpu="rtx-3090" /> 안에 들어가지만<Expect model="qwen3-32b" gpu="rtx-3090" verdict="S" />, f16 KV 32k에서는 <Num kind="needGB" model="qwen3-32b" ctx="32768" />가 필요해 넘친 부분이 시스템 RAM으로 가고, 그래서 느려집니다. 해결책은 `OLLAMA_CONTEXT_LENGTH`나 `num_ctx`로 VRAM에 들어가는 가장 긴 컨텍스트 길이를 지정하고 `ollama ps`로 확인하는 것입니다.

## Ollama 기본 컨텍스트는 GPU 메모리로 정해진다

컨텍스트 길이를 따로 지정하지 않으면 한 가지 값으로 고정되지 않습니다. Ollama 컨텍스트 길이 문서 기준으로 <RuntimeFact id="ollama-default-ctx" />. CanRun 카탈로그로 보면 <HubLink gpu="rtx-4060" />(8GB), RTX 3060 12GB, <HubLink gpu="rtx-5060-ti-16gb" />는 4k 구간이고, <HubLink gpu="rtx-3090" />·RTX 4090(24GB)과 <HubLink gpu="rtx-5090" />(32GB)은 32k 구간입니다. 카탈로그에서 가장 큰 그래픽카드가 32GB라, 한 장으로 256k 구간에 드는 카드는 없습니다.

4k는 모델이 감당하는 길이보다 한참 짧습니다. Llama 3.1 8B는 최대 <Num kind="maxContext" model="llama-3.1-8b" />, <HubLink model="qwen3-14b" />는 <Num kind="maxContext" model="qwen3-14b" />까지 지원합니다(Qwen3는 모델 카드 기준 네이티브 32k, YaRN 적용 시 128k).

### 컨텍스트를 넘으면 오래된 메시지부터 빠진다

대화가 컨텍스트 길이보다 길어져도 Ollama는 오류를 내지 않습니다. 채팅 요청은 기본으로 가장 오래된 메시지부터 버리되 시스템 메시지와 마지막 메시지는 남기고(`server/prompt.go`, 요청에서 `truncate`를 지정하지 않으면 켜짐), 생성 도중 컨텍스트가 가득 차면 앞쪽 토큰 일부를 버리고 계속 씁니다(`shift`, 역시 기본으로 켜짐). 메시지를 잘라 냈다는 사실은 디버그 수준 로그에만 기록됩니다. 그래서 초반에 준 지시나 붙여 넣은 문서의 앞부분이 조용히 빠지고, 모델이 앞 내용을 잊은 것처럼 보입니다.

생각(thinking) 모드 모델은 컨텍스트가 더 빨리 찹니다. Qwen3 모델 카드는 대부분의 질문에 출력 길이 32k 토큰을 권하는데, 4k 컨텍스트로는 한참 모자랍니다.

오래된 글이나 일부 참조 문서가 적어 둔 단일 기본값(Modelfile 파라미터 표의 `2048`, FAQ의 `4096`)은 지금 규칙이 아닙니다. 실제로 잡힌 값은 `ollama ps`로 봅니다. CONTEXT 열이 쓰는 컨텍스트 길이, PROCESSOR 열이 GPU와 CPU에 나눠 올린 비율입니다.

## 컨텍스트를 늘리면 메모리가 얼마나 더 드나

필요 메모리는 기본 양자화의 모델 파일, KV 캐시, 연산 버퍼를 더한 값입니다. 파일 크기는 컨텍스트와 상관없이 그대로이고, 전체 어텐션(full attention) 모델이면 KV 캐시가 컨텍스트 길이에 비례해 커집니다.

### 해결 2: KV 캐시 양자화

## Ollama 컨텍스트 늘리는 방법

Ollama 문서에 나온 설정 방법은 다섯 가지입니다.

- **Ollama 앱**: 설정(Settings)의 컨텍스트 길이 슬라이더를 옮깁니다.
- **서버 전체 기본값**: 환경 변수 `OLLAMA_CONTEXT_LENGTH`를 씁니다. 예: `OLLAMA_CONTEXT_LENGTH=16384 ollama serve`(macOS·Linux 터미널 기준, Windows는 아래 절 참고)
- **`ollama run` 대화 중**: `/set parameter num_ctx 16384`를 입력합니다.
- **API 요청마다**: 요청 본문 `options`에 `num_ctx`를 넣습니다(아래 `/api/chat` 예시).
- **모델마다**: Modelfile에 `PARAMETER num_ctx 16384`를 적고 `ollama create`로 모델을 새로 만듭니다.

```json
{
  "model": "llama3.1:8b",
  "messages": [{ "role": "user", "content": "이 문서를 요약해 줘" }],
  "options": { "num_ctx": 16384 }
}
```

`OLLAMA_CONTEXT_LENGTH`는 자동으로 고르는 기본값만 바꿉니다. Modelfile이나 요청에 `num_ctx`가 있으면 그쪽이 우선합니다(환경 변수 도움말, `server/routes.go`의 옵션 적용 순서). 환경 변수를 바꿨는데 `ollama ps`의 CONTEXT가 그대로라면, 먼저 Ollama를 완전히 종료했다가 다시 실행했는지 확인하고, 그다음 Modelfile이나 요청을 보내는 프로그램이 `num_ctx`를 따로 지정하는지 봅니다.

### Windows에서 환경 변수 설정하기

1. 알림 영역(트레이)의 Ollama 아이콘에서 앱을 종료합니다.
2. 설정 앱이나 시작 메뉴에서 ‘환경 변수’를 검색해 ‘계정의 환경 변수 편집’을 엽니다. 사용자 변수 아래 ‘새로 만들기’를 눌러 변수 이름에 `OLLAMA_CONTEXT_LENGTH`, 변수 값에 `16384`처럼 원하는 길이를 넣고 ‘확인’을 누릅니다.
3. 시작 메뉴에서 Ollama를 다시 실행합니다.

잠깐 시험만 하려면 앱을 끈 뒤 PowerShell에서 `$env:OLLAMA_CONTEXT_LENGTH="16384"; ollama serve`를 실행합니다. 그 PowerShell 창에서 띄운 서버에만 적용되며, 조합 페이지가 보여 주는 명령도 이 형태입니다. macOS 앱은 `launchctl setenv OLLAMA_CONTEXT_LENGTH 16384`를 실행하고 앱을 다시 시작합니다. Linux systemd는 `systemctl edit ollama.service`로 `[Service]` 아래에 `Environment="OLLAMA_CONTEXT_LENGTH=16384"`를 넣은 뒤 `systemctl daemon-reload`, `systemctl restart ollama`를 실행합니다.

## 이 숫자는 얼마나 확실한가

메모리 수치(파일 + KV 캐시 + 연산 버퍼)는 실제 GGUF 파일 크기와 모델 config에서 공식으로 계산한 값이라 오차 범위를 붙이지 않고, 속도는 오차 범위와 신뢰 라벨을 붙인 추정치입니다. 보정된 추정은 NVIDIA·AMD 그래픽카드에서 dense 모델을 GPU에만 올릴 때 ±12%, 부분 오프로드·MoE·그 밖의 하드웨어에서 ±20%이고, 이론 추정은 ±30%입니다. 이 글의 두 컨텍스트 표는 NVIDIA 카드의 dense 모델이라 모두 보정된 추정이며, RTX 4060에서 Llama 3.1 8B의 8k·f16 칸만 실측입니다.

<Measured model="llama-3.1-8b" gpu="rtx-4060" />

이 실측은 LocalScore가 4k 컨텍스트에서 잰 공개 측정 한 건으로, Ollama로 잰 값이 아닙니다. 우리 8k 추정 범위와 나란히 보여 줍니다. 이 카드에서 다른 모델의 결과는 <HubLink gpu="rtx-4060" /> 페이지에 모아 두었습니다.

Ollama는 자체 메모리 추정으로 GPU/CPU 분할을 정하므로 `ollama ps`의 SIZE나 분할이 우리 수치와 정확히 같지는 않습니다. 내 PC에서의 기준은 `ollama ps`의 PROCESSOR와 CONTEXT 열입니다.

표는 Windows에서 그 카드로 화면을 출력하고(OS가 VRAM 일부를 예약), 시스템 RAM 32GB(DDR5)에 모델 하나, 요청 슬롯 하나(Ollama FAQ상 `OLLAMA_NUM_PARALLEL` 기본값 `1`)를 쓰며, KV 캐시 양자화에 필요한 플래시 어텐션을 쓸 수 있다고 가정합니다. 문장 속 판정은 모두 8k 컨텍스트·f16 KV 기준이고, 컨텍스트별 결과는 표에서 읽습니다.

## 자주 묻는 질문

### Ollama가 긴 대화에서 앞 내용을 잊는 이유는 무엇인가요?

컨텍스트가 가득 찼기 때문입니다. <RuntimeFact id="ollama-default-ctx" />. 컨텍스트가 차면 Ollama는 기본으로 가장 오래된 메시지부터 버리고(시스템 프롬프트와 마지막 메시지는 유지) 오류도 띄우지 않습니다(Ollama 소스 `server/prompt.go`). 메모리가 허락하는 만큼 `OLLAMA_CONTEXT_LENGTH`, 앱 슬라이더, `num_ctx`로 늘리고 `ollama ps`의 CONTEXT 열로 확인합니다.

### 컨텍스트를 늘리면 Ollama가 느려지나요?

크게 느려지는 것은 늘어난 KV 캐시가 VRAM을 넘어 Ollama가 모델 일부를 시스템 RAM에 둘 때이고, 이때 `ollama ps`에 `100% GPU` 대신 CPU/GPU 비율이 나옵니다. 예를 들어 Qwen3 32B Q4_K_M은 f16 KV 32k에서 <Num kind="needGB" model="qwen3-32b" ctx="32768" />가 필요한데, 32k가 이미 기본값인 24GB 카드의 사용 가능 메모리는 <Num kind="usableGB" gpu="rtx-3090" />입니다. GPU 안에 머무는 동안에는 추정 속도가 조금씩만 내려갑니다(위 표의 행 참고).

### 32k 컨텍스트에는 메모리가 얼마나 더 드나요?

모델이 토큰마다 저장하는 KV 캐시 크기에 달렸습니다. f16 KV 32k에서 Llama 3.1 8B는 <Num kind="kvGB" model="llama-3.1-8b" ctx="32768" />, Qwen3 32B는 <Num kind="kvGB" model="qwen3-32b" ctx="32768" />를 더 쓰지만, 슬라이딩 윈도 층이 있는 gpt-oss-20b는 <Num kind="kvGB" model="gpt-oss-20b" ctx="32768" />뿐입니다. 전체 필요량(파일 + KV 캐시 + 연산 버퍼)은 위 32k 메모리 표에서 사용 가능 메모리와 비교합니다.

### Ollama에서 q8_0이나 q4_0 KV 캐시를 켜야 하나요?

`OLLAMA_KV_CACHE_TYPE`은 서버 전체에 거는 설정이라 모든 모델에 적용되고, 플래시 어텐션이 켜져 있어야 합니다. Ollama FAQ에 따르면 q8_0은 KV 캐시를 대략 절반으로 줄이면서 정밀도 손실이 아주 작고, q4_0은 더 줄이는 대신 손실이 작거나 중간 정도이며 컨텍스트가 길수록 더 두드러질 수 있습니다(우리 표에서는 f16의 약 54%·29%). 들어가느냐 넘치느냐를 가르기도 합니다. Qwen3 32B는 32k·q4_0에서 <Num kind="needGB" model="qwen3-32b" ctx="32768" kv="q4_0" />로, RTX 3090의 사용 가능 메모리 바로 아래입니다.

### 다른 글에는 Ollama 기본값이 `2048`이나 `4096`이라고 나오던데요?

예전 버전의 Ollama와 일부 참조 문서가 한 가지 값을 적어 두었기 때문입니다(Modelfile 파라미터 표의 `2048`, FAQ의 `4096`). 현재 컨텍스트 길이 문서의 설명은 다음과 같습니다. <RuntimeFact id="ollama-default-ctx" />. 내 PC에 실제로 잡힌 값은 `ollama ps`로 확인합니다.
