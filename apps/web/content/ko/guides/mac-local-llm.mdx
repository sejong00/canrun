## 통합 메모리 중 GPU가 쓸 수 있는 몫

맥에는 따로 붙은 VRAM이 없고, CPU와 GPU가 통합 메모리를 나눠 씁니다. CanRun은 그중 약 70%를 GPU가 쓸 수 있는 양으로, 나머지를 macOS와 다른 앱 몫으로 계산합니다. 애플 Metal 문서는 GPU가 쓸 수 있는 메모리 한도(`recommendedMaxWorkingSetSize`)를 ‘GPU가 성능에 영향 없이 할당할 수 있는 메모리의 근삿값’이라고 설명하고, CanRun의 70%는 이 한도를 한 비율로 어림한 값입니다. 용량별 GB는 이 절 끝 표의 ‘GPU 사용 가능량’ 열에 있습니다.

컨텍스트 길이에 따라 늘어나는 메모리는 모델마다 다릅니다. f16 KV 32k에서 Llama 3.1 8B의 KV 캐시는 <Num kind="kvGB" model="llama-3.1-8b" ctx="32768" />인데, gpt-oss-20b는 슬라이딩 윈도 층의 KV가 일정 길이 이상 늘지 않아 <Num kind="kvGB" model="gpt-oss-20b" ctx="32768" />입니다. 원리는 ‘<GuideLink slug="kv-cache-context" />’에 있습니다.

메모리가 모자라면 KV 캐시를 양자화하는 방법도 있습니다. <RuntimeFact id="ollama-kv-cache-type" />. 맥의 Ollama 앱이라면 `launchctl setenv OLLAMA_FLASH_ATTENTION 1`과 `launchctl setenv OLLAMA_KV_CACHE_TYPE q8_0`을 실행한 뒤 앱을 다시 시작합니다. CanRun은 q8_0·q4_0 KV 캐시를 f16의 약 54%·29%로 계산하며, 조합 페이지에서 q8_0 칸을 고르면 llama.cpp 명령의 `-fa on` 뒤에 `--cache-type-k q8_0 --cache-type-v q8_0`이 붙습니다.

맥에서 컨텍스트 길이를 바꾸는 방법은 다음과 같습니다. 명령은 모두 macOS 터미널에서 실행합니다.

- **Ollama 앱**: 설정(Settings)의 컨텍스트 길이 슬라이더를 옮깁니다.
- **환경 변수(Ollama 앱)**: `launchctl setenv OLLAMA_CONTEXT_LENGTH 16384`를 실행하고 Ollama 앱을 다시 시작합니다. 맥 앱은 `launchctl setenv`로 정한 환경 변수를 시작할 때 읽습니다(Ollama FAQ). 맥을 재시동하면 이 설정이 사라지므로 다시 실행합니다.
- **터미널에서 한 번만 시험**: 앱을 끄고 `OLLAMA_CONTEXT_LENGTH=16384 ollama serve`로 서버를 띄웁니다.
- **llama.cpp**: `llama-server -hf bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M -c 16384 -ngl all -fa on`처럼 `-c`로 정합니다. macOS 빌드는 Metal(애플 GPU 가속)이 기본으로 켜져 있습니다(llama.cpp 빌드 문서).

길이를 정하지 않으면 Ollama가 고릅니다. <RuntimeFact id="ollama-default-ctx" />. CanRun은 맥의 통합 메모리가 어느 구간으로 잡히는지 확인하지 못했으므로, `ollama ps`의 CONTEXT 열로 실제 길이를, PROCESSOR 열로 `100% GPU`인지를 확인합니다. 설정 전반은 ‘<GuideLink slug="ollama-context-length" />’에 있습니다.

더 읽을거리:

- 그래픽카드 VRAM별로 도는 모델: <GuideLink slug="vram-requirements" />
- KV 캐시가 늘어나는 원리: <GuideLink slug="kv-cache-context" />
- 더 작은 양자화로 메모리 아끼기: <GuideLink slug="gguf-quantization" />
- 한국 모델의 판정: <GuideLink slug="korean-open-llms" />

칩 페이지에서는 메모리 구성마다 모든 모델의 판정을 볼 수 있습니다.

## 이 숫자는 얼마나 확실한가

메모리 수치는 실제 GGUF 파일 크기, 모델 config에서 구한 KV 캐시, 연산 버퍼 식을 더해 공식으로 계산하므로 오차 범위를 붙이지 않습니다. 다만 GPU 몫 70%는 macOS 기본 한도를 한 비율로 어림한 것이고, 실제 기본값은 용량에 따라 달라 36GB 이상 구성에서는 CanRun 수치가 실제보다 보수적일 수 있습니다(첫 절 참고).

속도는 신뢰 라벨과 오차 범위를 붙인 추정치입니다. 맥에서 실측이 없는 풀 GPU 칸은 보정된 추정 ±20%이고, ±12%는 NVIDIA·AMD 그래픽카드의 dense 모델에만 씁니다. 맥의 CPU 전용 칸은 실측과 대조한 적이 없어 이론 추정 ±30%입니다.

CanRun은 애플의 기본·Pro·Max 칩에 같은 효율 계수를 써서 추정 속도가 대역폭에 비례해 오릅니다. 그런데 llama.cpp 토론 #4167의 공개 측정에서는 M4 Pro에서 40코어 GPU M4 Max로 대역폭이 두 배가 돼도 생성 속도는 두 배에 분명히 못 미치니, Max 칩의 추정치는 오차 범위 아래쪽까지 감안해 읽습니다. gpt-oss-20b·gpt-oss-120b 같은 리즈닝 모델은 사고 토큰을 더 쓰므로 판정 기준을 1.5배 엄격하게 적용합니다.

CanRun 계산에 들어가지 않는 것도 있습니다.

- MLX 형식 모델(애플 MLX 프레임워크용). 추정은 GGUF 파일 기준이고 llama.cpp 결과로 보정했습니다.
- 함께 열어 둔 다른 앱이 쓰는 메모리
- 노트북의 발열·전력 제한(오차 범위로만 흡수)
- `iogpu.wired_limit_mb`로 올린 한도
- 모델이나 요청 여러 개를 동시에 돌리는 경우

내 맥에서 실제로 어떻게 올라갔는지는 `ollama ps`의 SIZE, PROCESSOR(`100% GPU`인지), CONTEXT 열로 확인하고, llama.cpp라면 모델을 불러올 때 나오는 로그를 봅니다. 칩별 결과는 <HubLink gpu="apple-m4" />·<HubLink gpu="apple-m4-pro" /> 같은 칩 페이지에, 그래픽카드와의 비교는 ‘<GuideLink slug="vram-requirements" />’에 있습니다.

문장 속 판정 이름은 모두 8k 컨텍스트·f16 KV 기준입니다. 판정별 조건은 다음과 같습니다.

## 자주 묻는 질문

### 통합 메모리 16GB로 로컬 LLM을 돌릴 수 있나요?

CanRun 계산으로는 8B~12B 모델을 Q4_K_M으로 돌릴 수 있습니다. Llama 3.1 8B와 Gemma 3 12B는 16GB M4의 GPU에 모두 올라가 원활입니다<Expect model="llama-3.1-8b" gpu="apple-m4" verdict="A" /><Expect model="gemma-3-12b" gpu="apple-m4" verdict="A" />. 14B는 경계입니다. Qwen3 14B는 8k에서 <Num kind="needGB" model="qwen3-14b" />가 필요해 16GB의 약 70% 안에 아슬아슬하게 들어가고, M4에서 판정은 겨우 가능이며<Expect model="qwen3-14b" gpu="apple-m4" verdict="B" />, Phi-4는 GPU 몫을 넘습니다. `ollama ps`에서 `100% GPU`인지 확인합니다. gpt-oss-20b는 파일만 <Num kind="fileGB" model="gpt-oss-20b" />로 16GB 맥의 GPU 몫보다 커서 들어가지 않습니다. 모델 카드의 ‘16GB 메모리 안에서’는 16GB 전부를 모델이 쓸 수 있다는 전제입니다. 컨텍스트를 늘리면 여유가 더 줄어듭니다(위 컨텍스트 표).

### GPU가 통합 메모리를 70%보다 더 쓰게 할 수 있나요?

네, 올릴 수 있습니다. llama.cpp 토론 #2182에는 macOS 터미널에서 `sudo sysctl iogpu.wired_limit_mb=N`(N은 MB 단위)으로 한도를 올리는 방법이 나오며, 재시동하면 원래대로 돌아갑니다(유지하려면 `/etc/sysctl.conf`에 추가). macOS 몫을 너무 적게 남기면 스와핑이 심해진다는 경고가 있으니 조금씩 올리고 다른 앱은 닫아 둡니다. CanRun의 표는 기본 한도를 가정하므로 `ollama ps`로 직접 확인합니다. macOS 기본 한도 자체도 용량에 따라 달라서(32GB 이하 맥은 GPU 몫이 약 3분의 2, 그보다 큰 맥은 약 4분의 3), CanRun 표는 실제 기본 한도와 거의 같거나 그보다 보수적으로 잡혀 있습니다.

### 통합 메모리가 크면 모델이 더 빨리 도나요?

모델이 이미 GPU에 모두 올라간다면 아닙니다. CanRun 계산에서 풀 GPU 속도는 칩의 메모리 대역폭이 정하고, 같은 칩이라면 모델이 GPU에 모두 올라가는 메모리 구성끼리는 속도 추정이 같습니다. 메모리가 크면 들어가는 모델과 컨텍스트 길이가 달라집니다. Qwen3 30B-A3B (2507)은 48GB M4 Pro에서 GPU에 모두 올라가 쾌적이지만<Expect model="qwen3-30b-a3b-2507" gpu="apple-m4-pro" verdict="S" />, 24GB에서는 CPU 전용으로 계산돼 판정이 겨우 가능으로 제한됩니다. 예외는 32코어·40코어 GPU판의 대역폭이 다른 M4 Max(<Num kind="bandwidth" gpu="apple-m4-max-32c" />와 <Num kind="bandwidth" gpu="apple-m4-max-40c" />)와 M5 Max로, 애플 사양표상 36GB 구성은 32코어판뿐입니다.

### 맥의 통합 메모리는 그래픽카드 VRAM과 어떻게 다른가요?

CanRun 계산으로는 맥의 GPU가 통합 메모리의 약 70%만 쓰고 모델이 넘치면 나눠 둘 곳이 없지만, 고를 수 있는 최대 메모리 용량은 그래픽카드 VRAM보다 훨씬 큽니다. 16GB 맥이 모델에 주는 메모리는 Windows에서 RTX 3060 12GB가 쓸 수 있는 <Num kind="usableGB" gpu="rtx-3060-12gb" />와 비슷합니다. PC라면 CanRun은 넘친 부분을 그래픽카드와 시스템 RAM에 나눠 두는 경로(부분 오프로드, MoE 전문가 RAM 배치)를 계산하지만, 맥에서는 CanRun이 곧바로 CPU 전용(이론 추정, 겨우 가능이 상한)으로 계산합니다. 실제 배치는 `ollama ps`로 확인합니다. 반면 128GB M4 Max(40코어 GPU)는 gpt-oss-120b를 GPU에 모두 올려 쾌적인데<Expect model="gpt-oss-120b" gpu="apple-m4-max-40c" verdict="S" />, CanRun 카탈로그에서 가장 큰 그래픽카드는 32GB입니다. 큰 모델이 목표라면 그 모델의 필요 메모리를 보고 통합 메모리 용량을 정합니다.
