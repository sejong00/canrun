## 128GB 가운데 GPU가 쓸 수 있는 양

CanRun은 통합 메모리 기기라면 어느 것이든 메모리의 약 70%를 GPU 몫으로 봅니다. 실제 한도는 운영체제와 설정에 따라 다르고, 세 회사가 다루는 방식도 다릅니다.

### 맥 스튜디오

macOS는 GPU가 가져갈 수 있는 통합 메모리에 한도를 둡니다. llama.cpp 토론 #2182에 인용된 코드를 보면, 32GB보다 큰 맥은 약 4분의 1을 남겨 둡니다. 그래서 128GB 맥은 기본 설정에서 GPU가 약 4분의 3까지 쓸 수 있습니다. CanRun이 잡는 70%보다 많습니다. 한도는 macOS 터미널에서 `sudo sysctl iogpu.wired_limit_mb=` 뒤에 MB 단위 값을 붙여 올립니다. 기본값과 명령, macOS에 메모리를 너무 적게 남겼을 때의 위험은 ‘<GuideLink slug="mac-local-llm" />’에서 다룹니다.

### 스트릭스 헤일로

Windows에서는 AMD의 가변 그래픽 메모리(Variable Graphics Memory)를 씁니다. 시스템 RAM 일부를 그래픽 전용 메모리로 돌리는 기능입니다. 설정은 AMD Software: Adrenalin Edition에서 합니다. AMD FAQ에 따르면 128GB Ryzen AI Max+ 395 시스템은 최대 96GB를 그래픽 전용으로 돌릴 수 있습니다. 이렇게 설정하면 공유 메모리까지 합쳐 GPU가 112GB까지 쓸 수 있습니다. 다만 AMD는 작업을 96GB 안에서 돌릴 때 성능이 가장 좋다고 설명합니다.

Linux에서는 사정이 다릅니다. AMD ROCm 문서에 따르면 GPU가 기본으로 쓸 수 있는 공유 메모리는 시스템 RAM의 약 절반입니다. 이 한도를 GTT라고 부릅니다. 커널 드라이버가 정하는 한도라서, llama.cpp를 ROCm으로 돌리든 Vulkan으로 돌리든 똑같이 걸립니다. AMD는 BIOS의 전용 메모리 예약은 작게 두고, 공유 메모리 한도를 올리라고 권합니다. `amd-debug-tools` 패키지에 든 `amd-ttm` 도구로 지금 한도를 보고 새 한도를 정합니다. 바꾼 값은 재부팅한 뒤에 적용됩니다. `amd-ttm`의 GB는 1024 기준이라 CanRun 수치보다 7%쯤 작게 나옵니다. 128GB의 절반이면 gpt-oss-120b의 필요량 <Num kind="needGB" model="gpt-oss-120b" gpu="amd-strix-halo" />를 넣고 남는 여유가 거의 없습니다. 이 모델을 불러오기 전에 한도부터 높여 두세요.

### DGX Spark

NVIDIA는 DGX Spark의 메모리를 128GB 통합 시스템 메모리로만 적고, GPU 몫을 따로 밝히지 않습니다. NVIDIA의 알려진 문제(Known issues) 문서에는 메모리 표시에 관한 내용이 있습니다. GPU에 전용 프레임버퍼 메모리가 없어서, `nvidia-smi`는 전체 메모리 사용량을 Not Supported로 표시합니다. 프로세스별 GPU 메모리는 그대로 보여 줍니다. 같은 문서는 CUDA 프로그램이 읽는 남은 메모리가 실제로 할당할 수 있는 양보다 적게 나올 수 있다고 경고합니다.

### CanRun의 70%는 어디쯤인가

128GB 맥에서 CanRun의 70%는 macOS 기본 한도보다 낮습니다. 스트릭스 헤일로에서는 Linux 기본값과 Windows 최대치 사이에 있습니다. DGX Spark는 GPU 몫이 공개되지 않아서, 70%는 CanRun이 가정한 값입니다. 이 차이는 필요량이 그 사이에 걸리는 모델에서만 문제가 됩니다. 예를 들어 Solar Open 2 250B의 Q2_K 파일은 <Num kind="needGB" model="solar-open2-250b" quant="Q2_K" gpu="amd-strix-halo" />가 필요합니다. Q2_K는 품질 손실이 큰 2비트 양자화입니다. 이 필요량은 CanRun의 GPU 몫을 넘어서, 128GB 기기에서는 CPU 전용으로 계산됩니다. CPU 전용으로 계산하면 속도와 상관없이 판정이 겨우 돌아가는 단계에서 멈춥니다<Expect model="solar-open2-250b" gpu="amd-strix-halo" ram="128" quant="Q2_K" verdict="B" mode="cpu-only" />. 이 값은 이론 추정입니다. 한도를 올리면 GPU에 들어갈 수도 있습니다. 실제로 어디에 올라갔는지는 `ollama ps`나 llama.cpp 로딩 로그로 확인하세요.

## 이 숫자는 얼마나 확실한가

메모리 수치는 공식으로 계산합니다. 실제 GGUF 파일 크기에 모델 설정으로 구한 KV 캐시와 연산 버퍼를 더합니다. 어림한 부분은 GPU 몫입니다. 통합 메모리 기기 모두에 70%를 쓰고, 기기별 실제 한도와 어떻게 다른지는 둘째 절에서 설명했습니다.

속도는 신뢰 라벨이 ‘실측’인 칸만 공개 벤치마크 결과입니다. 이 글에서 GPU에 전부 올라가는 나머지 칸은 ‘보정된 추정’이고, 오차 범위는 ±20%입니다. ±12%는 NVIDIA·AMD 그래픽카드의 dense 모델에만 씁니다. CPU 전용 칸과 전문가를 RAM에 둔 RTX 5090 칸은 ‘이론 추정(±30%)’입니다.

CanRun은 기기 종류마다 효율 계수로 대역폭을 속도로 바꿉니다. 계수는 공개 벤치마크 결과에 맞춰 정합니다. DGX Spark 계수는 llama.cpp 개발진의 결과 파일에서 나왔습니다. 같은 빌드로 다섯 모델을 대화 첫머리와 8k 토큰이 쌓인 뒤에 잰 결과이고, CanRun 추정은 그 결과 하나하나와 5분의 1 안쪽으로 맞습니다. 다만 모두 mmap을 끈 기기 한 대의 결과입니다. 스트릭스 헤일로 계수는 다른 공개 결과에서 나왔습니다. 그래서 CanRun 추정은 이 글의 모든 모델에서 DGX Spark를 스트릭스 헤일로보다 빠르게 보고, 그 차이는 앞의 같은 빌드 비교보다 큽니다. 차이의 크기는 조심해서 봐야 합니다. 애플 칩의 공개 결과를 보면 Ultra 칩은 Max 칩보다 대역폭을 속도로 덜 살립니다. 그래서 CanRun은 Ultra 칩에 더 낮은 계수를 씁니다.

소프트웨어도 결과를 바꿉니다. 스트릭스 헤일로는 llama.cpp를 ROCm이나 Vulkan으로 돌립니다. DGX Spark 결과는 llama.cpp 빌드와 mmap 설정에 따라 달라졌습니다. 맥에서는 MLX 형식 모델도 돌릴 수 있습니다. CanRun의 추정은 llama.cpp에서 GGUF 파일을 돌리는 경우를 기준으로 합니다.

CanRun 계산에 넣지 않는 것도 있습니다.

- 프롬프트 처리 시간은 이 글의 판정에 들어가지 않습니다.
- 기기의 전력 모드는 따로 계산하지 않습니다.
- 사용자가 올린 GPU 메모리 한도는 반영하지 않습니다.
- 다른 프로그램이 쓰는 메모리는 따로 빼지 않습니다.
- 요청 여러 개를 동시에 처리하는 경우도 계산하지 않습니다.

내 기기에서 모델이 실제로 어떻게 올라갔는지는 `ollama ps`로 확인합니다. SIZE 열에서 차지한 메모리를, PROCESSOR 열에서 `100% GPU`인지를, CONTEXT 열에서 컨텍스트 길이를 봅니다. llama.cpp라면 모델을 불러올 때 나오는 로그를 봅니다. DGX Spark에서 `nvidia-smi`는 전체 메모리 사용량을 Not Supported로 표시하지만, 프로세스별 GPU 메모리는 보여 줍니다.

이 글에서 말하는 판정은 모두 8k 컨텍스트·f16 KV 기준입니다. 생각 모드가 있는 모델은 답하기 전에 토큰을 더 쓸 수 있습니다. 그래서 CanRun은 이런 모델의 속도 기준을 1.5배 엄격하게 잡습니다. Gemma 4 31B처럼 생각 모드가 기본으로 꺼져 있어도 마찬가지입니다. 아래 범례에는 이 점이 나오지 않습니다. 판정별 조건은 아래 표와 같습니다.

답을 생성하는 속도는 큰 차이가 없습니다. 한 참여자가 같은 llama.cpp 빌드로 잰 결과에서, 기본 설정으로는 두 기기가 거의 같았습니다. DGX Spark에서 mmap을 끄자 대화 첫머리에서 약 5분의 1, 32k 토큰이 쌓인 뒤에는 약 10분의 1 더 빨랐습니다. DGX Spark가 크게 앞서는 것은 프롬프트 처리이고, 프롬프트가 길수록 차이가 커집니다. CanRun 추정은 이 글의 모든 모델에서 DGX Spark를 스트릭스 헤일로보다 빠르게 봅니다. MoE 모델도 마찬가지이고, 차이는 그 비교보다 큽니다. 두 기기의 효율 계수가 서로 다른 공개 결과에서 나왔으니, 차이의 크기는 조심해서 봐야 합니다. 메모리는 둘 다 128GB이고, CanRun 계산의 GPU 몫도 같습니다.

### 맥 스튜디오가 스트릭스 헤일로나 DGX Spark보다 빠른가요?

생성 속도는 CanRun 추정으로 더 빠릅니다. 대역폭이 M4 Max는 두 배쯤, Ultra 칩은 세 배쯤 되기 때문입니다. 차이는 위 판정표에서 볼 수 있고, dense 모델에서 가장 크게 벌어집니다. 프롬프트 처리는 CanRun 데이터의 M2 Ultra 결과가 대화 첫머리에서 스트릭스 헤일로와 DGX Spark 사이에 있습니다. 32k 토큰이 쌓인 뒤의 맥 결과는 없습니다.

### 128GB로 gpt-oss-120b를 긴 컨텍스트로 돌릴 수 있나요?

CanRun 계산으로는 돌릴 수 있습니다. 128k 컨텍스트를 f16 KV 캐시로 잡아도 필요량이 <Num kind="needGB" model="gpt-oss-120b" ctx="131072" gpu="nvidia-dgx-spark" />라서, 128GB 기기의 GPU 몫 안에 들어갑니다<Expect model="gpt-oss-120b" gpu="nvidia-dgx-spark" ctx="131072" fits="true" />. 다만 긴 컨텍스트에서는 판정이 한 단계 내려갑니다. 스트릭스 헤일로는 64k부터(위 표)<Expect model="gpt-oss-120b" gpu="amd-strix-halo" ctx="65536" verdict="A" />, DGX Spark는 128k에서입니다<Expect model="gpt-oss-120b" gpu="nvidia-dgx-spark" ctx="65536" verdict="S" /><Expect model="gpt-oss-120b" gpu="nvidia-dgx-spark" ctx="131072" verdict="A" />. Linux에서 스트릭스 헤일로를 쓴다면, 둘째 절에서 설명한 대로 GPU 메모리 한도부터 올리세요.
