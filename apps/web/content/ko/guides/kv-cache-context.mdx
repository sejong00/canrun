KV 캐시는 컨텍스트의 토큰마다 각 어텐션 층이 키와 값을 저장해 두는 메모리라, 크기가 고정된 모델 파일과 달리 설정한 컨텍스트 길이에 비례해 커집니다. 예를 들어 4비트급 양자화 Q4_K_M으로 받은 Llama 3.1 8B는 파일이 <Num kind="fileGB" model="llama-3.1-8b" />인데, 128k에서 기본 형식(f16) KV 캐시는 <Num kind="kvGB" model="llama-3.1-8b" ctx="131072" />로 파일의 세 배가 넘습니다. 늘어나는 폭은 어텐션 설계에 따라 달라서, 슬라이딩 윈도나 하이브리드 구조 모델은 같은 컨텍스트에서 훨씬 적게 씁니다. KV 캐시를 8비트(q8_0)·4비트(q4_0)로 양자화하면 캐시가 각각 대략 절반과 4분의 1로 줄지만 정밀도 손실이 따릅니다.

## 컨텍스트를 늘리면 메모리가 왜 더 드나

필요한 메모리는 세 부분입니다. 모델 파일은 가중치 양자화 등급(Q4_K_M 등)으로 크기가 정해져 컨텍스트와 무관하고, KV 캐시는 컨텍스트 길이에 비례해 커집니다. 연산 버퍼는 계산 중간값을 담는 작은 작업 공간이고, CanRun은 llama.cpp 로그를 바탕으로 만든 근사식으로 컨텍스트에 따라 조금씩 늘려 잡습니다.

KV 캐시는 이미 컨텍스트에 들어온 토큰의 키(key)와 값(value)을 모아 두는 공간입니다. 각 어텐션 층이 토큰마다 KV 헤드(키와 값을 만드는 헤드로, 쿼리 헤드 여러 개가 하나를 나눠 쓸 수 있습니다)별로 키와 값을 저장해 두므로, 새 토큰을 만들 때 앞 토큰의 키와 값을 다시 계산하지 않아도 됩니다. 토큰 하나가 차지하는 KV 크기는 `2(키와 값) × 층 수 × KV 헤드 수 × 헤드 크기 × 값 하나의 바이트 수`이고, f16은 값을 16비트로 저장하는 기본 형식입니다.

전체 KV 크기는 토큰당 크기에 컨텍스트 길이를 곱한 값이라, 컨텍스트를 두 배로 늘리면 KV 캐시도 두 배가 됩니다. 아래 표의 열은 4k에서 32k까지 두 배씩 늘어납니다.

### 그룹 쿼리 어텐션(GQA)

GQA는 여러 쿼리 헤드가 KV 헤드 하나를 나눠 쓰게 해 KV 캐시를 줄입니다(Llama 3.1 모델 카드: 모든 버전에 GQA 적용). 모든 층이 컨텍스트 전체를 보는 전체 어텐션 모델이면 비용은 총 파라미터가 아니라 층 수 × KV 헤드 수 × 헤드 크기를 따르므로, 같은 14B급이라도 Phi-4가 Qwen3 14B보다 토큰당 KV가 큽니다(표 참고). 한국 모델도 마찬가지로, HyperCLOVA X SEED Think 14B는 토큰당 KV가 Qwen3 14B와 비슷하고 Kanana 1.5 8B는 Llama 3.1 8B와 같습니다.

### 슬라이딩 윈도 어텐션

Gemma 3·Gemma 4, gpt-oss, EXAONE 4.0 32B·EXAONE 4.5 33B는 최근 토큰 일정 구간만 보는 로컬 층과 컨텍스트 전체를 보는 글로벌 층을 섞어 씁니다. 로컬 층의 방식을 슬라이딩 윈도(sliding window) 어텐션이라고 하며, 두 층 가운데 글로벌 층의 KV 캐시만 컨텍스트 길이에 따라 커집니다. Gemma와 이 두 EXAONE 모델은 로컬 층이 대부분이고, gpt-oss는 두 층이 절반씩입니다. Gemma 3 기술 보고서는 글로벌 층당 로컬 층을 늘리고 로컬 구간을 짧게 해 KV 메모리를 줄였다고 설명합니다. gpt-oss-20b config에는 윈도가 128토큰인 슬라이딩 층과 전체 어텐션 층이 번갈아 나옵니다. 모델 카드에 따르면 EXAONE 4.0 32B는 로컬·글로벌 층을 3:1로 섞습니다(같은 4.0 세대의 1.2B는 모든 층이 전체 어텐션입니다). 표에서 <HubLink model="gemma-3-12b" />의 토큰당 KV는 크기가 비슷한 Qwen3 14B의 절반에도 못 미칩니다.

32B급 한국 모델에서도 차이가 뚜렷합니다. CanRun 계산으로 LG <HubLink model="exaone-4.0-32b" />의 f16 KV 32k는 <Num kind="kvGB" model="exaone-4.0-32b" ctx="32768" />로, Qwen3 32B(<Num kind="kvGB" model="qwen3-32b" ctx="32768" />)의 4분의 1 수준입니다. 이 값은 슬라이딩 층의 윈도 부분을 뺀 것이라 실제로는 이보다 더 쓰고, 두 모델의 차이도 그만큼 줄어듭니다(아래 ‘CanRun이 슬라이딩 윈도·하이브리드 모델을 세는 방법’ 참고).

### 하이브리드 선형 어텐션(Qwen3.5)

Qwen3.5 9B 모델 카드에 따르면 Gated DeltaNet 층 3개 뒤에 Gated Attention 층 1개가 오는 묶음이 8번 반복됩니다. 다른 Qwen3.5 모델도 같은 3:1 묶음을 쓰고 묶음 수만 다릅니다. 네 층 가운데 한 층(Gated Attention)만 KV 캐시를 두고, 선형 어텐션 층인 Gated DeltaNet은 컨텍스트와 상관없이 크기가 일정한 상태만 가집니다. 그래서 f16 KV 32k에서 <HubLink model="qwen3.5-9b" />는 <Num kind="kvGB" model="qwen3.5-9b" ctx="32768" />로, 크기가 비슷한 Qwen3 8B(<Num kind="kvGB" model="qwen3-8b" ctx="32768" />)의 약 4분의 1입니다.

### MoE 여부와 파라미터 수로는 알 수 없다

MoE(전문가 혼합) 구조만으로는 KV 캐시가 줄지 않습니다. KV는 활성 파라미터가 아니라 어텐션 구조를 따르기 때문입니다. ### CanRun이 슬라이딩 윈도·하이브리드 모델을 세는 방법

## KV 캐시 양자화 — q8_0·q4_0

KV 캐시 양자화는 키와 값을 16비트 대신 8비트(q8_0)나 4비트(q4_0) 블록으로 저장합니다. 블록마다 스케일 값도 함께 저장하므로 CanRun 표에서는 f16 대비 q8_0이 약 54%, q4_0이 약 29%로, Ollama FAQ가 말하는 대략 절반·4분의 1보다 조금 큽니다.

가중치 양자화와는 별개입니다. 대문자 Q4_K_M·Q8_0은 모델 파일의 양자화 등급으로 파일 크기를 정하고, 소문자 q8_0·q4_0 KV는 실행할 때 지정하는 설정으로 컨텍스트 메모리만 줄입니다. 커뮤니티 글은 둘 다 ‘Q8’로 쓰기도 하니 구분해야 합니다. 둘은 함께 쓸 수 있고, KV 양자화로 아끼는 양은 컨텍스트가 길수록 커집니다. 모델 파일 쪽은 ‘<GuideLink slug="gguf-quantization" />’에서 다룹니다.

대가는 정밀도입니다. Ollama FAQ에 따르면 q8_0은 정밀도 손실이 아주 작고, q4_0은 작은~중간 수준의 손실이 있으며 컨텍스트가 길수록 더 두드러질 수 있습니다. 영향은 모델과 작업에 따라 다르고, 쿼리 헤드 여러 개가 KV 헤드 하나를 나눠 쓰는 정도(GQA 수)가 높은 모델(FAQ의 예는 Qwen2)은 더 크게 받을 수 있다고 합니다. CanRun은 품질을 측정하지 않습니다. 메모리 기준으로는 f16으로 넘치면 q8_0을 먼저 시도하고, q8_0으로도 넘칠 때만 q4_0을 씁니다. 컨텍스트를 줄이는 방법도 있습니다.

### 켜는 방법

<RuntimeFact id="ollama-kv-cache-type" />. Windows에서는 작업 표시줄 알림 영역의 Ollama 아이콘에서 앱을 종료한 뒤, PowerShell에서 `$env:OLLAMA_CONTEXT_LENGTH="16384"; $env:OLLAMA_FLASH_ATTENTION="1"; $env:OLLAMA_KV_CACHE_TYPE="q8_0"; ollama serve`를 실행합니다(위 12GB 예시의 16k q8_0 칸과 같은 설정). 이 설정은 그 PowerShell 창에서 띄운 서버에만 적용되고, 모델은 다른 PowerShell 창에서 `ollama run hf.co/unsloth/Qwen3-14B-GGUF:Q4_K_M`로 불러옵니다. 계속 쓰려면 ‘계정의 환경 변수 편집’(관리자 권한 불필요)에서 사용자 변수 `OLLAMA_FLASH_ATTENTION`(값 `1`)과 `OLLAMA_KV_CACHE_TYPE`(값 `q8_0` 또는 `q4_0`)을, 필요하면 `OLLAMA_CONTEXT_LENGTH`도 함께 추가하고 Ollama를 다시 실행합니다.

llama.cpp의 `llama-server`는 `-fa on --cache-type-k q8_0 --cache-type-v q8_0`처럼 키와 값의 타입을 따로 지정합니다(서버 README 기준 기본값 f16). 조합 페이지가 q8_0·q4_0 칸에 보여 주는 명령도 이 형태입니다.

GPU에 다 들어가는 칸끼리 비교할 때 q8_0·q4_0 칸의 속도가 f16보다 높게 나오는 것은 CanRun 대역폭 공식에서 읽을 KV가 줄어든 결과일 뿐 측정값이 아닙니다. KV 캐시 양자화는 속도가 아니라 메모리를 위한 수단입니다.

## 이 숫자는 얼마나 확실한가

메모리 수치 가운데 파일 크기는 실제 GGUF 파일 크기를 그대로 쓰고, KV 캐시는 각 모델이 공개한 config에서 공식으로 계산한 값입니다. 토큰당 KV 식은 CanRun 엔진 테스트의 일곱 가지 구조에서 공개된 값과 일치합니다. 연산 버퍼는 llama.cpp 로그를 바탕으로 한 근사입니다.

슬라이딩 윈도·하이브리드 모델의 KV 수치는 윈도 부분과 선형 어텐션 층의 상태를 뺀 만큼 실제보다 낮게 나오고, 윈도가 넓은 EXAONE 4.0 32B는 짧은 컨텍스트에서 차이가 큽니다. llama.cpp 서버의 `--swa-full` 옵션(기본 꺼짐)을 켜면 슬라이딩 윈도 층도 컨텍스트 전체만큼 캐시를 잡으므로, 슬라이딩 윈도 모델은 CanRun 수치보다 훨씬 많이 씁니다. 예를 들어 Gemma 3 12B는 캐시를 잡는 층이 CanRun이 세는 글로벌 층의 여섯 배라, KV 캐시도 CanRun 수치의 여섯 배 정도가 됩니다.

CanRun 계산은 런타임의 실제 동작이 아닙니다. Ollama는 자체 메모리 추정으로 GPU·CPU 분할을 정하므로, 내 PC에 실제로 어떻게 올라갔는지는 `ollama ps`의 SIZE·PROCESSOR·CONTEXT 열로 확인합니다. 표는 Windows에서 그 카드로 화면을 출력하고 시스템 RAM 32GB(DDR5)에 모델 하나, 요청 슬롯 하나를 가정합니다. Ollama FAQ에 따르면 필요한 메모리는 `OLLAMA_NUM_PARALLEL` × `OLLAMA_CONTEXT_LENGTH`에 따라 늘어납니다.

속도는 오차 범위와 신뢰 라벨을 붙인 추정치입니다. 보정된 추정은 NVIDIA·AMD 그래픽카드에서 dense 모델을 GPU에만 올릴 때 ±12%, 부분 오프로드·MoE·그 밖의 하드웨어에서 ±20%이고, 이론 추정은 ±30%입니다. 이 글의 두 컨텍스트 표는 속도 칸이 모두 보정된 추정입니다. 다만 q8_0·q4_0 칸은 KV 양자화 효과를 공식으로만 반영한 값이고, CanRun이 보정에 쓰는 공개 측정 가운데 KV 캐시를 양자화한 기록은 없습니다.

MoE 모델 조합 페이지에서 전문가를 시스템 RAM에 두는 칸(MoE 전문가 RAM 배치)은 이론 추정이고, 실제보다 느리게 나올 가능성이 큽니다. 컨텍스트를 늘리면 이 방식으로 바뀌는 칸이 생기는데, 이런 칸의 속도는 확정된 결과가 아니라 참고치로 봅니다.

문장 속 판정 이름은 모두 8k 컨텍스트·f16 KV 기준이고, 다른 컨텍스트의 결과는 표에서 읽습니다.

## 자주 묻는 질문

### 대화가 짧아도 컨텍스트를 길게 잡으면 메모리를 더 쓰나요?

네. Ollama 컨텍스트 길이 문서에 따르면 컨텍스트 길이를 늘리면 필요한 메모리가 늘어나고, CanRun 표도 대화에 쓴 길이가 아니라 설정한 길이만큼 KV 캐시를 잡는다고 계산합니다. Llama 3.1 8B의 f16 KV 캐시는 8k에서 <Num kind="kvGB" model="llama-3.1-8b" ctx="8192" />, 128k에서 <Num kind="kvGB" model="llama-3.1-8b" ctx="131072" />입니다. 필요한 만큼만 설정하고 `ollama ps`의 CONTEXT·SIZE 열로 확인합니다. 컨텍스트가 덜 찼을 때도 메모리는 그대로 차지하지만, 속도는 끝까지 찼다고 가정한 표의 행보다 덜 떨어집니다.

### 왜 큰 모델이 작은 모델보다 컨텍스트 메모리를 덜 쓰기도 하나요?

KV 비용이 파라미터 수가 아니라 어텐션 설계(층 수, KV 헤드, 슬라이딩 윈도·선형 어텐션 층)로 정해지기 때문입니다. CanRun 계산으로 f16 KV 32k에서 gpt-oss-120b는 <Num kind="kvGB" model="gpt-oss-120b" ctx="32768" />로 Llama 3.1 8B의 <Num kind="kvGB" model="llama-3.1-8b" ctx="32768" />보다 작고, EXAONE 4.0 32B는 <Num kind="kvGB" model="exaone-4.0-32b" ctx="32768" />로 Qwen3 32B(<Num kind="kvGB" model="qwen3-32b" ctx="32768" />)의 4분의 1 수준입니다. EXAONE 값은 슬라이딩 층의 윈도 부분을 뺀 것이라 실제로는 이보다 더 씁니다. MoE 구조라고 KV 캐시가 줄지는 않습니다. 둘 다 MoE이지만 어텐션 구조가 다른 Qwen3 30B-A3B (2507)은 gpt-oss-20b보다 토큰당 비용이 네 배 큽니다. 컨텍스트를 정하기 전에 KV 표에서 그 모델의 행을 봅니다.

### KV 캐시 양자화는 Q4_K_M 모델 파일을 고르는 것과 같은 건가요?

아닙니다. Q4_K_M 같은 가중치 양자화는 모델 파일의 고정 크기를, q8_0·q4_0 KV는 실행할 때 컨텍스트가 차지하는 메모리를 정합니다. 둘은 독립이라 함께 쓸 수 있고, KV 양자화로 아끼는 양은 컨텍스트가 길수록 커집니다. RTX 3060 12GB(사용 가능 <Num kind="usableGB" gpu="rtx-3060-12gb" />)에서 Qwen3 14B는 16k일 때 f16 KV로 <Num kind="needGB" model="qwen3-14b" ctx="16384" />, q8_0으로 <Num kind="needGB" model="qwen3-14b" ctx="16384" kv="q8_0" />가 필요합니다. f16으로는 사용 가능 메모리를 넘고, q8_0이면 아슬아슬하게 들어가니 `ollama ps`로 확인합니다. Ollama는 `OLLAMA_KV_CACHE_TYPE`(서버 전체 설정, 플래시 어텐션 필요), llama.cpp는 `-fa on --cache-type-k q8_0 --cache-type-v q8_0`처럼 켭니다.

### q8_0·q4_0 KV 캐시는 품질을 얼마나 떨어뜨리나요?

Ollama FAQ에 따르면 q8_0은 정밀도 손실이 아주 작고, q4_0은 작은~중간 수준의 손실이 있으며 컨텍스트가 길수록 더 두드러질 수 있습니다. 영향은 모델과 작업에 따라 다르고, 쿼리 헤드 여러 개가 KV 헤드 하나를 나눠 쓰는 정도(GQA 수)가 높은 모델(예: Qwen2)은 더 크게 받을 수 있습니다. CanRun은 품질을 측정하지 않습니다. 메모리 기준으로는 f16으로 넘치면 q8_0을, q8_0으로도 넘칠 때만 q4_0을 쓰고, 목표 컨텍스트에서 평소 프롬프트로 직접 시험해 봅니다.
