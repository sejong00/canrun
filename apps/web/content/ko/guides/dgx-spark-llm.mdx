## 두 대·네 대 연결

### NVIDIA가 지원하는 범위

DGX Spark에는 QSFP 포트 두 개가 달린 ConnectX-7 네트워크가 들어 있습니다. NVIDIA 클러스터링 문서는 케이블로 바로 잇는 경우 세 대까지, 스위치를 쓰면 네 대까지 지원한다고 적습니다. 제품 페이지는 대수를 2의 거듭제곱으로 맞추라고 권합니다. 두 대는 QSFP 케이블 하나로 잇습니다. NVIDIA 케이블 연결 안내에 따르면 케이블을 두 개로 늘려도 성능은 오르지 않습니다. 세 대는 케이블 세 개로 고리 모양으로 잇습니다. 네 대는 NVIDIA 스위치 연결 안내대로 200GbE 스위치를 씁니다. 케이블 네 개로 고리를 만드는 방법도 있지만 수동 설정에서만 됩니다.

NVIDIA가 여러 대용으로 낸 공식 안내는 NCCL과 vLLM입니다. NCCL은 기기 사이에서 GPU끼리 데이터를 주고받는 라이브러리입니다. vLLM 안내는 두 대~네 대를 다룹니다. NVIDIA의 llama.cpp 안내는 여러 대 연결을 다루지 않습니다. llama.cpp RPC로 여러 대를 잇는 것은 커뮤니티에서 쓰는 방법입니다. CanRun이 계산하는 것은 이 방식입니다. 이 사이트가 이미 보여 주는 llama.cpp 명령을 그대로 넓힌 방식이기 때문입니다.

### CanRun이 계산하는 방식: llama.cpp RPC

llama.cpp RPC에서는 첫 기기가 `llama-server`를 띄우고, 나머지 기기는 RPC 서버를 띄워 층을 나눠 맡습니다. 메모리는 합쳐지지만 토큰은 모든 기기를 차례로 지나갑니다. 그래서 대역폭은 합쳐지지 않고, 기기를 건널 때마다 토큰 하나에 드는 시간이 늘어납니다. CanRun은 두 대로 돌린 공개 결과에서 이 시간을 구하고, 기기가 하나 늘 때마다 한 번씩 더합니다. 원래 빠른 작은 모델일수록 이 시간이 차지하는 비율이 커서 더 많이 느려집니다.

공개 결과도 같은 방향을 가리킵니다. llama.cpp의 DGX Spark 토론에서 한 참여자가 같은 빌드로 gpt-oss-120b를 한 대와 두 대에서 돌렸습니다. 기본 TCP 연결에서는 두 대가 5분의 1쯤 느렸습니다. RDMA로 이은 다른 테스터는 DeepSeek V4 Flash 0731을 두 대로 돌려도 몇 % 느려지는 데 그쳤습니다. 이 테스터는 한 대에 안 들어가는 4비트 파일도 두 대에 올렸습니다. 같은 토론에는 MiniMax-M2와 Qwen3-VL-235B의 4비트 파일을 두 대로 돌린 결과도 있습니다. 둘 다 한 대에는 안 들어가는 크기입니다. 네 대를 llama.cpp RPC로 돌린 공개 결과는 찾지 못했습니다. 그래서 CanRun의 네 대 행은 두 대에서 구한 시간을 늘려 잡은 값입니다.

아래 입력 칸으로 계산기를 열어 DGX Spark를 고르고 연결 대수를 정하면, 기기마다 실행할 명령이 결과에 나옵니다. 명령은 아래와 같은 꼴이고, 주소 자리에는 각 기기의 ConnectX-7 주소를 넣습니다. 먼저 2번 기기부터 나머지 기기마다 RPC 서버를 띄웁니다.

```
ggml-rpc-server -H <node2-ip> -p 50052 -c
```

그다음 1번 기기에서 llama-server를 실행합니다.

```
llama-server -hf <model> -c 8192 -ngl all -fa on --rpc <node2-ip>:50052
```

llama.cpp는 `-DGGML_RPC=ON`으로 빌드하고 `ggml-rpc-server` 타깃도 함께 빌드해야 합니다. NVIDIA llama.cpp 안내의 빌드 명령은 `llama-server`만 만들기 때문입니다. 2026년 6월 말 전 빌드에서는 서버 이름이 `rpc-server`입니다. libibverbs가 있는 상태로 빌드하면 RPC 연결이 알아서 RDMA로 바뀝니다. RPC 서버에는 보안 기능이 없으니, 기기끼리 잇는 전용 연결에서만 쓰세요. Ollama는 이렇게 모델을 여러 기기에 나눠 올리지 않습니다.

### vLLM 텐서 병렬은 더 빠를 수 있다

vLLM이나 TensorRT-LLM은 층 하나를 여러 기기에 나눠 맡길 수 있습니다. 이 방식을 텐서 병렬이라고 부릅니다. 토큰마다 기기가 저마다 층의 일부만 읽으니, 이때는 대역폭도 합쳐집니다. NVIDIA 기술 블로그는 NVFP4 Llama 3.3 70B를 TensorRT-LLM 텐서 병렬로 돌린 결과를 실었습니다. 출력 토큰 하나에 걸리는 시간이 두 대에서 절반쯤으로, 네 대에서 4분의 1을 조금 넘는 수준으로 줄었습니다. 한 테스터는 DeepSeek V4 Flash 0731을 두 대에서 vLLM으로 돌렸습니다. 같은 두 대의 llama.cpp RPC보다 네 배쯤 빨랐습니다. 다만 글쓴이가 밝혔듯 두 쪽은 가중치와 양자화가 서로 다릅니다.

CanRun은 텐서 병렬을 계산하지 않습니다. 이 사이트의 여러 대 행은 모두 llama.cpp RPC 기준입니다. 여러 대에서 vLLM을 돌릴 계획이라면 이 행은 llama.cpp 기준값으로만 보세요. vLLM은 가중치 형식과 메모리 설정도 따로 씁니다.

## 이 숫자는 얼마나 확실한가

메모리 수치는 공식으로 계산한 값입니다. 실제 GGUF 파일 크기, 모델 설정에서 구한 KV 캐시 크기, 연산 버퍼 공식을 씁니다. 근사가 들어가는 곳은 GPU 몫입니다. 128GB 구성은 가장 낮은 공개 부팅 기록에서 구했고, 64GB 구성은 그 값에서 다시 계산했습니다. 여러 대를 이으면 CanRun은 모델을 가장 많이 맡는 기기 한 대를 봅니다. 층은 llama.cpp 기본값처럼 기기마다 남은 메모리 비율로 나눈다고 봅니다. 층마다 크기가 같다고 보고 계산하므로 이 몫도 근사입니다.

한 대의 속도는 ‘실측’ 라벨이 붙은 칸이 공개 벤치마크 결과입니다. 나머지 한 대 칸은 ±20% 범위의 보정된 추정입니다. 보정에는 llama.cpp 개발자들이 mmap을 끄고 잰 DGX Spark 결과 파일과, llama.cpp 풀 리퀘스트 하나에 실린 DGX Spark 결과를 썼습니다. 프롬프트 처리 계수는 그 풀 리퀘스트에서만 구했습니다. 여러 대 행의 판정은 모두 이론 추정(±30%)이고, 같은 모델의 CanRun 한 대 추정보다 빠르게 나오지 않습니다. 한 대에 들어가는 모델은 여러 대 판정을 따로 보이지 않습니다. 한 대 칸에 공개 벤치마크가 있는 Gemma 4 31B도 그렇습니다<Expect model="gemma-4-31b" gpu="nvidia-dgx-spark" ram="64" fits="true" confidence="measured" /><Expect model="gemma-4-31b" gpu="nvidia-dgx-spark" ram="64" nodes="2" oneUnit="true" />. 계산기에서 이 모델로 여러 대를 고르면 그 추정이 공개 벤치마크보다 높게 나올 수 있습니다. 공개 벤치마크가 CanRun의 한 대 추정보다 낮기 때문입니다. 기기를 건너는 시간은 기본 TCP 연결로 두 대를 돌린 공개 결과에서 구했습니다. RDMA로 두 대를 이은 공개 결과도 있습니다. 같은 테스터가 잰 한 대 결과와 비교하면, 기기를 건널 때마다 잃는 시간이 CanRun이 잡은 값보다 짧았습니다. 네 대는 비교할 공개 결과가 없습니다. 여러 대의 프롬프트 처리 속도는 한 대와 같은 값으로 추정하며, 대략 ±40% 범위입니다. 두 대로 돌린 공개 결과는 한 대보다 빠른 경우와 느린 경우가 섞여 있습니다.

텐서 병렬, 전원 모드, 다른 프로그램이 쓰는 메모리, 동시에 여러 요청을 받는 경우는 계산하지 않습니다. 본문의 판정 이름은 8k 컨텍스트·f16 KV 기준입니다. 생각 모드가 있는 모델은 답하기 전에 생각에 토큰을 더 쓸 수 있습니다. Gemma 4 31B처럼 기본으로 꺼져 있어도 마찬가지라, CanRun은 속도 기준을 1.5배 엄격하게 잡습니다. 아래 범례에는 이 조정이 나오지 않습니다. 판정 기준은 다음과 같습니다.

같은 GB10 칩과 같은 메모리 대역폭을 쓰고, 주로 저장장치가 다릅니다. 그래서 CanRun은 이 제품들을 DGX Spark로 계산하고, 계산기에서 제품 이름으로 찾을 수도 있습니다. NVIDIA가 직접 파는 제품은 128GB뿐이고, 64GB 구성은 협력 제조사만 팝니다.
