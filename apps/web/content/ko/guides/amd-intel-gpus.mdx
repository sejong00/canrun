## ROCm·Vulkan·SYCL — Windows와 Linux에서 무엇이 되나

Ollama와 LM Studio는 둘 다 llama.cpp로 GGUF 모델을 돌립니다. llama.cpp가 AMD·인텔 GPU를 쓰는 길은 크게 세 가지입니다. ROCm은 AMD의 GPU 연산 플랫폼이고, llama.cpp는 HIP 백엔드로 ROCm을 씁니다. Vulkan은 제조사와 상관없이 쓰는 그래픽·연산 API입니다. Ollama 문서에 따르면 Windows 그래픽 드라이버는 대부분 Vulkan 지원을 함께 담고 있습니다. SYCL은 인텔 GPU용 백엔드입니다. llama.cpp 문서도 주로 인텔 GPU를 위해 만들었다고 설명합니다.

가중치와 KV 캐시는 어느 백엔드로 돌려도 크기가 같습니다. 그래서 CanRun의 메모리 수치는 백엔드와 상관없이 같습니다. 다만 런타임이 계산 중에 쓰는 메모리는 백엔드마다 조금 다를 수 있습니다. 여유가 적은 모델이라면 `ollama ps`로 확인하세요.

### Ollama

Ollama 하드웨어 문서는 ROCm으로 지원하는 라데온 카드를 OS별로 따로 적어 둡니다(2026년 10월 확인).

- **Linux**(AMD ROCm v7 드라이버): RX 9070 XT·9070 GRE·9070·9060 XT·9060 XT LP·9060, RX 7600 이상의 RX 7000 계열, RX 6800 이상의 RX 6000 계열, Radeon PRO와 Ryzen AI 칩
- **Windows**(ROCm v7, 즉 HIP 7 지원 드라이버): RX 7900 XTX·7900 XT·7900 GRE·7800 XT·7700 XT·7600 XT·7600과 Radeon PRO W7500~W7900뿐

그 밖의 GPU는 Vulkan으로 돌립니다. 같은 문서에 따르면 Vulkan은 백엔드가 설치돼 있으면 Windows와 Linux에서 기본으로 켜집니다. Windows의 Ollama는 <HubLink gpu="rx-9070-xt" />와 <HubLink gpu="rx-9060-xt-16gb" />를 Vulkan으로 돌립니다. 인텔 Arc 카드는 문서에 이름이 없지만, 역시 Vulkan으로 돌아갑니다. Linux용으로는 인텔 드라이버 설치 안내 링크가 걸려 있습니다.

Ollama가 실제로 무엇을 골랐는지는 서버 로그의 `inference compute` 줄에서 봅니다. 찾은 GPU마다 쓸 라이브러리(ROCm·Vulkan·CUDA)가 적혀 있습니다. 로그 위치와 GPU를 못 잡을 때 할 일은 따로 정리했습니다. ‘<GuideLink slug="gpu-offload-check" />’ 가이드를 보세요.

### llama.cpp

llama.cpp는 GitHub 릴리스마다 Windows용 빌드를 여러 개 올립니다. CUDA·CPU 빌드 말고도 Vulkan·ROCm·SYCL 빌드가 따로 있습니다(2026년 10월 b11630에서 확인). Windows용 ROCm 빌드는 Ollama의 Windows 목록보다 많은 라데온 세대를 대상으로 합니다. 릴리스 설정에는 RDNA 2(RX 6000), RDNA 3, RDNA 4 칩이 모두 들어 있습니다. LLVM 프로세서 표에 따르면 `gfx1030`은 RX 6800~RX 6900 XT, `gfx1031`은 RX 6700 XT입니다. `gfx1200`과 `gfx1201`은 각각 RX 9060 계열과 RX 9070 계열입니다.

Windows의 Ollama는 RX 6000·RX 9000 계열을 Vulkan으로 돌립니다. 그러니 이 카드들에는 llama.cpp의 ROCm 빌드가 또 하나의 선택지입니다. 다만 아래 ‘어느 백엔드가 빠른가’에서 보듯, 공개 결과에서는 RX 9070 XT의 생성 속도가 Vulkan 쪽이 더 빨랐습니다.

인텔 쪽은 llama.cpp SYCL 문서가 Arc B580을 검증된 장치로, Windows 11을 지원 OS로 적어 둡니다. Windows용 패키지에는 필요한 oneAPI 라이브러리가 들어 있고, 인텔 GPU 드라이버는 따로 설치합니다. 릴리스에는 인텔 하드웨어용 OpenVINO 빌드도 있습니다. 다만 llama.cpp README는 이 백엔드를 아직 개발 중으로 표시합니다.

빌드를 풀고 그 폴더에서 PowerShell을 엽니다. 모델을 올리기 전에 빌드가 어떤 장치를 찾았는지 먼저 봅니다. 둘째 줄은 16GB 카드에서 gpt-oss-20b를 돌릴 때 CanRun 조합 페이지가 보여 주는 명령입니다. Linux에서는 그 폴더에서 `./llama-server`로 실행합니다.

```powershell
.\llama-server.exe --list-devices
.\llama-server.exe -hf ggml-org/gpt-oss-20b-GGUF:MXFP4 -c 8192 -ngl all -fa on
```

`--list-devices`에 GPU가 하나도 나오지 않으면 그 빌드는 내 카드를 쓰지 못합니다. 그럴 때는 Vulkan 빌드를 받아 다시 해 보세요. 장치가 여러 개 나오면 `-dev`에 목록에 나온 내 카드 이름을 붙여 고릅니다(예: `-dev Vulkan1`). CPU에 들어 있는 라데온 내장 그래픽이 함께 잡힐 때가 그렇습니다.

### LM Studio

LM Studio는 llama.cpp 엔진을 CPU·CUDA·Vulkan·ROCm·Metal용 런타임으로 나눠 제공합니다. Ctrl+Shift+R로 런타임 탭을 엽니다. 라데온이면 Vulkan이나 ROCm 런타임을, Arc면 Vulkan 런타임을 고릅니다.

### 어느 백엔드가 빠른가

CanRun 계산에는 백엔드가 들어가지 않습니다. 라데온·Arc의 dense 모델 효율 값은 Vulkan으로 잰 공개 llama-bench 결과에서 나왔습니다. llama.cpp의 공개 성능 모음을 보면 Llama 2 7B 기준으로 대강의 답이 나옵니다. RX 9070 XT에서는 Vulkan의 생성 속도가 ROCm보다 30%쯤 빨랐습니다. RX 7900 XTX에서는 10%쯤 빨랐습니다. 프롬프트 처리 속도는 두 카드 모두 비슷했습니다.

다만 서로 다른 빌드와 PC에서 잰 결과이니, 내 카드에서는 직접 재 보세요. 같은 GGUF를 빌드마다 올리고, 답이 끝날 때마다 llama-server가 찍는 `eval time` 줄을 비교합니다. 무엇을 비교할지는 ‘<GuideLink slug="tokens-per-second" />’ 가이드에 있습니다. gpt-oss-20b를 ROCm으로 잰 공개 결과는 아래 ‘이 숫자는 얼마나 확실한가’에서 다룹니다.

## 같은 VRAM, 다른 속도 — RX 9070 XT와 RTX 5070 Ti, RX 7900 XTX와 RTX 3090

모델이 다 들어가면 생성 속도는 메모리 대역폭을 따라갑니다. 토큰 하나를 만들 때마다 활성 가중치와 KV 캐시를 VRAM에서 읽기 때문입니다. CanRun은 카드의 대역폭에 제조사별 효율 값을 곱해 속도를 추정합니다. 이 값은 공개 llama-bench 결과에 맞춰 정했습니다. 라데온 값은 NVIDIA보다 10% 가까이 높고, 인텔 Arc 값은 15%쯤 낮습니다.

### RX 9070 XT와 RTX 5070 Ti

대역폭은 RX 9070 XT가 <Num kind="bandwidth" gpu="rx-9070-xt" />, RTX 5070 Ti가 <Num kind="bandwidth" gpu="rtx-5070-ti" />입니다. 그래서 CanRun은 RX 9070 XT의 생성 속도를 RTX 5070 Ti의 80% 정도로 봅니다. ### Arc에서 돌리는 MoE 모델

CanRun 데이터에는 Arc 카드에서 MoE 모델을 잰 공개 결과가 없습니다. NVIDIA와 AMD 카드에는 MoE 모델용 효율 값을 따로 둡니다. 이 값은 dense 값의 3분의 2쯤입니다. Arc에는 MoE용 값이 없어서 dense 값을 그대로 씁니다. 그래서 B580의 MoE 추정치는 실제보다 높게 나올 수 있습니다. 이런 이유로 B580의 MoE 칸은 모델이 GPU에 다 올라가도 전부 이론 추정(±30%)입니다.

### Arc의 프롬프트 처리

B580의 약점은 프롬프트를 읽는 속도입니다. llama.cpp에 공개된 Llama 2 7B 결과가 있습니다. Vulkan으로 돌린 B580은 프롬프트 처리 속도가 CUDA로 돌린 RTX 3060 12GB의 3분의 1에 못 미쳤습니다. 생성 속도는 조금 느린 정도였습니다. llama.cpp SYCL 문서는 oneAPI 2026.1로 만든 빌드의 결과를 소개합니다. 이 빌드는 Arc B570에서 프롬프트를 세 배쯤 빨리 처리했습니다. 비교 대상은 oneAPI 2025.3 기반의 이전 릴리스 빌드입니다. Arc에서 긴 프롬프트를 자주 쓴다면 Vulkan과 함께 SYCL 빌드도 시험해 보세요.

## 라데온·Arc의 프롬프트 처리가 느린 이유

생성은 토큰을 하나씩 만들며 메모리를 읽습니다. 프롬프트 처리는 프롬프트 전체를 크게 묶어 한꺼번에 읽습니다. 그래서 메모리 대신 GPU 연산 성능이 속도를 정합니다. 자세한 원리는 ‘<GuideLink slug="tokens-per-second" />’ 가이드에 있습니다. 이 차이는 모델이 답하기 전에 읽을 내용이 많을 때 크게 느껴집니다. 긴 문서를 붙여 넣을 때, 캐시가 비워진 긴 대화를 이어 갈 때가 그렇습니다. 코딩 에이전트의 긴 지시문과 도구 설명을 읽을 때도 마찬가지입니다.

CanRun 조합 페이지는 모델이 GPU에 다 올라갈 때 프롬프트 처리 속도를 대략적 추정(±40%)으로 보여 줍니다. 카드의 FP16 연산 성능으로 계산하는 값입니다. AMD·인텔 카드는 연산 성능이 같아도 프롬프트 처리 속도를 NVIDIA 카드의 4분의 1쯤으로 잡습니다. 이 비율은 Vulkan 공개 결과를 바탕으로, RX 7900 XTX의 결과보다 조금 높게 잡은 값입니다. 이 추정에서 RX 9070 XT의 프롬프트 처리 속도는 RTX 5070 Ti의 절반을 조금 넘습니다. 생성 속도가 80% 정도인 것과 비교하면 차이가 큽니다.

공개 결과는 이 계산보다 높게 나온 것도, 낮게 나온 것도 있습니다. RX 9070 XT의 Vulkan 결과와 RX 7900 XT의 gpt-oss-20b ROCm 결과는 CanRun 값보다 높습니다. 반대로 RX 7900 XTX와 Arc B580은 CanRun 값보다 낮게 나왔습니다. 그러니 라데온·Arc 페이지의 프롬프트 처리 속도는 대략적인 범위로만 보세요. 긴 프롬프트가 중요하다면 직접 재는 편이 낫습니다. `ollama run`에 `--verbose`를 붙이면 `prompt eval rate`가 나옵니다. llama-server는 답이 끝날 때마다 `prompt eval time` 줄을 찍습니다.

## 이 숫자는 얼마나 확실한가

메모리 수치는 실제 GGUF 파일의 크기와 헤더, 모델이 공개한 설정값으로 공식에 따라 계산한 값입니다. 이 값은 제조사와 상관없이 같습니다. 그래서 어떤 모델이 들어가는지는 라데온·Arc 카드도 NVIDIA 카드와 똑같이 계산됩니다.

속도는 추정치라서 오차 범위와 신뢰 라벨을 붙입니다. ‘실측’은 그 카드·모델·양자화 조합의 공개 벤치마크 결과입니다. ‘보정된 추정’은 NVIDIA·AMD 카드에서 dense 모델을 GPU에만 올릴 때 ±12%입니다. MoE 모델, 부분 오프로드, 인텔 Arc를 포함한 그 밖의 하드웨어에서는 ±20%입니다. ‘이론 추정’은 ±30%입니다. 이 글에서는 전문가를 시스템 RAM에 둔 구성과 Arc B580의 모든 MoE 모델이 여기에 해당합니다.

라데온·Arc의 dense 모델 효율 값은 Llama 2 7B의 Vulkan 공개 결과에 기대고 있습니다. Llama 2 7B는 카탈로그에 없고, 위 표의 라데온·Arc 칸 가운데 공개 벤치마크 결과가 붙은 칸은 없습니다. MoE 모델은 llama.cpp의 gpt-oss 안내 토론 글에 gpt-oss-20b를 ROCm으로 잰 결과가 두 건 있습니다. 둘 다 llama-bench로 2k 컨텍스트에서 잰 값이고, CanRun이 직접 잰 값은 아닙니다. 카탈로그에 없는 RX 7900 GRE는 CanRun이 쓰는 것과 같은 MXFP4 파일로 쟀습니다. CanRun 계산식은 이 카드를 잰 값보다 10%쯤 빠르게 봅니다. <HubLink gpu="rx-7900-xt" /> 결과는 이보다 한참 느립니다. 이 결과를 올린 사람은 모델을 직접 변환했고, 그 파일은 전문가 밖 가중치를 16비트로 담고 있어 토큰마다 MXFP4 파일보다 메모리를 더 많이 읽습니다. 그래서 CanRun은 이 결과를 MXFP4 칸에 붙이지 않습니다. RX 7900 XT의 gpt-oss-20b는 보정된 추정으로 쾌적하게 돌아갑니다<Expect model="gpt-oss-20b" gpu="rx-7900-xt" verdict="S" confidence="calibrated" />. 파일 차이를 감안해도 이 결과는 CanRun 추정보다 낮습니다. 그러니 결과가 더 쌓이기 전까지는 라데온 카드의 MoE 속도 추정이 높게 나왔을 수 있다고 보세요.

표는 다음 조건을 가정합니다. Windows에서 그 카드로 화면을 출력하고, 시스템 RAM은 DDR5-5600 듀얼 채널 32GB입니다. 컨텍스트는 8k, KV 캐시는 f16입니다. 모델은 하나만 올리고 요청은 한 번에 하나씩 처리하며, 런타임은 llama.cpp 계열로 봅니다. ROCm·Vulkan·SYCL 같은 백엔드 차이는 계산에 들어가지 않습니다. 내 PC에서 실제로 어떻게 올라갔는지는 `ollama ps`의 PROCESSOR 열이 알려 줍니다.

본문의 판정은 8k 컨텍스트, f16 KV 캐시 기준입니다. Qwen3 14B·Qwen3 32B·gpt-oss처럼 생각 모드가 있는 모델에는 앞에서 말한 1.5배 높은 속도 기준을 적용합니다. 아래 기준표에는 이 배수가 반영되어 있지 않습니다.

## 자주 묻는 질문

### 라데온이나 Arc 카드로도 NVIDIA 카드와 같은 모델을 돌릴 수 있나요?

메모리 용량이 같으면 CanRun 계산으로는 같은 모델이 들어갑니다. 들어가는지는 카드가 쓸 수 있는 VRAM만으로 정해지기 때문입니다. gpt-oss-20b는 RX 9070 XT에도 RTX 5070 Ti처럼 GPU에 다 들어갑니다<Expect model="gpt-oss-20b" gpu="rx-9070-xt" fits="true" mode="full-gpu" /><Expect model="gpt-oss-20b" gpu="rtx-5070-ti" fits="true" mode="full-gpu" />. Qwen3 30B-A3B는 24GB인 RX 7900 XTX에도 RTX 3090처럼 다 들어갑니다<Expect model="qwen3-30b-a3b-2507" gpu="rx-7900-xtx" fits="true" mode="full-gpu" /><Expect model="qwen3-30b-a3b-2507" gpu="rtx-3090" fits="true" mode="full-gpu" />. 다만 속도와 소프트웨어 지원은 위에서 본 것처럼 다릅니다.

### Windows에서 Ollama가 라데온 RX 9000 계열을 ROCm으로 돌리나요?

아니요. 2026년 10월에 Ollama의 Windows ROCm 목록을 확인했습니다. 목록에는 RX 7000 계열 일곱 종과 Radeon PRO W7000 계열만 있습니다. 일곱 종은 RX 7600부터 RX 7900 XTX까지입니다. Windows의 Ollama는 RX 9070 XT·RX 9060 XT 같은 RX 9000 계열을 Vulkan으로 돌립니다. Vulkan은 기본으로 켜져 있습니다. Linux에서는 RX 9000 계열도 ROCm 목록에 있습니다. llama.cpp가 직접 내는 Windows용 ROCm 빌드는 RX 9000 계열 칩도 대상에 넣고 있습니다.

### ROCm과 Vulkan 중 무엇을 써야 하나요?

먼저 쓰는 도구가 내 카드에서 지원하는 백엔드로 시작하세요. 속도가 중요하다면 그다음에 직접 재 보면 됩니다. llama.cpp의 Llama 2 7B 공개 결과를 보면 생성은 Vulkan이 빨랐습니다. RX 9070 XT와 RX 7900 XTX 모두 그랬고, 프롬프트 처리 속도는 비슷했습니다. Ollama는 백엔드를 스스로 고르고, llama.cpp와 LM Studio는 빌드를 직접 고를 수 있습니다. CanRun 추정은 백엔드를 따지지 않아서 어느 쪽이든 같은 값입니다. 결국 같은 GGUF를 빌드마다 올려 보고, 찍히는 속도를 비교해야 답이 나옵니다. Arc라면 프롬프트가 길 때 SYCL 빌드도 함께 시험해 보세요.

### 메모리 대역폭이 같으면 라데온이 NVIDIA보다 빠른가요?

CanRun 계산으로는 생성 속도가 조금 빠릅니다. 라데온의 효율 값이 10% 가까이 높기 때문입니다. 그래서 Qwen3 32B는 RX 7900 XTX에서 쾌적하게, RTX 3090에서 원활하게 돌아갑니다<Expect model="qwen3-32b" gpu="rx-7900-xtx" verdict="S" /><Expect model="qwen3-32b" gpu="rtx-3090" verdict="A" />. 두 추정치가 생각 모드 기준선 양쪽에 걸쳐 있어서 생긴 차이입니다. Llama 2 7B 공개 결과에서는 RX 7900 XTX의 생성 속도가 RTX 3090보다 15% 남짓 빨랐습니다. 하지만 프롬프트 처리는 30% 가까이 느렸습니다.

### 12GB인 Arc나 라데온 카드로 14B 모델을 돌릴 수 있나요?

여기서 든 14B 모델은 Q4_K_M과 8k 컨텍스트라면 아슬아슬하게 들어갑니다. Arc B580에는 Qwen3 14B, Phi-4, HyperCLOVA X SEED Think 14B가 모두 GPU에 다 들어갑니다<Expect model="qwen3-14b" gpu="arc-b580" fits="true" mode="full-gpu" /><Expect model="phi-4" gpu="arc-b580" fits="true" mode="full-gpu" /><Expect model="hyperclovax-seed-think-14b" gpu="arc-b580" fits="true" mode="full-gpu" />. 여유가 가장 적은 것은 Phi-4이니 `ollama ps`로 확인하세요. CanRun은 12GB 카드라면 어느 카드든 같은 양을 빼고 계산합니다. 그래서 12GB 라데온에도 같은 모델이 들어갑니다. 16k로 늘릴 때는 KV 캐시를 q8_0으로 바꾸면 Qwen3 14B가 B580의 GPU에 다 들어갑니다<Expect model="qwen3-14b" gpu="arc-b580" ctx="16384" kv="q8_0" fits="true" mode="full-gpu" />.
