CanRun은 자주 바뀝니다. 새 모델이 들어오고, 계산기에 기능이 붙고, 계산이 틀린 부분을 찾아 고치기도 합니다. 이 페이지에는 사이트를 쓰면서 느낄 만한 변화를 최신순으로 적었습니다. 그 아래에는 모델마다 카탈로그에 들어온 날짜를 모아 두었습니다. 지금의 계산 방식은 <SiteLink to="/methodology">계산 방법</SiteLink> 페이지에서 볼 수 있습니다.

## 바뀐 기능과 고친 계산

<Update id="sparse-linear-hybrid">

### 희소 어텐션과 선형 어텐션을 섞은 모델도 계산합니다

<SiteLink to="/model/glm-5.3-flash">GLM-5.3 Flash</SiteLink>는 선형 어텐션 층과 희소 어텐션 층을 섞은 모델인데, 이제 이 구조도 계산하고 KV 캐시는 희소 어텐션 층에만 셉니다. 그래서 컨텍스트가 길어져도 메모리가 크게 늘지 않고, 그날 8k 컨텍스트에서 M3 Ultra 512GB는 Q4_K_M 파일이 GPU에 전부 올라가지만 256GB는 Q2_K 파일만 올라간다고 계산됐습니다. 이 모델의 GGUF 파일은 Q4_K_M을 llama.cpp가 같은 형식에 붙이는 짧은 이름 Q4_K로 적어 두는데, 파일 이름에 Q4_K_M이 없어도 헤더로 형식을 확인한 뒤 Q4_K_M 행으로 읽고 명령에는 파일 이름의 태그를 그대로 씁니다. 요청 슬롯마다 선형 어텐션 상태를 따로 잡기 때문에, llama-server가 기본으로 여는 슬롯 4개로는 추정보다 메모리가 더 들어서 이 모델의 llama.cpp 명령에는 `-np 1`을 붙였습니다. 이 모델이 층마다 더 하는 연산은 속도식에 들어 있지 않고 최근 llama.cpp 빌드로 잰 공개 결과도 추정보다 느렸기 때문에, 모든 조합을 이론 추정으로 표시합니다.

</Update>

<Update id="compressed-attention">

### 압축 어텐션 모델도 계산합니다

<SiteLink to="/model/deepseek-v4-flash-0731">DeepSeek V4 Flash 0731</SiteLink>은 층마다 KV 캐시를 여러 토큰씩 묶어 압축해 저장하는 모델인데, 이제 이 구조도 계산하고 모델 페이지에 압축 어텐션이라고 표시합니다. llama.cpp는 이 캐시를 요청 슬롯마다 따로 잡기 때문에, KV 캐시는 슬롯 하나 기준으로 세고 이 모델의 llama.cpp 명령에도 슬롯을 하나만 여는 `-np 1`을 붙였습니다. 그날 8k 컨텍스트에서 M3 Ultra 256GB는 MXFP4 파일이 GPU에 전부 올라간다고 계산됐습니다. Q4_K_M 파일이 없는 GGUF 저장소는 이제 MXFP4를 기준 양자화로 쓰며, 계산기에서 Hugging Face 모델을 불러올 때도 마찬가지입니다. 이 모델이 층마다 더 하는 연산은 속도식에 들어 있지 않고 지금 llama.cpp 빌드로 잰 공개 실측 한 건도 추정보다 느렸기 때문에, 모든 조합을 이론 추정으로 표시합니다.

</Update>

<Update id="looped-layers">

### 같은 층을 되풀이해 쓰는 모델도 계산합니다

<SiteLink to="/model/nanbeige4.2-3b">Nanbeige4.2 3B</SiteLink>는 토큰마다 같은 가중치로 22개 층을 두 번 지나는 모델인데, 이제 이 구조도 계산합니다. llama.cpp는 지날 때마다 KV 캐시를 따로 두기 때문에, 긴 컨텍스트에서는 작은 모델인데도 훨씬 큰 모델만큼 KV 캐시 메모리가 듭니다. 그래서 8GB인 RTX 4060에서 32k 컨텍스트의 Q4_K_M은 부분 오프로드로 계산됐습니다. llama.cpp는 지날 때마다 층을 따로 세므로, 모델 일부를 CPU에 두는 명령에서는 `-ngl` 값이 층 수보다 큽니다. 속도는 되풀이하는 층을 두 번 읽는다고 보고 계산하는데, 근거가 공개 실측 한 건뿐이라 이 모델은 모든 조합을 이론 추정으로 표시합니다.

</Update>

### K2-Horizon 두 모델을 계산합니다 — 값 전문가(MoVA) 구조 반영

llama.cpp가 K2-Horizon을 지원하면서 <SiteLink to="/model/k2-horizon-7b">K2-Horizon 7B</SiteLink>와 <SiteLink to="/model/k2-horizon-mova-36b-a4b">K2-Horizon MoVA 36B-A4B</SiteLink>를 계산할 수 있게 됐습니다. CanRun도 같은 자리에 두고 계산해 보니, 8k 컨텍스트의 Q4_K_M은 8GB인 RTX 4060에서는 MoE 전문가를 RAM에 두어도 들어가지 않아 CPU 전용으로 계산됐고, 16GB인 RTX 5060 Ti에서는 MoE 전문가를 RAM에 두고 '원활'로 나왔습니다. 그래픽카드에서 돌릴 때의 속도는 토큰마다 고른 값 전문가만 읽는다고 보고 계산하지만, 공개 벤치마크가 아직 없고 값 전문가를 고르는 데 드는 짧은 시간도 따로 세지 않아서 이 모델은 모든 조합을 이론 추정으로 표시합니다.

### 프롬프트 처리 추정이 모델 크기를 반영합니다

조합 페이지의 프롬프트 처리 추정은 그래픽카드마다 7B 모델에 맞춘 값 하나여서, 같은 카드면 1B 모델과 70B 모델의 프롬프트 처리 속도가 같게 나왔습니다. 이제 이 값을 모델 크기로 나누고, MoE 모델은 한 번에 읽는 프롬프트 토큰이 전문가마다 나뉘는 만큼 활성 파라미터보다 큰 모델처럼 계산합니다. 최근 llama.cpp 빌드로 잰 공개 벤치마크 91건에 맞추면서 NVIDIA·AMD·Strix Halo의 계수도 다시 정했고, 라데온 카드는 AMD가 밝힌 FP16 행렬 연산 성능(RX 9000 시리즈는 보통 쓰는 FP16 값의 두 배)을 씁니다. <SiteLink to="/gpu/rtx-4090">RTX 4090</SiteLink>에서 Qwen3 32B는 예전 값의 4분의 1이 조금 안 되게, Llama 3.2 1B는 5배쯤으로 바뀌었고, <SiteLink to="/gpu/nvidia-dgx-spark">DGX Spark</SiteLink>에도 이제 프롬프트 처리 추정이 나옵니다. 생성 속도와 판정은 그대로입니다.

</Update>

<Update id="strix-halo-speed">

### Strix Halo 속도 추정을 고쳤습니다

<SiteLink to="/gpu/amd-strix-halo">Ryzen AI Max+ 395(Strix Halo)</SiteLink>의 효율 계수는 근거가 분명하지 않은 예전 값이어서, 지금 llama.cpp 빌드에서 dense 모델 속도를 낮게 잡았습니다. 지금 빌드의 Vulkan 공개 결과에 계수를 다시 맞추고, MoE 모델에서 전문가마다 드는 고정 시간도 함께 다시 맞췄습니다. dense 모델은 4분의 1쯤 빨라졌고, Qwen3 8B 같은 8B 모델은 ‘원활’에서 ‘쾌적’으로 바뀌었습니다. MoE 모델은 많게는 5분의 1쯤 바뀌었는데, gpt-oss-20b처럼 빨라진 모델도 있고 Qwen3 30B-A3B처럼 조금 느려진 모델도 있습니다. 계수는 Vulkan 백엔드 기준이고, 같은 기기로 비교한 공개 결과에서 ROCm은 3~12% 느렸습니다.

</Update>

<Update id="moe-fixed-cost">

### MoE 모델 속도 추정을 고쳤습니다

MoE 모델의 속도는 하드웨어 종류마다 따로 정한 효율 계수로 추정했고, 토큰마다 읽는 양에서 공유 층을 대부분 빠뜨렸습니다. 이제 읽는 양은 파일 헤더로 세고, 층마다 전문가 하나를 돌릴 때 드는 고정 시간을 최근 llama.cpp 빌드의 공개 벤치마크에 맞춰 따로 더합니다. 최상위 NVIDIA 그래픽카드의 작은 MoE 모델은 이제 일정한 상한에 묶이지 않고, 맥의 큰 MoE 모델은 전보다 빠르게 나옵니다. Q4_K_M 기준으로 24GB <SiteLink to="/gpu/apple-m4">애플 M4</SiteLink>의 gpt-oss-20b는 ‘원활’에서 ‘쾌적’으로 바뀌었습니다. 8GB 그래픽카드에서 전문가를 시스템 RAM에 두는 조합 몇 개는 ‘겨우 가능’에서 ‘원활’로 바뀌었습니다.

</Update>

<Update id="apple-gpu-compute">

### 애플 칩의 연산 성능 값을 고쳤습니다

애플은 칩의 GPU 연산 성능을 밝히지 않는데, 그동안 보여 드린 값은 GPU가 FP16을 두 배 속도로 처리한다고 보고 FP32 이론값을 두 배로 잡은 것이었습니다. 애플 GPU는 FP16을 FP32와 같은 속도로 처리하므로, 이제 GPU·모델 페이지에는 위키백과 'Apple silicon' 표의 이론값이 그대로 나옵니다(전보다 절반쯤). 프롬프트 처리 계수는 이 값으로 같은 공개 벤치마크에 다시 맞춰서 추정이 7% 안쪽으로만 바뀌었고, 값이 없던 <SiteLink to="/gpu/apple-m5-ultra">애플 M5 Ultra</SiteLink>에도 이제 프롬프트 처리 추정이 나옵니다. 생성 속도와 판정은 그대로입니다.

</Update>

<Update id="apple-prompt-speed">

### 맥의 프롬프트 처리 속도 추정을 고쳤습니다

애플 칩의 프롬프트 처리 속도는 GPU 연산 성능에 계수 하나를 곱해 모든 칩을 추정했습니다. 그런데 M5 계열은 GPU 코어마다 행렬 연산 가속기가 들어 있어서 llama.cpp의 애플 공개 벤치마크에서 같은 연산 성능으로 이전 칩보다 프롬프트를 3배쯤 빨리 읽기 때문에, 계수 하나로는 M5 계열은 낮게, 나머지 칩은 높게 추정했습니다. 이제 M5 계열에는 따로 맞춘 계수를 써서 프롬프트 처리 추정이 70%쯤 올랐고, M4 계열과 Ultra 칩은 40%쯤 내려갔습니다. <SiteLink to="/gpu/apple-m5-max-40c">애플 M5 Max(40코어 GPU)</SiteLink>의 추정은 이제 그 벤치마크 결과와 가깝습니다. 생성 속도와 판정은 그대로입니다.

</Update>

<Update id="mixed-gpus">

### 서로 다른 그래픽카드를 함께 계산할 수 있습니다

'다른 GPU 함께 쓰기'를 누르면 같은 제조사의 데스크톱 그래픽카드를 모두 합쳐 4장까지 섞을 수 있습니다. RTX 3090과 RTX 3060 12GB를 함께 꽂은 구성이 한 예입니다. 메모리는 카드끼리 더해지지만, 토큰 하나가 카드를 차례로 거쳐 만들어지기 때문에 느린 카드가 전체 속도를 끌어내립니다. 빠른 카드 한 장에 모델이 다 들어가면 결과에서 그 점도 알려 드립니다. 섞은 구성의 결과는 늘 이론 추정(±30%)으로 표시합니다.

</Update>

<Update id="manual-model">

### 모델 값을 직접 넣어 계산할 수 있습니다

Hugging Face에서 불러올 수 없는 모델은 모델 카드나 config.json에 적힌 값을 넣어 계산할 수 있습니다. 전체 파라미터 수, 층 수, KV 헤드 수, 헤드 차원을 넣고, MoE 모델이면 활성 파라미터 수와 전문가 수도 넣습니다. 파일 크기는 파라미터 수로 어림하기 때문에 결과는 이론 추정으로 표시합니다. 계산은 브라우저 안에서만 이루어지고, Hugging Face에도 아무것도 요청하지 않습니다.

</Update>

<Update id="combo-ram">

### '이 GPU에서 이 모델' 페이지에서 시스템 RAM을 바꿔 볼 수 있습니다

모델이 그래픽카드에 다 들어가지 않으면 시스템 RAM 용량에 따라 판정이 달라집니다. 이런 페이지에 RAM 16GB부터 128GB까지 용량별 판정 목록을 붙였습니다. 용량을 고르면 판정 문장과 llama.cpp·Ollama 명령이 그 용량에 맞게 바뀝니다. RAM을 바꿔도 결과가 같은 페이지에는 그렇다고 적어 두었습니다. 계산기에서 넘어오면 계산기에서 고른 RAM 용량이 그대로 이어집니다.

</Update>

<Update id="gpu-weights">

### 그래픽카드 메모리는 실제로 카드에 올라가는 몫만 셉니다

llama.cpp는 모델의 입력 임베딩 표를 시스템 RAM에 둡니다. 일부 최신 모델에 들어 있는 MTP(다중 토큰 예측) 블록도 MTP를 켜지 않으면 불러오지 않습니다. 예전에는 이 두 부분까지 그래픽카드 메모리에 넣어 계산했지만, 지금은 GGUF 파일 헤더에서 크기를 읽어 뺍니다. 그래서 더 긴 컨텍스트까지 카드에 다 올라가는 모델이 생겼고, GeForce RTX 2080 Ti에서 HyperCLOVA X SEED Think 14B는 판정이 '원활'에서 '쾌적'으로 바뀌었습니다. 맥은 지금도 파일 전체를 셉니다.

</Update>

<Update id="hybrid-models">

### Mamba 같은 하이브리드 층이 섞인 모델도 계산합니다

최근 모델 가운데는 어텐션 층 사이에 Mamba2, 짧은 합성곱(short convolution), KDA 같은 층을 섞은 모델이 있습니다. 이런 층은 컨텍스트가 길어질수록 커지는 KV 캐시 대신 크기가 정해진 작은 상태만 들고 있습니다. 이제 이런 모델도 계산합니다. 목록에 있는 모델뿐 아니라 Hugging Face 주소로 불러온 모델에도 적용됩니다. Nemotron 3.5 Lightning 30B-A3B와 LFM2.5 2.6B, Ling-3.0 두 모델이 같은 날 카탈로그에 들어왔습니다.

</Update>

<Update id="thinking-mode">

### 생각 모드가 있는 모델은 모두 더 엄격한 속도 기준으로 판정합니다

답하기 전에 생각을 길게 쓰는 모델은 답 하나를 받기까지 토큰이 훨씬 많이 나와서, 속도 기준을 1.5배로 높여 판정합니다. 예전에는 저희가 리즈닝 모델로 분류한 모델에만 이 기준을 썼습니다. 이제는 공식 모델 카드와 채팅 템플릿을 보고, 생각 모드가 있으면 끌 수 있는 모델이라도 모두 높은 기준을 씁니다. Phi-4처럼 생각 모드가 없는 모델은 일반 기준으로 판정합니다. 이 변경으로 GeForce RTX 3060 12GB에서 Qwen3 14B처럼 판정이 '쾌적'에서 '원활'로 한 단계 내려간 조합이 있습니다.

</Update>

<Update id="krw-prices">

### 한국어 페이지에 원화 참고 가격을 함께 적습니다

한국어 GPU·모델 페이지와 '이 GPU에서 이 모델' 페이지, 계산기에서는 달러 가격 옆에 원화 금액을 함께 보여 드립니다. 미국 달러 가격을 유럽중앙은행(ECB) 기준환율로 단순히 환산한 참고값이라 국내 판매가와 다를 수 있습니다. 환율은 매주 갱신합니다. 가이드 본문과 영어 페이지에는 달러 가격만 나옵니다.

</Update>

<Update id="multi-gpu">

### 같은 GPU 여러 장을 계산할 수 있습니다

계산기의 'GPU 수' 설정으로 같은 그래픽카드 2~4장 구성을 계산할 수 있고, 메모리는 카드 수만큼 늘어납니다. llama.cpp 기본 방식처럼 층을 나눠 올리면 카드가 토큰마다 차례로 일하기 때문에, CanRun 계산에서는 생성 속도가 빨라지지 않습니다. 이 기능을 추가했을 때 계산해 보니, 8k 컨텍스트에서는 GeForce RTX 3090 두 장에 Llama 3.3 70B Q4_K_M이 다 들어갔고 16k에서는 일부가 시스템 RAM으로 넘어갔습니다. 여러 장 구성은 공개 벤치마크 결과를 계산에 연결하지 않아 결과를 이론 추정(±30%)으로 표시합니다. GPU·모델 페이지와 '이 GPU에서 이 모델' 페이지는 지금도 그래픽카드 한 장을 기준으로 합니다.

</Update>

<Update id="hf-models">

### 목록에 없는 모델도 Hugging Face 주소로 계산합니다

계산기의 '목록에 없는 모델'에 Hugging Face 모델 주소나 이름(예: Qwen/Qwen3-4B)을 넣으면 같은 방식으로 계산합니다. 모델 설정과 파일 목록은 브라우저가 Hugging Face에서 직접 읽어 옵니다. MoE 모델처럼 필요한 경우에는 GGUF 파일 앞부분도 읽어 구성 요소의 크기를 잽니다. 이미 목록에 있는 모델이면 그 모델의 결과 카드로 안내합니다. 불러온 모델의 결과는 이론 추정(±30%)으로 표시합니다.

</Update>

<Update id="moe-expert-placement">

### MoE 모델은 전문가를 GPU에 올릴 수 있는 만큼 올려 계산합니다

MoE(전문가 혼합) 모델이 그래픽카드에 다 들어가지 않으면 llama.cpp는 전문가 가중치를 시스템 RAM에 둘 수 있습니다. 이제는 카드에 들어가는 만큼 전문가를 올리고 나머지만 RAM에 두는 배치로 계산하는데, 요즘 llama.cpp와 Ollama가 스스로 나누는 방식과 같은 방향입니다. 명령어의 `--n-cpu-moe` 값도 이 배치를 따르고, 전문가 크기는 GGUF 파일 헤더에서 읽습니다. 예를 들어 GeForce RTX 4060 같은 8~12GB 카드에서 gpt-oss-20b는 판정이 '겨우 가능'에서 '원활'로 바뀌었습니다. 이 결과는 계속 이론 추정(±30%)으로 표시합니다.

</Update>

### MoE 모델 속도 추정을 바로잡았습니다

전문가를 시스템 RAM에 둔 MoE 모델의 속도를 그때까지 2.5배쯤 낮게 추정하고 있었습니다. 예전 식이 모든 토큰이 함께 쓰는 공유 가중치까지 RAM 속도로 읽는다고 계산했기 때문입니다. 이제는 토큰마다 고른 전문가만 RAM에서 읽는다고 계산하고, 새 추정은 공개 벤치마크 결과와 비교해 확인했습니다. 8~16GB 카드에서 Qwen3 30B-A3B를 돌리는 구성처럼 많이 쓰는 조합은 판정이 '겨우 가능'에서 '원활'로 올라갔습니다.

</Update>

<Update id="gemma4-kv">

### Gemma 4 모델의 KV 캐시 계산을 바로잡았습니다

Gemma 4 12B는 KV 캐시를 실제보다 4배, Gemma 4 26B-A4B는 2배 크게 잡고 있었습니다. 두 모델은 컨텍스트 전체를 보는 층의 KV 헤드 수와 헤드 크기가 설정 파일에 따로 적혀 있는데, 그 대신 슬라이딩 윈도 층의 값으로 계산했기 때문입니다. 값을 바로잡으면서 KV 캐시가 각각 4분의 1과 절반으로 줄어, 컨텍스트가 길수록 필요한 메모리가 더 많이 줄었습니다.

</Update>
