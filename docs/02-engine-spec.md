# 02. 계산 엔진 명세 (`@canrun/engine`)

> 순수 TypeScript 패키지. 부작용 없음, 브라우저/빌드 양쪽에서 동일 실행. **본 명세의 모든 상수는 2026-08-09 실측 대조 검증 완료** (§7). 상수 변경 시 반드시 출처 주석 + 테스트 갱신.

## 1. 입력/출력 타입 (요약)

```ts
type Hardware = {
  kind: 'dgpu' | 'unified' | 'cpu';
  os: 'windows' | 'linux' | 'macos';  // osReserve 산출·실행 커맨드 스니펫 분기 (PRD 입력 항목)
  vramGB?: number;            // dgpu
  memBandwidthGBs: number;    // 스펙 대역폭
  fp16Tflops?: number;        // pp 추정용
  fp16MatrixTflops?: number;  // pp 추정용 행렬 코어 FP16(dense) — AMD 가 따로 밝힌 값, 있으면 fp16Tflops 대신 (§3.5, 10-16 D91)
  ramGB: number; ramBandwidthGBs: number; // 시스템 RAM (cpu-moe/오프로드)
  unifiedUsableGB?: number;   // unified: GPU 가 쓸 수 있는 통합 메모리 — 기기 근거 값(데이터 `usableGBByRam`, 지금은 DGX Spark). 없으면 ram × 0.70 (§2.3, 10-23 D117 · 엔진 0.13.0)
  effClass: EffClass;         // 'nvidia'|'amd'|'intel-arc'|'apple'|'apple-ultra'|'strix'|'dgx-spark'|'cpu'
  effOverride?: number;       // 실측 누적 시 기기별 학습 계수 (Phase 2)
  isDisplayGpu?: boolean;     // OS 예약 차감 여부
  gpuCount?: number;          // dgpu: 같은 GPU 장수 (§6, D58)
  gpus?: GpuUnit[];           // dgpu: 카드 목록 1~4장, 서로 달라도 된다 (§6, 10-03 D67) — 있으면 장수·VRAM·대역폭·효율·화면 출력은 이것을 따른다
};
type GpuUnit = { vramGB: number; memBandwidthGBs: number; effClass: EffClass; effOverride?: number; isDisplayGpu?: boolean };
type ModelQuant = {
  paramsB: number; activeParamsB?: number;         // MoE면 active 존재
  fileGB?: number;                                  // 실제 GGUF 크기(있으면 최우선)
  quant: QuantId;                                   // bpw 폴백 계산용
  kvBytesPerToken: number;                          // 사전 계산값 (03-data-spec)
  attnType: 'full'|'swa'|'mla'|'hybrid'|'compressed'; // KV 스케일링 표시용 — compressed = 압축 어텐션(DeepSeek V4, 10-22 D115 · 엔진 0.12.1 — 표시 값만, 산식 무관)
  nonExpertGB?: number;                             // MoE: attention+shared 텐서 크기 (cpu-moe 판정)
  expertGB?: number;                                // MoE: 라우팅 전문가 텐서 (GGUF 헤더 실측 — 있으면 nonExpertGB 도 실측)
  activeExpertFrac?: number; moeLayers?: number;    // MoE: topK/experts, 전문가 층 수 (§3.3·§2.4-2)
  topK?: number;                                    // MoE: 토큰당 활성 전문가 수 — 토큰당 고정 시간(§3.1, 10-16 D88)
  offGpuGB?: number;                                // dense: 파일 중 그래픽카드에 안 올리는 GB (헤더 실측, §2.4-1 — 10-03 D62)
  pleGB?: number;                                   // dense: 층별 임베딩 표 per_layer_token_embd GB (헤더 실측, offGpuGB 안 — §2.4·§3.1, 10-21 D112)
  valueExpertGB?: number; valueExpertFrac?: number; // MoE: 값 전문가(MoVA attn_v_exps) GB (헤더 실측, nonExpertGB 안)·토큰당 비율 valueTopK/valueExperts — 읽기 바이트만 (§3.1, 10-21 D113 · 엔진 0.11.0)
  loops?: number; loopGB?: number;                 // dense: 반복 층 횟수(≥2 — Nanbeige4.2 num_loops)·반복 블록 GB(트렁크 blk.N.* 헤더 실측) — 읽기 바이트·부분 오프로드 KV 몫·pp 만 (§3.1·§3.4·§3.5, 10-22 D114 · 엔진 0.12.0)
  maxContext: number;
};
type Result = {
  verdict: 'S'|'A'|'B'|'F';
  mode: 'full-gpu'|'cpu-moe'|'partial-offload'|'cpu-only';
  vram: { weights: number; kv: number; buffer: number; osReserve: number; total: number; limit: number };
  tgTokS: { est: number; low: number; high: number };  // low/high = est × (1∓오차)
  ppTokS?: { est: number };
  confidence: 'measured' | 'calibrated' | 'theoretical';
  bestQuant?: QuantId;  // 요청 quant가 불가일 때 대안
};
```

### 2.2 KV 캐시 (토큰당 바이트)
기본식(GQA): `kvBytesPerToken = 2 × n_layers × n_kv_heads × head_dim × bytesPerEl`
- bytesPerEl: f16=2, **q8_0=1.07, q4_0=0.57** (KV quant 토글; V-cache quant는 FA 필요 — 2026 기본 on)
- **아키텍처 보정 (2026 필수, 값은 03의 모델별 사전 계산 필드에 반영)**:
  - SWA(Gemma 3/4, gpt-oss): 슬라이딩 레이어는 window(512~1024, gpt-oss 128)에서 상한 → 긴 ctx에서 KV 거의 평탄. full-attn 레이어만 ctx 비례.
  - MLA(DeepSeek V3/R1, Kimi K2): `(kv_lora 512 + rope 64) × layers × 2B` ≈ 69 KiB/tok 수준.
  - 하이브리드 리니어(Qwen3.5/3.6, Kimi K3): full-attn 레이어(전체의 ~1/4)만 KV + 상수 recurrent state.
  - **상수 상태 층 하이브리드(10-03 D63, D53 대체)**: Mamba2(Nemotron-H)·short-conv(LFM2)·KDA(Ling-3.0) 층도 하이브리드 리니어와 같이 컨텍스트와 무관한 고정 상태 — **KV 는 어텐션 층만** 계상하고 상태(모델당 ≤ ~75MB)는 미계상(연산 버퍼 근사 0.5GB+ 여유 안). llama.cpp 가 KV 를 두는 층: 기본 하이브리드 필터 `!is_recr(il)`(https://github.com/ggml-org/llama.cpp/blob/master/src/llama-memory-hybrid.cpp), Nemotron-H 는 전용 필터 `!is_recr(il) && n_ff(il) == 0` 으로 Mamba·MoE 전용 블록 제외(https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model.cpp).
  - **KDA+MLA 혼합(Ling-3.0)**: MLA 층에만 `(kv_lora_rank + qk_rope_head_dim) × 2B` — **V 캐시 없음**(`has_v = !is_mla`, https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp). MLA 층 = 변환기 `is_full_attention`(https://github.com/ggml-org/llama.cpp/blob/master/conversion/bailingmoe3.py) — nextn(MTP) 층 포함(BAILINGMOE3 는 nextn 층 필터가 없어 KV 를 둔다 — 보수 쪽). 예: Ling-3.0-flash 8 × 1152 = 9,216 B/tok.
  - **KV 공유 층(Gemma 4 E2B·E4B — 10-21 D112, 10-16 D98 보류 해제)**: 뒤쪽 `num_kv_shared_layers` 층은 KV 를 두지 않고 같은 종류의 앞 층 KV 를 다시 읽는다. llama.cpp 는 `n_layer_kv_from_start = 층 수 − 공유 층`(https://github.com/ggml-org/llama.cpp/blob/9a3b91c6801e68f412fcf1b6f8e153aa562b8536/src/models/gemma4.cpp#L8-L11), `has_kv(il) = il < n_layer_kv_from_start`(같은 커밋 src/llama-hparams.cpp#L321-L332), KV 캐시는 `has_kv` 인 층에만 할당한다(src/llama-kv-cache.cpp#L165-L169). 그래서 저장 KV = `layer_types[0 : 층 수 − 공유 층]` 안의 전체 어텐션 층 × kv 헤드 × global_head_dim × 4B — E4B 앞 24층 안 4층 × 2 × 512 × 4 = **16,384 B/tok**, E2B 앞 15층 안 3층 × 1 × 512 × 4 = **6,144 B/tok**(7층으로 세면 28,672·14,336). 슬라이딩 층은 다른 Gemma 와 같이 평탄 근사로 뺀다. gemma4_text 의 슬라이딩 층 지도가 있을 때만 계산하고, 다른 model_type 의 `num_kv_shared_layers`·`hidden_size_per_layer_input` 은 그대로 보류한다(llama.cpp 규칙을 확인한 구조만). 계산기 "HF 에서 불러오기"(카탈로그 밖)는 층별 임베딩 표 모델을 계속 받지 않는다 — 양자화 행마다 헤더 실측(pleGB)이 있어야 한다.
  - **값 전문가(MoVA — K2-Horizon MoVA 36B-A4B, 10-21 D113)**: MoE 층마다 V 투영을 값 전문가 64개 중 4개로 만들어 그 가중 합을 V 로 쓴다 — 토큰마다 `{n_embd_v_gqa}` 한 줄이라 표준 V 와 모양이 같고(https://github.com/ggml-org/llama.cpp/blob/4625240437c6821ee5c2da99e12d4817c6a8f07f/src/models/k2-horizon.cpp#L137-L211), KV 캐시도 표준 입력(`build_attn_inp_kv`, 같은 파일 #L225)이다. 그래서 KV 는 기본식 그대로(48층 × 8 × 128 × 4 = **196,608 B/tok**). 값 전문가 가중치의 배치는 §3.3(비전문가 — 늘 그래픽카드), 토큰당 읽기는 §3.1(고른 몫만 — 엔진 0.11.0), 남은 한계는 §9.
  - **반복 층(looped transformer — Nanbeige4.2 3B, 10-22 D114)**: 물리 층(`num_hidden_layers` 22)을 `num_loops`(2) 번 이어 돈다 — llama.cpp 는 논리 층 수를 `n_layer_all = 물리 층 × num_loops` 로 늘리고(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/models/nanbeige.cpp#L19-L32) 물리 가중치를 논리 층이 함께 가리키되 "each slot still has its own KV index"(같은 파일 #L66-L73), KV 캐시는 `n_layer_all` 을 돌며 층마다 K·V 를 만든다(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-kv-cache.cpp#L102 · #L165-L171, `has_kv` 기본 true — src/llama-hparams.cpp#L321-L332). 그래서 KV = 기본식의 층 수를 논리 층으로 — `layers × loops × kvHeads × headDim × 4` = 44 × 8 × 128 × 4 = **180,224 B/tok**(반복 없이 세면 90,112 — 8k 1.48 · 32k 5.91 · 128k 23.6GB, 13B급 dense 와 같은 크기). 전체 어텐션이라 `attnOverrides` 없이 `kvBytesPerTokenF16` 에 바로 들어가고, validateAll·sync-models 의 전체 어텐션 공식도 × loops 로 센다. 변환기는 반복 옵션 가운데 `num_loops`·`skip_loop_final_norm` 만 옮기므로(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/conversion/nanbeige.py#L13-L25) 원본 config 클래스의 LoopSplit(`enable_double_loop_split`·`loop_middle_layers`·`loop_share_kv`)·mHC·깊이 어텐션·n-gram 임베딩·비어 있지 않은 `loop_loss_weights`(원본은 그 길이 + 1 번 반복) 가 켜진 config 는 보류한다(`nanbeigeShape`). 가중치 읽기는 §3.1, 남은 한계는 §9. Ouro(`total_ut_steps` 4 — llama.cpp PR #29823 미머지)도 같은 필드로 표현되지만 본선 지원 전이라 계속 보류.
  - **압축 어텐션(CSA·HCA — DeepSeek V4 Flash 0731, 10-22 D115, attnType `compressed`)**: 층마다 `compress_ratios`(0·4·128)가 KV 저장 방식을 정한다. llama.cpp `llama_kv_cache_dsv4`(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-model.cpp#L3016-L3058)는 ① raw SWA 캐시(전 층, 창 `sliding_window` 128) ② CSA 압축 캐시(비율 4 층, 셀 = ceil(ctx/4)) ③ HCA 압축 캐시(비율 128 층, ceil(ctx/128)) ④ 라이트닝 인덱서 캐시(비율 4 층, 헤드 1 × `index_head_dim`) ⑤ 압축기 상태 3개를 두고, 모두 **K 만**(V 없음 — MLA 식, `dsv4_make_k_only`) 저장한다(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-kv-cache-dsv4.cpp#L18-L30 · #L887-L891 · #L1248-L1336, 압축 캐시는 256 셀 단위 패딩). 그래서 컨텍스트에 비례하는 KV(f16) = Σ층 비율 4 → (head_dim × kv + index_head_dim) × 2B / 4 · 비율 128 → head_dim × kv × 2B / 128 — V4 Flash(43층 중 CSA 21·HCA 20·raw 만 2, head_dim 512·KV 헤드 1·인덱서 128) **21 × 320 + 20 × 8 = 6,880 B/tok**(V3 MLA 의 약 1/10, 8k 0.056 · 128k 0.90 · 1M 7.2GB). llama.cpp 로그(https://github.com/ggml-org/llama.cpp/issues/27680 — ctx 64000·-ub 4096·bf16)의 CSA 16,128셀 × 21층 330.75 MiB · 인덱서 82.69 MiB · HCA 512셀 × 20층 10.00 MiB 와 층·셀당 1,024·256 B 로 일치하고, 세 캐시 합은 이 식의 64k 값과 1% 안이다(패딩). **이 값은 요청 슬롯 하나 기준이다**(10-22 D115 리뷰): llama.cpp 는 DSV4 캐시(raw SWA·CSA·HCA·인덱서·압축기 상태)를 통합 KV 모드여도 시퀀스마다 따로 잡는다(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-kv-cache-dsv4.cpp#L1247-L1248 · #L1291-L1333 — 텐서 = 셀 × 시퀀스 수, src/llama-kv-cache.cpp#L84 · #L233). `-np` 를 주지 않은 llama-server 는 슬롯 4개·통합 KV 로 뜨고 슬롯마다 n_ctx 를 받으므로(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/tools/server/server.cpp#L169-L173 · src/llama-context.cpp#L379-L380) 압축 KV·raw SWA·상태가 모두 4배가 된다 — 다른 모델은 슬롯들이 n_ctx 셀 하나를 나눠 써서 엔진 값과 같다. #27680 로그도 `-np 1`(`1/1 seqs`·`streams = 1`) 실행이고, 스니펫은 압축 어텐션 모델의 llama.cpp 명령에 `-np 1` 을 붙인다(`packages/data/src/snippet.ts` — 회귀 14 가 로그의 슬롯 수를 고정). **raw SWA 캐시와 압축기 상태는 컨텍스트와 무관한 상수**라 슬라이딩 층 평탄 근사처럼 빼고 연산 버퍼 근사(§2.3)에 맡긴다 — raw SWA 셀 = PAD(min(ctx, 창 + n_ubatch), 256)(https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-kv-cache-iswa.cpp#L73)라 기본 ubatch 512 면 768셀 × 43층 × 1KB ≈ 34MB, 상태 ≈ 12MB(로그 1.31 + 10.00 + 0.33 MiB)로 8k 연산 버퍼 근사의 1/10 아래다(-ub 4096 이면 raw SWA 191.6MB — §9). 스키마에 컨텍스트와 무관한 고정 상태 바이트 필드는 없다(Mamba2·KDA 상태도 같은 이유로 미계상 — 위 상수 상태 층 줄). 분류기 `deepseekV4Arch`(데이터 계층)는 DeepseekV4ForCausalLM 만, llama.cpp deepseek4 변환기·로더가 읽는 키 밖의 옵션이 켜지면 보류(비전 변형·MLA 키·앞쪽 dense 층·다른 점수 함수·0·4·128 밖 비율·KV 헤드 ≠ 1), 결과의 KV 근거는 `attnOverrides.sources` 에 남긴다(그 모델은 `attnOverrides` 필수 — validateAll). 본 GGUF 파일에는 MTP 블록이 없고(변환기가 기본으로 뺀다 — https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/conversion/deepseek.py#L579-L626), DSpark 투기적 디코딩 초안은 별도 `dspark-*.gguf` 라 계산에 넣지 않는다(파일 매칭도 보조 파일로 뺀다). `deepseek_v41_text`(V4.1)는 llama.cpp 본선 지원 전이라 계속 보류.
  - **KDA 선형 층 + DSA 희소 MLA·라이트닝 인덱서(GLM-5.3-Flash, 10-22 엔진 후속 ⑧-b, attnType `hybrid`)**: 45층 = KDA(순환 상태) 34층 + DSA 11층(3·7·…·43 — config `layer_types` 의 `deepseek_sparse_attention`). llama.cpp `llama_memory_hybrid_idx`(https://github.com/ggml-org/llama.cpp/blob/a37cc46104eb50900d5ab4a9ba02a0abdac039db/src/llama-model.cpp#L2883-L2926)는 ① 어텐션 캐시(DSA 층 — MLA 잠재 K 만, `n_embd_head_v_full = kv_lora_rank` · V 없음 `has_v = !is_mla` — https://github.com/ggml-org/llama.cpp/blob/a37cc46104eb50900d5ab4a9ba02a0abdac039db/src/models/glm5-next.cpp#L7-L59 · src/llama-kv-cache.cpp#L231) ② 순환 상태(KDA 층) ③ 인덱서 캐시(DSA 층 중 indexer full — 헤드 1, 행 폭 = `index_head_dim` × `indexer_kpool_row` 3 = key | gate | pooled, K 만 — https://github.com/ggml-org/llama.cpp/blob/a37cc46104eb50900d5ab4a9ba02a0abdac039db/src/llama-memory-hybrid-idx.cpp#L52-L74 · src/llama-hparams.h#L314)를 둔다. 그래서 KV(f16) = DSA 층마다 (kv_lora_rank + qk_rope_head_dim) × 2B + indexer full 인 DSA 층마다 index_head_dim × 3 × 2B — GLM-5.3-Flash 11 × (512 × 2 + 128 × 3 × 2) = **19,712 B/tok**(8k 0.16 · 128k 2.58 · 1M 20.7GB). ×3 은 config 가 아니라 llama.cpp 구현값이다(데이터 계층 `GLM5_NEXT_INDEXER_ROW_SLOTS` — 출처 URL). llama.cpp 메모리 로그(https://github.com/ggml-org/llama.cpp/pull/30499#issuecomment-6234771665 — n_ctx 262,144·`-np 1`·f16)의 MLA 2,816 MiB(층·셀당 1,024 B)·인덱서 2,112 MiB(768 B)와 정확히 같다(회귀 15). DeepSeek V4 와 달리 두 캐시는 표준 `llama_kv_cache` 라 통합 KV 면 슬롯들이 n_ctx 셀을 나눠 쓴다(KV 는 슬롯 수와 무관). **KDA 순환 상태**(층마다 head_dim² × 헤드 64 f32 = 4.19MB + conv 3 × (kernel − 1) × 8192 f32 = 0.29MB — https://github.com/ggml-org/llama.cpp/blob/a37cc46104eb50900d5ab4a9ba02a0abdac039db/src/llama-hparams.cpp#L208-L250, 34층 ≈ **153MB/시퀀스**, 같은 로그 582.25 MiB = 1 시퀀스 × (1 + rs_seq 3) 벌과 일치)는 컨텍스트와 무관하고 시퀀스마다 한 벌(`recurrent_rs_size = n_seq_max`)이라 다른 상수 상태 층(D63)처럼 미계상한다(기본 4슬롯이면 ≈ 0.61GB — 기존 상수 상태 층 하이브리드도 슬롯마다 같은 꼴로 미계상이다, §9). 스니펫이 이 모델의 llama.cpp 명령에 `-np 1` 을 붙이는 이유는 이 상태가 아니라 **인덱서 k-pool 연산 예약**이다: llama.cpp 가 풀 수를 최악 크기(셀 ÷ k-pool × n_seq_max)로 잡아 연산 버퍼가 슬롯 수 × 컨텍스트에 비례해 커진다(§9 ② — #29950. ggml-org 도 이 모델을 `-np 1` 로 띄웠다 — #30499). 표시는 모델 `arch.indexerKPool`(config `index_kpool` 4 — `LlamaCppPlan.singleSlot` 'pool', 10-22 ⑧-b 리뷰 — 처음엔 `arch.mhc` 로 붙이고 근거를 KDA 상태로 적었다). MoE 는 앞 3층 dense 뒤 42층(`arch.expertLayers` — `--n-cpu-moe` 블록 변환), mHC 는 llama.cpp 가 hc_mult 4 만 받는다(§4 ⑩). 분류기 `glm5NextArch`(데이터 계층)는 Glm5NextForConditionalGeneration 만, 변환기·로더가 읽는 키 밖의 옵션이 켜지면 보류(rope 를 쓰는 MLA·full 밖 indexer_types·k-pool 1·다른 점수 함수·그룹 라우팅 등), 본 GGUF 에 없는 MTP(nextn)는 결과 `offFileModules` 로 표시. 비전 인코더는 별도 mmproj, MTP 는 별도 `mtp-*.gguf`(ggml-org — 본 파일은 `--no-mtp` 변환)라 둘 다 계산에 넣지 않는다 — 단 llama-server `-hf` 는 mmproj 를 기본으로 받아 GPU 에 함께 올린다(§9 ⑤ — 카탈로그의 모든 비전 모델이 같다).
  - 엔진 입력은 그대로 `kvBytesPerTokenF16` 하나 — 위 산식은 데이터 계층(`packages/data/src/hf.ts` classifyArch → `attnOverrides`)이 계산한다. **계속 보류**: nanbeige 밖의 반복 층(Ouro total_ut_steps — 본선 미지원), 디스크에서 읽는 n-gram·PLE 임베딩(Qwen3.8-Flash-Next — 4GiB 를 넘어 TENSOR_READ_LAZY 로 행만 읽는 표), deepseek_v4 밖의 압축 어텐션(`compress_ratios`)·deepseek_v4·glm5_next_text 밖의 하이퍼 커넥션(`hc_mult` > 1), 3진 가중치.
- 검증값: Llama-3.1-8B 128 KiB/tok(@16k f16 = 2.15GB), Qwen3-14B 160, Qwen3-32B 256, 70B 320, Qwen3-30B-A3B 96. **7종 전수 일치** (§7).

### 2.3 오버헤드·사용 가능 메모리
```
computeBuffer = 0.5GB + 0.3GB × (ctx/32k)      // llama.cpp 그래프·스크래치 근사
osReserve(kind, os, isDisplayGpu) = dgpu·display만 windows 0.6GB | linux 0.3GB — 그 외(headless·unified·cpu·macos) 0 (macOS는 unified ×0.70에 흡수)
usable(dgpu)   = vram − osReserve               // 여러 장(§6): Σ vram_i − 화면 출력 카드의 osReserve
usable(unified)= unifiedUsableGB ?? ram × 0.70  // 기기 근거 값이 있으면 그 값(DGX Spark — 아래), 없으면 macOS wired limit 기본(맥·Strix Halo). sysctl 상향 툴팁
usable(cpu)    = usableRam = ram − 4GB (OS)     // usableRam = 모든 kind의 시스템 RAM측 한도 (cpu-moe expert·partial CPU측·cpu-only)
                                                 // unified + unifiedUsableGB 면 min(ram − 4, unifiedUsableGB) — 같은 메모리라 CPU 경로도 OS 몫을 뺀 값을 넘지 않는다
```

**통합 메모리 기기 근거 값 (10-23 D117 · 엔진 0.13.0)** — ×0.70 은 macOS 의 기본 GPU 한도(wired limit) 근거라 Linux·CUDA 통합 메모리 기기(DGX Spark)에는 맞지 않는다(GPU 가 다른 프로그램과 같은 메모리에서 할당받는다 — 한도는 커널이 내준 메모리에서 OS·데스크톱이 쓰는 몫을 뺀 양). 그런 기기는 데이터 레코드의 구성별 값(`usableGBByRam` — docs/03 §1·§2, 출처는 레코드 sources)을 엔진 입력 `Hardware.unifiedUsableGB` 로 넘긴다. 맥·Strix Halo 등 값이 없는 기기는 산식·출력이 그대로다.
- **DGX Spark 128GB = 116.9GB**: 공개 부팅 로그 가운데 가장 낮은 가용량 — DGX OS 7.5.0(커널 7.0, Kexec HandOver 로 예약이 늘어난 상태) `Memory: 117,723,484K available` = 120.55GB(https://forums.developer.nvidia.com/t/dgx-os-7-5-0-ota-uefi-5-36-0acum027-7-2-gib-less-ram-available-at-boot/383222 — 같은 글의 커널 6.11 은 128.28GB·6.17 은 130.40GB, 인식 메모리 133,828,484 KiB. 글타래에 완화 업데이트가 배포 중이라는 답) − 데스크톱 기본 사용량 3.6GB("the actual usage is 3.6GB/128GB or 3.3Gi/119Gi" — https://forums.developer.nvidia.com/t/the-dgx-system-itself-takes-up-20gb-memory/350359) = 116.95 → 내림 116.9. 화면 예약(UEFI Display Reserved Memory 기본 2GB, 4GB 로 올릴 수 있음 — 2026-10 릴리스는 자동·모니터 없으면 512MB, https://docs.nvidia.com/dgx/dgx-spark/release-notes.html)은 부팅 로그의 예약 안에 들어 있다고 본다 — 4GB 로 올리면 약 2GB 더 줄어든다
- **DGX Spark 64GB = 48.2GB**: 공식·공개 수치가 없다 → 128GB 판의 고정 몫(물리 128GiB 137.44GB − 120.55 = 16.89GB)과 데스크톱 3.6GB 를 64GiB(68.72GB)에서 그대로 뺀다 = 48.23 → 48.2. 메모리에 비례해 줄어드는 몫(페이지 구조체 등)까지 고정으로 본 보수값이다 — 비례로 줄이면 58.5, KHO 없는 6.17 커널 기준이면 58.1. 보도된 "가중치 + KV 약 56GB"(IT Home 인용 Guru3D — NVIDIA 확인 아님)보다 낮고 옛 ×0.70(44.8)보다 높다
- **대조(§7 회귀 16)**: 1대 공개 실측 — GLM-5.3-Flash UD-IQ2_XXS 101.84GB 를 깊이 65,536 까지 GPU 로(#30640), Qwen3-235B-A22B Q3_K_M 105GB "barely fits"(Classmethod b8012), DeepSeek V4 Flash 0731 UD-IQ3_S 116.1GB 가 1대 상한·UD-Q3_K_XL 128.2GB 는 안 들어감(Classmethod 2026-08-10, 컨텍스트 2,048). 116.9 로는 넷 모두 맞고(UD-IQ3_S 는 여유 0.27GB), ×0.70(89.6)으로는 1대에서 돈 셋이 GPU 에 안 들어간다
- **CPU 경로도 같은 한도**: 같은 메모리라 cpu-only 도 이 값을 넘지 않는다(ram − 4 = 124 로 두면 GPU 에 안 들어가는 116.9~124GB 구성이 CPU 로는 들어간다고 나온다 — 실제로는 같은 메모리가 모자란다). 그래서 DeepSeek V4 Flash 0731 Q2_K(8k 필요 118.0)는 DGX Spark 128GB 에서 CPU 전용 B → 불가가 된다(§9)

### 2.4 fit 판정 순서 (알고리즘)
정본은 `packages/engine/src/fit.ts` (불일치 시 코드 우선). 기본 ctx 8k, `need = resident + kv + buffer`, MoE 판정 = `activeParamsB`·`nonExpertGB` 둘 다 존재.
```
0. kind=cpu: 1~3 없이 곧바로 4 → 실패 시 5
1. full-gpu:  need ≤ usable(hw)  — dgpu vram−osReserve / unified ram×0.70 (통합 풀 전량 탑재도 full-gpu) → 최고 속도
   여러 장(§6): buffer = computeBuffer × 장수, usable = Σ vram_i − 화면 출력 예약, 물리 한도 limit = Σ vram_i.
   서로 다른 카드(10-03 D67)도 모든 카드에 나눠 올린다(llama.cpp 기본) — 빠른 카드 한 장에 들어가는 모델도 카드를 고르지 않는다
   resident(dgpu) = gpuResidentGBFor(mq) = weights − offGpuGB  (dense 헤더 실측)
                  | expertGB + nonExpertGB                       (MoE 헤더 실측 분할)
                  | weights                                      (실측 없음 — 보수)   … [0, weights] 로 묶음
   resident(unified·cpu) = weights (파일 전체)
   (10-21 D112, 엔진 0.10.0) 층별 임베딩 표가 있는 행(`pleGB`)은 dgpu 의 그래픽카드 밖 몫도 시스템 RAM 에 들어가야 한다:
   offGpu = weights − resident ≤ usableRam. 표가 없는 행은 검사하지 않는다(그 GPU 밖 몫 중 MTP 블록은 RAM 에도 올라가지 않는다 — D112 리뷰).
   층별 임베딩 표(PLE, `pleGB` — Gemma 4 E 계열)는 입력층이라 llama.cpp 가 늘 CPU 에 둔다(LLM_TENSOR_LAYER_INPUT,
   https://github.com/ggml-org/llama.cpp/blob/9a3b91c6801e68f412fcf1b6f8e153aa562b8536/src/llama-arch.cpp#L1031 · src/llama-model.cpp#L1684-L1686).
   표는 TENSOR_READ_LAZY 로 만들지만(src/models/gemma4.cpp#L59) 기본(auto) lazy 모드는 4GiB 넘는 텐서만 디스크에서 행을 읽어
   (src/llama-model-loader.cpp#L1094-L1098) Q4~Q8 표(1.3~3.0GB)는 시스템 RAM(mmap)에 있다 — 그래서 offGpuGB 에 들어 있고 파일의 37~55% 라
   RAM 이 작으면 못 올린다. 다른 행의 GPU 밖 몫(입력 임베딩·MTP·헤더)은 파일의 0~18%(최대 ling-3.0-flash Q8_0 3.69GB 중 MTP 3.27)라
   검사를 넣어도 계산기 최소 RAM 8GB(사용 가능 4GB)에서 걸리지 않지만, MTP 가 4GB 를 넘는 모델이 들어오면 잘못 떨어지므로 PLE 행에만 건다
   (10-03 D62, 엔진 0.6.0) llama.cpp 는 입력층(token_embd 등)을 항상 CPU 에 두고
   (https://github.com/ggml-org/llama.cpp/blob/cb7934c/src/llama-model.cpp#L1605-L1607), MTP/NextN 층은 load_mtp=false(기본)면
   TENSOR_SKIP 으로 할당하지 않는다(src/models/qwen35.cpp#L36-L38 · qwen35moe.cpp#L41,
   llama-model-loader.cpp#L1177-L1185, 기본값 llama-model.cpp#L2943, common/common.cpp#L1661 — `--spec-type draft-mtp` 일 때만 켬).
   exaone4(EXAONE 4.5)는 load_mtp 와 상관없이 NextN 층을 늘 TENSOR_SKIP 한다(exaone4.cpp#L39-L44 "not executed yet") — 켤 수 없음.
   임베딩 공유(tied) 모델은 출력층 사본이 GPU 에 가므로(llama-model-loader.cpp#L1161-L1168) 절감 0. 통합 메모리는 Metal 이 mmap 의
   [first,last] 범위를 백엔드 버퍼로 감싸(llama-model.cpp#L1856-L1870) 이 바이트가 GPU 범위에 들어갈 수 있어 파일 전체로 둔다.
   unified는 실패 시 곧바로 4 (2·3은 dgpu 전용)
2. cpu-moe (dgpu + MoE만): nonExpertGB + kv + buffer ≤ usable(dgpu) 이면, 남는 VRAM 에 전문가 층을 채운다 (10-01 D56)
   perLayer  = expertGB / moeLayers
   gpuLayers = clamp(floor((usable − nonExpert − kv − buffer) / perLayer) − CPU_MOE_GPU_LAYER_MARGIN(1), 0, moeLayers − 1)
   N(= --n-cpu-moe) = moeLayers − gpuLayers,  RAM 조건: perLayer × N + (weights − expertGB − nonExpertGB) ≤ usableRam
   → VRAM 상주 = nonExpert + GPU 전문가 + kv + buffer. moeLayers 가 없는 입력은 N = 전부(전문가 전량 RAM, 09-30 가정).
   llama.cpp b7410(2025-12-15, PR #16653) 이후 기본 `--fit on` 과 Ollama 0.30+(llama-server 위임)가 같은 방향으로
   자동 배치한다(비전문가 우선 → 남는 VRAM 만큼 전문가 층 → 나머지 층 전문가만 CPU). 12~16GB 카드로 30B~120B MoE 구동하는 표준 경로
3. partial-offload (dgpu + MoE 아님 — dense와 nonExpertGB 없는 MoE): kv+buffer는 GPU 상주, 가중치만 분할
   gpuW = min(resident, usable(dgpu) − kv − buffer)  // > 0 이어야 함. VRAM 이 모자라 1 이 실패했으면 gpuW < resident 라 상한은 그대로,
                                                     // RAM 이 모자라 1 이 실패한 경우(10-21 D112)만 상주 가중치에서 막힌다(그때 cpuW ≥ offGpu > usableRam 이라 여기서도 실패)
   cpuW = weights − gpuW ≤ usableRam
   gpuFrac = min(1, gpuW / (weights − pleGB))   … 속도 절벽 경고 (§3.4). 분모는 파일 − 층별 임베딩 표(처음부터 CPU·토큰마다 한 줄 — §3.1 의 읽기 바이트와
                                                  같은 기준, 10-21 D112). 표가 없는 모델은 파일 전체(입력 임베딩·MTP 포함 — 보수, §9)
   (c66f9ff 외부 리뷰 정정: 구식 need 비례식 gpuFrac = usable/need, cpuW = weights×(1−gpuFrac)는
    kv·buffer 일부가 CPU로 간다고 가정해 CPU측을 과소평가 → 거짓 양성. 반례 Qwen3-14B Q4·8GB GPU·RAM 7GB
    (usableRam 3GB — 구식 cpuW ≈2.9 탑재 / 정정 ≈3.5 불가)를 fit.test.ts 회귀로 고정)
4. cpu-only:  weights + kv ≤ usableRam   // MoE(nonExpertGB 有)는 2 실패 시 3을 건너뛰고 여기로
5. 전부 실패 → F. 더 낮은 quant 루프로 bestQuant 탐색 (IQ2_M까지):
   사다리 IQ2_M…Q8_0 중 요청 quant보다 bpw 낮은 것을 높은 품질부터, weights = paramsB×bpw/8
   (bpw 폴백 — 실파일 크기는 데이터 레이어 몫), MoE nonExpertGB도 같은 비율로 축소 → 0~4 첫 성공 quant.
   헤더 실측(offGpuGB·expertGB)은 요청 파일 전용이라 비운다 — 다른 quant 는 resident = weights(층별 임베딩 표도 GPU 몫으로 센다 — 보수).
   층별 임베딩 표는 구조라 pleGB 만 같은 비율(w / weights)로 줄여 남긴다(gpuFrac 분모용 — 10-21 D112)
   값 전문가(valueExpertGB — MoVA, 10-21 D113 · 엔진 0.11.0)도 구조라 같은 비율로 줄여 남긴다 — 출력에는 영향이 없다(사다리는 fitOnce 의
   fits 만 보고 quant 이름만 돌려주는데, fitOnce 는 이 값을 읽지 않는다 — 10-22 D114 리뷰에서 확인. 구조 보존용)
   반복 층 모델(`loops`)의 fit 은 반복이 없을 때와 같다 — 가중치는 한 벌만 상주하고, KV 는 데이터의 kvBytesPerToken 이 이미 논리 층 값이다.
   그래서 사다리도 loops·loopGB 를 건드리지 않는다(bestQuant 는 반복이 있든 없든 같다 — 10-22 D114 리뷰)
   네이티브(MXFP4·UD-*)·F16은 사다리 제외
```

## 3. 속도 모델

### 3.1 토큰 생성(tg) — 대역폭 지배
```
bytesPerToken = weightsReadGB + kvReadGB(ctx)
  dense: weightsReadGB = fileGB − pleGB          // 층별 임베딩 표(PLE)는 토큰마다 한 줄만 읽는다(get_rows, 입력층 — 10-21 D112). 표가 없으면 fileGB.
                         + (loops − 1) × loopGB  // 반복 층(10-22 D114 · 엔진 0.12.0): 반복 블록(트렁크 blk.N.* — 헤더 실측)을 토큰마다 loops 번,
                                                 // 입력 임베딩·출력층은 한 번. loopGB 가 없으면 (fileGB − pleGB) 전체를 블록으로(보수), loops 가 없으면 0.
                                                 // 블록은 [0, fileGB − pleGB] 로 묶는다. cpu-only 경로(§2.4-4)·부분 오프로드도 같은 바이트
  MoE:   weightsReadGB = nonExpertGB + expertGB × activeExpertFrac(= topK/experts)   // GGUF 헤더 분할(행 실측, 없으면 기준 양자화 유도 — §3.3)
                         − valueExpertGB × (1 − valueExpertFrac(= valueTopK/valueExperts))  // 값 전문가(MoVA, 10-21 D113 · 엔진 0.11.0) — 비전문가 안에 있지만 고른 몫만 읽는다.
                                                                                    // valueExpertGB 가 없는 모델은 0 을 뺀다(산식 그대로). 빼는 몫은 [0, nonExpertGB] 로 묶는다
         분할이나 비율이 없으면 fileGB × (activeParamsB / paramsB)                   // 10-16 D88 전의 식(공유 텐서 과소)
  kvReadGB(ctx) = kvBytesPerToken × ctx / 1e9                 // FA에서 전체 KV 읽음
dense: tg = eff × memBandwidthGBs / bytesPerToken
MoE(10-16 D88): t = bytesPerToken / (eff × memBandwidthGBs) + moeLayers × topK × MOE_EXPERT_OVERHEAD_US[effClass],  tg = 1 / t
  eff = 클래스 dense 계수(MoE 전용 계수 없음). 클래스 값이 없는 intel-arc 는 가장 큰 클래스 값(이론 추정 — §4)
  moeLayers·topK 가 없는 입력은 고정 시간 0(데이터 레이어는 늘 채우고, topK 가 없는 카탈로그 MoE 는 이론 추정으로 표시)
층별 임베딩 표 dense(10-21 D112 리뷰, 엔진 0.10.0): t = bytesPerToken / (eff × memBandwidthGBs) + PLE_TOKEN_OVERHEAD_MS[backend],  tg = 1 / t
  backend = cuda(nvidia·dgx-spark — PLE_CUDA_CLASSES) 1.35ms | vulkan(그 밖의 GPU 클래스 — Metal 은 실측이 없어 큰 쪽) 1.75ms
  GPU 경로(full-gpu, 부분 오프로드의 GPU 쪽, 통합 메모리 cpu-only 의 GPU 상한)만 — CPU 경로에는 더하지 않는다. pleGB 가 없는 모델은 0
여러 장(§6): eff × memBandwidthGBs 자리에 GPU 처리량 T 를 쓴다 (`gpuThroughputGBs`)
  같은 카드 N 장: T = eff × BW × MULTI_GPU_TG_FACTOR(1)
  서로 다른 카드(10-03 D67): T = MULTI_GPU_TG_FACTOR / Σ_i ( s_i / (eff_i × BW_i) ),  s_i = (vram_i − osReserve_i) / Σ_j (vram_j − osReserve_j)
```

**반복 층 읽기(looped — Nanbeige4.2 3B, 10-22 D114 · 엔진 0.12.0)** — llama.cpp 그래프는 논리 층 44개를 차례로 돌고(`for il < n_layer`, https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/models/nanbeige.cpp#L105), 반복 경계마다 `output_norm` 을 한 번 더 건다(#L164-L171). 같은 물리 텐서를 토큰마다 두 번 지나는데 사이에 다른 21층이 있어 캐시로 다시 쓰지 못하므로 반복 블록은 loops 번 읽고, 입력 임베딩(get_rows 한 줄)·출력층은 한 번이다. 반복 블록 = 행의 헤더 실측 `loopGB`(트렁크 `blk.N.*` 합 — `classifySplit` 의 blockGB, bartowski Q4_K_M 1.97GB · 출력층 Q6_K 0.42 · token_embd 0.29). 근거는 Llama 2 7B Q4_0 과 함께 한 댓글에 모은 Steam Deck(Vulkan) 같은 기기 표(빌드 b10360(48d22e295)은 Llama 2 단독 실행에만 적혀 있어 Nanbeige 행은 같은 빌드로 추정)의 같은 기기 비율 — 대역폭·클래스 계수가 비에서 지워진다(§7). 이 식(반복 블록 × 2 + 나머지 한 번)은 −2.6%(fa 1)·−0.6%(fa 0), 파일 한 번(반복 무시)은 +68~+71%, 파일 전체 × 2 는 −16~−14%, 반복 블록 × 2 + 출력층(token_embd 제외)은 +4.0%·+6.1% 였다(token_embd 는 토큰마다 한 줄이지만 지금 dense 식은 입력층을 따로 빼지 않는다 — 그 관례대로 둔 쪽이 실측에 더 가깝다). 배치(fit)·VRAM 은 바뀌지 않는다(가중치 한 벌). 새 상수는 없다. 대상 하드웨어 추정(Q4_K_M 8k, 이론 추정): RTX 4060 31.1 · RTX 3060 12GB 41.1 · RTX 5060 Ti 16GB 51.2 · RTX 5090 204.8 · M4 16GB 14.9 tok/s(반복을 아예 모르는 식 — KV 도 물리 22층 — 이면 4060 55.7 로 1.8배, KV 만 논리 층으로 세면 45.8 로 1.5배 높게 봤다).

**값 전문가 읽기(MoVA — K2-Horizon MoVA 36B-A4B, 10-21 D113 · 엔진 0.11.0)** — MoVA 층(앞 dense 3층 뒤 MoE 45층)은 V 투영 대신 값 전문가 64개 중 4개를 토큰마다 골라(`ggml_argsort_top_k`, https://github.com/ggml-org/llama.cpp/blob/4625240437c6821ee5c2da99e12d4817c6a8f07f/src/models/k2-horizon.cpp#L161) 그것만 곱한다(`build_lora_mm_id(layer.attn_v_exps, …, selected_experts)` 같은 파일 #L186 → `ggml_mul_mat_id`, https://github.com/ggml-org/llama.cpp/blob/4625240437c6821ee5c2da99e12d4817c6a8f07f/src/llama-graph.cpp#L1588-L1593). 라우팅 FFN 전문가와 같은 연산(같은 파일 #L2241·#L2355)이라 위 `expertGB × topK/experts` 와 같은 근거로 고른 몫만 읽는다고 본다. 값 전문가 텐서는 `--n-cpu-moe`·`--fit` 이 옮기지 않아 늘 그래픽카드에 있으므로 배치·VRAM(§2.4·§3.3)은 비전문가 그대로 두고, 읽기 바이트에서만 나머지 몫 `valueExpertGB × (1 − valueTopK/valueExperts)` 를 뺀다 — Q4_K_M 가중치 읽기 7.28 → 3.30GB, Q8_0 13.20 → 5.68GB. full-gpu, cpu-moe 의 GPU 몫, 통합 메모리 cpu-only 의 GPU 상한이 모두 이 값을 쓰고, 데스크톱 cpu-only 는 활성 슬라이스(파일 × 활성/전체 — 카드의 활성 4B 는 값 전문가를 고른 몫만 센 값)라 바뀌지 않는다. 새 상수는 없다. 값 전문가 라우팅·작은 행렬곱의 고정 시간은 더하지 않는다 — 공개 실측이 없고, 값 전문가 하나를 FFN 전문가 하나와 같은 고정 시간(45층 × 4 × 클래스 µs, 행렬곱이 셋인 FFN 전문가보다 실제로는 작을 것)으로 쳐도 추정이 2~17%(RTX 5090 full-gpu −17% · M4 Pro 48GB −6% · RTX 5060 Ti 16GB cpu-moe −4%) 낮아질 뿐이라 이론 추정 ±30%(§4 ⑧) 안이다.

### 3.3 cpu-moe 모드 속도
**10-01 개정(PROGRESS §4 D56, 엔진 0.4.0)** — 전문가 일부 GPU 배치. 토큰 시간 = RAM 몫 + GPU 몫 + MoE 고정 시간(직렬, 고정 시간은 10-16 D88):
```
routed = expertGB × activeExpertFrac(= topK / experts)              // 토큰당 읽는 라우팅 전문가
f      = N / moeLayers                                              // CPU 에 둔 전문가 층 비율 (§2.4-2 의 N)
t = routed × f / (CPU_MOE_RAM_EFF × ramBandwidthGBs)                 // CPU_MOE_RAM_EFF = 0.5
  + (nonExpertRead + routed × (1 − f) + kvReadGB) / (eff_gpu(dense) × memBandwidthGBs)   // nonExpertRead = nonExpertGB − valueExpertGB × (1 − valueTopK/valueExperts) (§3.1 — 값 전문가가 없으면 nonExpertGB)
  + moeLayers × topK × MOE_EXPERT_OVERHEAD_US[effClass]              // §3.1 — 10-16 D88 전에는 GPU 몫을 eff_gpu(moe) 로 읽고 고정 시간이 없었다
tg = min(1 / t, full-gpu 값)
```
- **입력 정의(GGUF 헤더 실측, 데이터 레이어 `model-quants.json` 행 필드)**: `expertGB` = 이름에 `_exps` 가 든 라우팅 전문가 텐서 합(트렁크 층만). 값 전문가 `attn_v_exps`(MoVA, 10-21 D113)는 빼고 `nonExpertGB` 에 넣으며, 그 크기를 `valueExpertGB` 로 따로 둔다(읽기 바이트에서 고르지 않은 몫을 빼는 데만 쓴다 — §3.1, 엔진 0.11.0) — llama.cpp `--cpu-moe`·`--n-cpu-moe`(LLM_FFN_EXPS_REGEX `\.ffn_(up|down|gate|gate_up)_(ch|)exps`, https://github.com/ggml-org/llama.cpp/blob/4625240437c6821ee5c2da99e12d4817c6a8f07f/common/common.h#L1225)와 `--fit` 자동 배치(common/fit.cpp#L618)가 FFN 전문가만 CPU 로 옮겨 값 전문가는 늘 그래픽카드에 있다. `nonExpertGB` = GPU 에 상주하는 나머지(어텐션·공유 전문가·라우터·출력층·dense FFN·`token_embd_norm`). llama.cpp 는 입력층(`token_embd`·`per_layer_token_embd`·`position_embd`·`token_types` — LLM_TENSOR_LAYER_INPUT)을 항상 CPU 에 두므로 제외한다. 다만 출력층이 없는 tied 모델은 GPU 에 출력층으로 복제되므로 포함한다. MTP·NextN 블록은 기본 로드가 아니라(`load_mtp=false` → TENSOR_SKIP) 둘 다에서 뺀다. 파싱 합계 = 파일 크기 ±0.02GB 로 33행 검증. `expertGB + nonExpertGB` 가 곧 full-gpu 의 그래픽카드 상주 가중치다(§2.4-1). dense 행은 같은 헤더 읽기로 `offGpuGB`(= 파일 − GPU 상주, 97행)를 둔다(10-03 D62).
- **실측이 없는 입력(bpw 사다리·엔진 단독 호출)**: `nonExpertGB` 는 기준 양자화에서 균등 bpw 로 유도한 값이다. 더 큰 양자화는 bpw 비율로 키우고 줄이지는 않는다(`nonExpertGBFor`). `expertGB` = 파일 − 비전문가. `activeExpertFrac` 도 없으면 09-30 식(`활성 슬라이스 − 비전문가` 를 전부 RAM 에서)으로 계산한다.
- **보정**: `CPU_MOE_RAM_EFF` = 0.5. 공개 실측에 N 을 적힌 그대로 넣고 맞췄다(η 0.45·0.55 보다 편향이 작다). 회귀 42점 기준으로 전체 평균 오차는 11.1%, 편향 −2.4%, ±20% 안 35점, 최대 39.7%다. NVIDIA(CUDA) 35점은 평균 10.3%, ±20% 안 89%, AMD ROCm 7점은 평균 14.9%, 최대 27.7%다. **10-16 D88**(GPU 몫 dense 계수 + 고정 시간): 42점 평균 11.1% 그대로, 편향 +0.1%, ±20% 안 35점, 최대 34.0% · NVIDIA 35점 평균 10.2%·±20% 안 89% · AMD 7점 평균 15.6%·최대 27.5% — 옛 GPU 몫 MoE 계수를 그대로 둔 것(평균 11.1%·최대 39.7%)보다 같거나 낫다. Vulkan(−31~+84%)·8채널 서버 RAM(CPU 연산 한계로 +30% 일관)·32k 이상 깊은 컨텍스트 서버 측정은 제외했다. 목록은 `packages/engine/test/fixtures.ts` `CPU_MOE_CASES`.
- **명령(데이터 레이어 `snippet.ts`)**: `-ngl all --n-cpu-moe N` 으로 추정과 같은 배치를 명시한다(명시하면 llama.cpp fit 의 가중치 배치는 꺼진다). **예외 — GPU 여러 장(같은 카드 D58·서로 다른 카드 D67, 10-03 정정)**: `-ngl`·`--n-cpu-moe` 를 빼고 `--fit`(b7410+ 기본)에 맡긴다(`LlamaCppPlan.ngl = 'auto'`). 층은 카드마다 남은 메모리 비율로 나뉘는데 `--n-cpu-moe N` 은 앞쪽 N 층만 CPU 로 보내므로, GPU 에 남는 전문가가 뒤쪽 층을 맡은 마지막 카드에 몰린다 — 엔진은 합산 용량만 보므로 그 카드가 메모리 부족이 될 수 있다. `--fit` 은 장치마다 여유(기본 1024MiB)를 두고 카드를 차례로 채운다(https://github.com/ggml-org/llama.cpp/blob/2145525a4081d66ff1a87cf43ef809f95a85ac0c/common/fit.cpp#L660-L750, 사용자가 -ngl·텐서 배치를 주면 멈춘다 #L463-L485). 계산기 카드가 이 명령과 각주("카드마다 1GB 남짓 비워 두고 알아서 나눠 올린다" — 화면 문구는 decimal GB)를 보인다. **전문가 층 단위 ≠ 블록 단위(10-03 D63)**: 라우팅 전문가가 일부 블록에만 있는 모델(데이터 `arch.expertLayers` — Nemotron-H 의 Mamba·어텐션 블록 사이 MoE 블록, Ling-3.0 의 앞쪽 dense 층)은 엔진 입력 `moeLayers` = 전문가 층 수(`expertLayers` 길이)이고, 명령 값은 엔진 N 번째 전문가 층까지 덮는 블록 수(`expertLayers[N−1] + 1`, `cpuMoeFlagLayers`)로 바꾼다 — `--n-cpu-moe` 가 "앞 N 블록"이라 그대로 쓰면 GPU 에 전문가가 더 남는다(Nemotron 실배치 기준 균등 근사 대비 최대 +1.03GB, 여유 1층 0.44GB 초과). 각주가 GPU 에 남는 층을 셀 때도 블록이 아니라 전문가 층으로 센다(`gpuExpertLayerCount` — 판정 문장과 같은 값). 각주 안내는 두 가지다. 메모리 부족 시 올릴 다음 값(전문가 층을 하나씩 더 RAM 으로 보내는 값 1~2개, `nextCpuMoeFlags` — 모든 블록에 전문가가 있으면 N+1·N+2, Nemotron 처럼 띄엄띄엄 있으면 전문가 없는 블록을 건너뛴 값), 그리고 b7410+ 는 두 옵션 없이도 자동 배치된다는 안내다. Ollama 0.30+ 는 자동 배치라 명령을 보여 주되 버전을 안내한다.
- **이력**: 09-30(D55)은 RAM 몫을 라우팅 전문가만으로 고쳤다(이전 ~2.5× 과소). 10-01(D56)은 전문가 일부 GPU 배치를 넣고, 실측 분할로 gpt-oss(유도 0.65/0.81 vs 실측 1.30/1.69GB)·UD 파일의 비전문가 과소를 해소했다. 이로써 D23 의 +1층 여유를 `CPU_MOE_GPU_LAYER_MARGIN` 으로 일반화했다.

### 3.4 partial-offload (dense) — 절벽 경고
`tg ≈ 1 / (gpuFrac/tg_gpu + (1−gpuFrac)/tg_cpu)` (조화 평균). gpuFrac < 0.9면 B등급 상한.
주의(10-03 D62): full-gpu 경계는 상주량(파일 − 입력 임베딩·MTP)으로 판정하지만 gpuFrac 분모는 파일 전체(층별 임베딩 표가 있는 모델만 파일 − 표 — 10-21 D112)라, 경계 바로 바깥 셀의 gpuFrac 상한은 `resident / file` 이다(Qwen3.5-9B Q4 0.872·Q8_0 0.862, MiniCPM5-1B 0.826, MiniCPM5-2B Q8_0 0.89 — 0.9 미만). 이런 모델은 S(full-gpu)에서 A 를 건너뛰고 B(cap-partial)로 바로 떨어진다. 실제로는 층 대부분이 GPU 에 있는 상태라 보수 쪽이며, 스니펫 `-ngl floor(gpuFrac × layers)` 도 그만큼 덜 올린다. 반복 층 모델(10-22 D114)은 `-ngl` 이 논리 층(층 × loops) + 출력층을 세고(`i_gpu_start = n_layer_all + 1 − ngl`, https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-model.cpp#L1670-L1695) 물리 가중치는 텐서의 블록 번호(0 ~ 층 − 1 — 첫 반복)로 장치를 고르므로(`dev_layer.at(tn.bid)` — 같은 커밋 src/llama-model.cpp#L2378-L2386, nanbeige 는 blk.0~21 만 만들고 논리 층이 가리키게 한다 — src/models/nanbeige.cpp#L48-L73) 물리 k 층을 GPU 에 두는 값 `layers × (loops − 1) + 1 + k`(k = floor(gpuFrac × layers))를 쓴다 — 그보다 작으면(Nanbeige `-ngl ≤ 23`) KV 일부·출력층만 GPU 에 가고 가중치는 하나도 가지 않는다. 그 값에서 GPU 에 가는 KV 는 논리 층 (layers × (loops − 1) + k) 개 몫이다(KV 는 논리 층마다 그 층의 장치 — 같은 커밋 src/llama-kv-cache.cpp#L216-L219). 메모리는 엔진의 부분 오프로드 가정(KV 전부 GPU)보다 작고(RTX 4060 32k: 엔진 7.40GB 가정 vs 그 명령 5.29GB — 보수), **속도는 그 배치대로 본다(엔진 0.12.0 — 10-22 D114 리뷰)**: 위 조화 평균은 KV 읽기도 gpuFrac 으로 나누지만 그 명령은 KV 의 ((loops − 1) + gpuFrac) / loops 쯤(4060 32k — 명령 27/44 = 0.61, 식 0.63)을 GPU 에 두므로, 반복 모델만 `t = gpuFrac × W/G + (1 − gpuFrac) × W/C + s × KV/G + (1 − s) × KV/C`(s = ((loops − 1) + gpuFrac) / loops — `partialKvGpuShare`, W = 가중치 읽기 §3.1, KV = kvRead, G·C = GPU·CPU 실효 처리량)로 셈한다. 가중치 몫은 gpuFrac 그대로 둔다(명령은 물리 k 층 + 출력층이라 조금 더 크다 — 보수). Q4_K_M: RTX 4060 32k 5.29 → 6.60 · RTX 3060 12GB 48k 6.48 → 8.25 · RTX 3050 8GB 32k 5.21 → 6.36 tok/s, Q8_0 4060 32k 3.72 → 4.42(판정은 모두 부분 오프로드 상한 B 그대로). 반복이 없는 모델은 식이 그대로다(바이트까지 같다). 단일 GPU 부분 오프로드 셀 중 floor(gpuFrac × 층) < 1 이라 명령이 `-ngl 0` 이 되는 셀(이 식이 맞지 않는 곳)은 없다(카탈로그 dGPU × RAM 8~128 × ctx 4k~256k × KV 3종 — 여러 장 1셀은 `--fit`, §9). GPU 가 여러 장이면 반복 모델 명령은 `-ngl` 을 빼고 `--fit` 에 맡긴다(§9 반복 층 ②). 분모를 상주량으로 바꾸는 안(판정 41건 변화)은 부분 오프로드 실측 검증이 없어 보류. UI에 "dense 모델 부분 오프로드는 급감" 고정 경고 + 실측 예시(gpt-oss-120b: 5090 naive 3.4 vs cpu-moe 9.6 tok/s).

### 3.5 프롬프트 처리(pp) — 연산 지배 (10-16 D91 개정, 엔진 0.9.0 — 모델 크기 반영)
```
ref   = ppCoef × TFLOPS                   // Llama 2 7B Q4_0 pp512 상당. TFLOPS = fp16MatrixTflops ?? fp16Tflops
x     = 실효 파라미터 / 6.74              // PP_REF_PARAMS_B (Llama 2 7B, llama-bench params)
pp    = ref × kq / (φ + (1 − φ) × x)      // φ = PP_FIXED_SHARE 0.05
실효 파라미터: dense = paramsB × (1 + (loops − 1) × loopGB / fileGB)   // 반복 층(10-22 D114)만 — 반복 블록은 토큰마다 loops 번 계산. 블록·파일이 없으면 × loops
               MoE   = activeParamsB × 1.9 × (64 / 전문가당 토큰)^0.35,  전문가당 토큰 = ubatch(512) × topK/experts
kq: dense K-quant·i-quant(Q2_K~Q6_K·IQ*·UD-*) 이고 Neural Accelerator 칩(M5 계열) 또는 strix 이면 0.6, 그 밖 1
```
- **왜 모델 크기로 나누나**: 프롬프트 처리 연산량은 토큰당 약 2 × 파라미터라 큰 dense 모델은 거의 반비례로 느려진다(4090 8B → 70B 실측 1/8.8 · 파라미터 비 8.8). 10-16 D89 까지의 식(`ppCoef × fp16Tflops`)은 GPU 마다 값 하나여서 1B·70B 가 같은 pp 를 보였다 — 같은 공개 실측 83점에서 MAE 92%·최대 +733%(D91).
- **고정 몫 φ**: 작은 모델은 모델과 무관한 토큰당 시간(어텐션·정규화·커널 실행) 때문에 파라미터 비만큼 빨라지지 않는다(4090 1B 는 8B 의 3.6배 — 비 6.5). 같은 빌드 1B·8B 쌍에서 φ 는 빠른 카드일수록 크다(4090 0.17 · 3090 0.09 · V100 0.08 · Apple ≈ 0). 하나로 둔 0.05 는 아래 MoE·양자화 계수와 함께 격자로 골라 전체 최대 오차가 가장 작은 값이다. 7B(x = 1)에서는 φ 와 무관하게 pp = ref 라 클래스 계수의 뜻(7B Q4_0 pp512 ÷ TFLOPS)은 그대로다.
- **MoE**: ubatch 의 토큰이 전문가에 나뉘어 전문가마다 작은 행렬곱이 되므로 활성 파라미터만큼 빠르지 않다. 전문가당 토큰이 적을수록(전문가가 많고 topK 가 작을수록) 더 느리다 — 같은 4090 에서 gpt-oss-20b(32·top-4, ub512 에서 전문가당 64토큰)는 8B dense 와 비슷하고 Qwen3.5-35B-A3B(256·top-8, 16토큰)는 8B 의 0.6배. 기준 64토큰(gpt-oss-20b·ub512)에서 배수 1.9, 지수 0.35. 전문가 비율(`activeExpertFrac`)이 없는 MoE 는 64토큰으로 본다. 엔진 기본 ubatch 512 는 llama-server·llama-bench·Ollama·LM Studio 의 기본값 — `ppEstimate(hw, mq, { ubatch })` 로 바꿀 수 있다(회귀는 출처의 -ub 를 넘긴다). gpt-oss 가이드의 `-ub 2048` 이면 MoE 는 추정보다 빠르다.
- **양자화 kq**: 행렬곱이 빠른 칩은 역양자화가 병목이라 K-quant 가 Q4_0·Q8_0 보다 느리다 — M5 Max 같은 빌드 Qwen3.5 27B Q4_K_M 356.52 vs Q8_0 721.19(0.49배), M5 Qwen3.5-9B Q4_K_M 은 식(Q4_0 기준)의 0.74배, Strix Halo Qwen3.8-27B Q5_K_XL 은 0.6배 안팎. MoE(mul_mat_id)는 같은 기기에서 Q4_K_M ≈ Q8_0 이라 dense 만. 그 밖의 클래스는 Q4_K_M 이 Q4_0 의 0.9~1.0배라 1.
- **클래스 계수 `PP_COEF`(10-16 D91)**: nvidia **154** · apple·apple-ultra **57**(D87 그대로) · M5 계열 `PP_COEF_NEURAL_ACCEL` **179**(D87 그대로) · amd **24.5**(행렬 FP16 기준) · strix **69** · dgx-spark **52**(새로 — 전에는 계수가 없어 DGX Spark pp 를 보이지 않았다) · intel-arc **35**(그대로, 지금 빌드 표준 모델 실측 없음). nvidia·amd·strix·dgx-spark 는 그 클래스의 회귀 11 점 전체(7B Q4_0 스코어보드 점 포함)에서 최대 오차를 가장 작게 하는 값(minimax) — 옛 nvidia 140 은 FA 끔·2025 빌드 값, strix 35 는 출처 없는 값(지금 Vulkan 7B 로 −39%)이었다. NVIDIA 는 카드마다 TFLOP 당 pp 가 147(4090)~198(5060) 로 퍼져 ±24% 가 클래스 값 하나의 한계다.
- **AMD 행렬 FP16(`fp16MatrixTflops`)**: 카탈로그 `fp16Tflops`(TechPowerUp FP16)는 RDNA4 에서 행렬 FP16 의 절반이다 — AMD 사양 "Peak Half Precision (FP16) Matrix Performance" 9070 XT 195 · 9070 145 · 9060 XT 103(카탈로그 97.3·72.3·51.3), RDNA3 7900 XTX 123 · 7900 XT 103 · 7800 XT 74.6(카탈로그와 같다). 카탈로그 값으로는 7B Q4_0 이 RDNA3 32/TFLOP·RDNA4 57~63/TFLOP 로 갈려 옛 35 가 9060 XT 를 −44%(±40% 밖)로 봤다. 행렬 값으로는 28~32 로 모인다(ROCm 도 같은 비). GPU 레코드 필드 → `Hardware.fp16MatrixTflops`(데이터 레이어 `dgpuHardware`·`hardwareConfigs`). 사양 표시는 fp16Tflops 그대로.
- Apple 의 두 계수는 토론 #4167 Llama 2 7B Q4_0 pp512 ÷ 카탈로그 fp16Tflops 로 정했다(10-16 D86 → D87) — M5 계열은 지금 빌드 162~202/TFLOP, 그 밖의 칩은 새 빌드 54.7~59.0(b1550 은 45~59). Apple 의 fp16Tflops 는 애플이 밝히지 않아 위키백과 'Apple silicon' 표의 FP32 이론값(ALU × 2 × 클럭, 클럭은 제3자 측정)을 쓴다 — 애플 GPU 는 FP16 FMA 처리량이 FP32 와 같다(M1·A15 실측 metal-benchmarks). D91 다모델 점에서도 Apple 은 ±35% 안이라(최대 +34.9% M5 gpt-oss-20b ub2048) 7B 실측에 묶은 값을 그대로 둔다 — 다모델 minimax 로 다시 맞추면 apple 62 · M5 165 로 최대 24% 가 되지만 7B 기준점이 ±15% 로 벌어진다. 칩별 #4167 실측에 직접 묶는 안(D89 보류)은 이번에도 보류 — 모양 오차(±25%)가 기준값 오차(평균 8%)보다 커서 이득이 작다.
- 표기는 "대략" 수준으로만(±40%) — P1-2부터 **범위 est×0.6~1.4 + 4번째 신뢰 라벨 `rough`(pp 전용, §4)**로 표시한다. D91 회귀 91점의 최대 오차는 34.9% 라 ±40% 를 유지한다(빌드에 따라 pp 가 빠르게 바뀐다 — CUDA MoE 는 2026 중반 +40%, Strix Halo 는 2026-02 → 10 사이 1.5배). 식이 fp16 연산 전제라 **full-gpu(통합 메모리 포함) fit일 때만** 표시하고 부분 오프로드·cpu-moe·cpu-only에선 생략(사유 한 줄). 밴드 상수는 데이터 레이어 정책(`packages/data` `PP_BAND = 0.4`, `// source: docs/02 §3.5 (policy)`) — 엔진 `Result.ppTokS`는 est만 반환(PROGRESS §4 09-29 D13). **짧은 프롬프트(pp512) 기준** — 문맥이 길어지면 어텐션 몫이 커져 느려진다(DGX Spark gpt-oss-20b pp2048 깊이 0 → 32k 에서 0.6배, benches/dgx-spark). 장문 RAG 유저용 참고치.

## 5. 판정 임계값 (ctx 8k, Q4_K_M 기준)
```
S: mode=full-gpu && tg ≥ 20
A: (full-gpu && 8 ≤ tg < 20) || (cpu-moe && tg ≥ 20)
B: 2 ≤ tg < 8 (모드 불문) || (cpu-moe && 8 ≤ tg < 20)
F: tg < 2 || 모든 quant 미탑재
```
부분 오프로드(§3.4): gpuFrac < 0.9면 B 상한, ≥ 0.9면 8 tok/s 이상에서 A까지(S는 full-gpu 전용) — `verdict.ts`가 정본.
근거: 20 tok/s ≈ 읽는 속도 상회(쾌적 체감), 8 ≈ 인내 가능, 2 미만 = 실사용 불가. 생각 모드가 있는 모델(`thinking` 필드 — 늘 생각·기본 켜짐·기본 꺼짐·자동. 끌 수 있어도 포함)은 사고 토큰 때문에 임계 ×1.5 상향(S ≥ 30 · A ≥ 12 · B ≥ 3 tok/s). 생각 모드가 없는 모델(phi-4 등)은 제외 — PROGRESS §4 D59(10-01, 옛 `category: reasoning` 기준 대체).
**판정 할인(데이터 레이어 — 10-22 ⑧-b 리뷰)**: 공개 실측 참고점이 **모두** 추정보다 느린 이론 추정 모델은 등급을 정할 때만 tg ÷ (1 + 할인)을 쓴다(`packages/data/src/assess.ts` `VERDICT_OVERESTIMATE` — 할인 = 참고점 가운데 가장 작은 과대 비율 min(추정 ÷ 공개 결과 − 1), 출처 URL). 표시 속도·범위·라벨은 엔진 값 그대로이고(엔진 산식·상수 무변경 — 스펙 버전 그대로), 실측이 조인된 결과에는 쓰지 않는다. 할인으로 등급이 낮아지면 사유 `cap-overestimate`(UI `VerdictReason.capOverestimate` — "표시된 추정보다 {pct}% 낮은 속도로 정했다"). ctx 계단·행렬(`estimateAt`)도 같은 규칙. 지금은 GLM-5.3-Flash 0.082 만(§7 — DGX Spark 64k +8.2%): 생각 모드라 쾌적 임계가 30 인데 M3 Ultra Q2_K 8k 추정 30.5 가 할인하면 28.2 로 원활(같은 칩 계열·같은 파일 M2 Ultra 참고점 +23.5% 로 보면 ≈ 24.7). ## 6. 멀티 GPU (베타 — 계산기만, 10-01 D58 · 10-03 D67)
같은 GPU N 장(`Hardware.gpuCount`, 2~4) 또는 카드 목록(`Hardware.gpus: GpuUnit[]`, 서로 다른 카드 — 10-03 D67, 엔진 0.7.0). usable = Σ vram − osReserve(화면 출력 카드 몫 — 같은 카드면 1장분), 연산 버퍼는 GPU 마다(×N), 물리 한도 = Σ vram.
층 나눠 올리기(llama.cpp 기본 `-sm layer`)는 층과 그 층의 KV 가 맡은 카드에만 있고 토큰이 카드를 차례로 지나므로 대역폭이 합산되지 않는다. `-ts` 가 없으면 카드마다 남은 메모리 비율로 층을 나눈다(입력층은 CPU, 출력층은 마지막 장치 — https://github.com/ggml-org/llama.cpp/blob/99b95488cac0f00ce3f05af113a8c1e287753f87/src/llama-model.cpp#L1558-L1616, 메인테이너 설명 https://github.com/ggml-org/llama.cpp/discussions/6046, 문서 https://github.com/ggml-org/llama.cpp/blob/b9afc19cb409be990784200ded9e007093beb607/docs/multi-gpu.md).
- **같은 카드**: tg = 단일 카드 식 그대로 × `MULTI_GPU_TG_FACTOR`(= 1). 카드 목록이라도 카드가 전부 같으면(`isUniformGpus`) 같은 연산이라 출력이 바이트까지 같다(fit.test 가 회귀 10점 전부에서 고정).
  - 근거(공개 실측 10점, `test/fixtures.ts` MULTI_GPU_CASES): 70B급 2~4장의 실효 대역폭은 카드 1장 피크의 75~90%(2×3090 16.57 · 2×4090 19.22 · 4×4090 21.25 tok/s) — 단일 카드 클래스 계수 0.70 보다 높아 추가 감속 없음이 10점 전부 보수 쪽(−22~0%, MAE ~12%). 같은 모델 1장 → N장 손실은 CUDA 최근 빌드 0~3%(A40 1→3장 동일).
  - 옛 표기 "단일 카드 계수 × 0.68" 은 근거(2×3090 70B 14~16 tok/s)를 잘못 옮긴 것 — 그 실측은 0.68~0.75 실효 계수에 해당한다(10-01 정정).
- **서로 다른 카드(10-03 D67)**: 토큰 1개 시간 = 카드별 (그 카드가 읽는 바이트 ÷ 그 카드 처리량)의 합 → GPU 처리량 T = factor / Σ s_i/(eff_i × BW_i), s_i = 남은 메모리 비율(§3.1). cpu-moe 의 GPU 몫·부분 오프로드의 GPU 쪽도 같은 T(넘치는 모드는 카드가 모두 차서 카드별 메모리 몫이 용량 비율에 가깝다 — 속도 배분은 근사). **대표 추정은 모든 카드에 나눠 올린 llama.cpp 기본 동작**이다 — 빠른 카드 한 장에 들어가는 작은 모델도 느린 카드에 몫이 가서 느려진다(3090 + 3060 × Qwen3 8B: 3090 한 장 105 → 두 장 68 tok/s). 그 카드만 쓰는 경우(`--device`)는 판정에 넣지 않고 계산기 카드의 참고 줄로만 보인다(데이터 레이어 `assessQuant` 로 카드 한 장 구성을 한 번 더 평가 — 계산기에 그 카드만 넣었을 때와 같은 값·라벨이라 8k·f16 이면 실측 조인, 엔진 무관. D67 리뷰 반영). 카드 부분집합을 고르는 안은 판정이 사용자 설정(`--device`)에 기대게 돼 버렸다(적대적 검토 — 기본값 실측 39.2 대 부분집합 추정 54.9, ±30% 밖).
  - 근거 3점(`test/fixtures.ts` HETERO_GPU_CASES, verify-regression 7): ① RTX 5070 Ti + RTX 3060 12GB, Gemma 4 31B Q4_K_M 18.81GB, CUDA `-ngl 99`·`-ts` 없음, tg128 실측 21.8 → 클래스 계수(nvidia 0.70) 추정 20.3, **−6.8%(보수 쪽)** (https://github.com/ggml-org/llama.cpp/discussions/21112) ② RTX 3060 12GB + Tesla P100 16GB, 카드별 단일 실측(9B 깊이 0: 3060 54.9 · P100 33.5 tok/s)으로 effOverride 를 맞추면 층 분할 9B 39.2 → 추정 40.2 **+2.6%**, 같은 처리량으로 27B(16.8GB) 13.81 → 13.6 **−1.5%** (https://github.com/kuraneko1/llama-split-bench/blob/272b0dee42afd60b823e769dd896630e6b13a402/examples/results-3060-p100.md) — 식만 검증, 클래스 계수 검증은 ①뿐.
  - 반례(범위 밖): RX 7800 XT + RX 580, Vulkan, Qwen3.6-35B-A3B Q4_K_M `-ts 28/15` tg128 48.59 — 클래스 계수 추정 약 112(+131%) (https://github.com/ggml-org/llama.cpp/discussions/22183). 2017년 카드·Vulkan 은 계수 표본 밖이고, P100 도 9B 단일 실측의 실효 계수가 약 0.26 으로 클래스 값 0.70 과 거리가 멀다.
  - **섞기 자격(데이터 레이어 정책, `canMixWith` — `// source: docs/02 §6 (policy)`)**: 두 카드 모두 카탈로그 데스크톱 dGPU · 같은 계열(nvidia 끼리 또는 amd 끼리 — `MIXABLE_GPU_CLASSES`) · FP16 크리플 아님(GTX 10 — 위 Pascal 반례). 제조사를 섞으려면 Vulkan 같은 다른 백엔드가 필요한데 그 계수는 표본 밖이다(같은 카드 여러 장도 Vulkan 은 −25%). 노트북·Arc·통합 메모리·CPU·커스텀 입력은 1번 카드가 될 수 없다. 합계 최대 4장(계산기).
  - **검증점이 없는 곳**: 서로 다른 카드의 MoE(전량 탑재·cpu-moe) 0점, AMD(ROCm) 0점, 3장 이상 0점. cpu-moe 는 `--fit` 이 dense 부분만 있는 층을 뒤에서부터 채운 뒤 앞쪽부터 전문가 층으로 바꿔(common/fit.cpp L660-L750) 토큰마다 읽는 바이트의 카드별 분포가 용량 비율과 다를 수 있고, 장치마다 비워 두는 1GiB 도 엔진은 모델링하지 않는다(cpuMoeLayers 가 낙관적일 수 있다).
- 공통: 실측 조인 없음(1장 기준 실측), 라벨은 이론 추정 고정. AMD·Vulkan 은 장수 손실 편차가 크다(7900 XTX ROCm −7.5%·Vulkan −25%). `-sm tensor`(2026-04, PR #19378)는 dense 1.2~2.3× — 모델링하지 않고 안내만(같은 카드). `-sm row` 는 CUDA 에서 제거(PR #24216). 허브·콤보는 1장 기준. 여러 장 cpu-moe 명령은 `--fit` 자동 배치(§3.3), 여러 장 반복 층 모델 명령도 `--fit`(물리 가중치가 앞쪽 카드에 몰린다 — §9 반복 층 ②, 10-22 D114 리뷰). pp(`ppEstimate`)는 1번 카드 값 그대로다 — 계산기는 pp 를 보이지 않는다(콤보 페이지는 1장).

## 9. 알려진 한계 (방법론 페이지에 공개할 것)
- **pp(§3.5, 10-16 D91)**: 짧은 프롬프트(pp512)·기본 ubatch 512 기준 — 문맥이 길어지면 어텐션 몫이 커져 느려지고(DGX Spark gpt-oss-20b 32k 에서 0.6배), `-ub 2048` 이면 MoE 는 추정보다 빠르다. llama.cpp 빌드에 따라 빠르게 바뀐다(CUDA MoE 2026 중반 +40%, Strix Halo 2026-02 → 10 사이 1.5배). NVIDIA 는 카드마다 TFLOP 당 pp 가 147(4090)~198(5060) 로 퍼져 클래스 값 하나로 ±24%. 회귀 밖: Intel Arc(지금 빌드 표준 모델 실측 없음), NVIDIA 노트북(카탈로그 TFLOPS 와 실측이 −39~+21% — 4060·5090 Laptop), Apple MoE 의 기본 ubatch(회귀 점은 전부 -ub 2048, 전문가당 토큰 지수로 외삽), 하이브리드 소형·카탈로그 밖 구조(qwen3next·MLA 는 M2 Ultra 에서 +50~+142%).
- **MoE 속도(§3.1, 10-16 D88)**: 읽는 바이트(헤더 분할)에 토큰당 고정 시간(MoE 층 × topK × 클래스 값)을 더한다 — 옛 근사(파일 × 활성/전체, 공유 텐서 과소)와 235 tok/s 캡을 대체했다. 남은 한계: ① 고정 시간은 클래스당 한 값이라 층당 연산이 많은 아키텍처(하이브리드 Qwen3.5/3.6·Gemma 4)와 적은 아키텍처(gpt-oss)의 차이를 ±20% 안에서만 흡수한다(2026 빌드 49점 최대 19.9%). ② 디양자화가 가벼운 Q8_0 은 같은 바이트를 dense 계수(Q4_0 7B 로 정한 값)보다 빨리 읽어 Q8_0 점은 모두 낮게(−6~−18%) 잡힌다. ③ apple-ultra 값은 M2 Ultra 실측뿐이라 M5 Ultra 는 낮게 잡힐 수 있다. ④ strix 값(14.3µs, 10-16 D90)은 Vulkan 기준이다 — 같은 빌드 ROCm 은 MoE 가 12%쯤, dense 가 3~10% 느리다. ⑤ 2025 빌드(gpt-oss 가이드 #15396 Apple)는 지금 식이 10~39% 높게 본다 — llama.cpp 를 오래 업데이트하지 않았다면 추정보다 느릴 수 있다. ⑥ CPU 경로(cpu-only)의 MoE 는 옛 바이트(파일 × 활성/전체)와 cpu MoE 계수 0.43 그대로다(CPU 실측 없음).
- LocalScore류 컨텍스트 가중 수치와 tg128 단문 수치는 조건이 다름 — 실측 수집 시 ctx 필드 필수.
- 열/전력 제한(노트북), 듀얼채널 미구성 RAM 등 사용자 환경 편차는 밴드로만 흡수.
- dGPU full-gpu 필요량은 그래픽카드 상주 가중치(파일 − 입력 임베딩·MTP 블록, GGUF 헤더 실측)로 계산한다(10-03 D62, 엔진 0.6.0 — 그 전엔 파일 전체). 남은 한계:
  - **MTP 를 켜면**(`--spec-type draft-mtp`, unsloth `*-MTP-GGUF` 행이 유도 — qwen35·qwen35moe 아키텍처만, 데이터 레이어 `MTP_LOADABLE_MODELS`) MTP 블록(`mtpGB`, Qwen3.6 Q4 0.90GB)과 MTP 컨텍스트 KV 가 더 든다 — 계산하지 않고 분해 바 각주로 안내한다. EXAONE 4.5(exaone4)는 켤 수 없어 "아직 안 쓴다"고만 쓴다. cpu-moe·부분 오프로드의 RAM 몫(파일 − GPU 가중치)에는 MTP 블록이 그대로 들어 있다(보수 — cpu-moe 각주가 밝힌다).
  - **llama.cpp `--fit`(Ollama 0.30+ 도 -ngl 없이 llama-server 를 띄워 같은 경로)** 은 장치마다 1024MiB 를 비워 둔다(https://github.com/ggml-org/llama.cpp/blob/cb7934c/common/common.h#L485). 16GB 이하 카드에서 새로 full-gpu 가 된 빠듯한 셀(예: 8GB × Qwen3.5-9B 32k 필요 6.99 vs 사용 가능 7.4)은 Ollama 에서 부분 오프로드가 될 수 있다(추정) — 가이드·방법론이 `ollama ps` 확인을 안내한다. `llama-server -ngl all` 은 vramGB 가 표기 용량(실제는 GiB — 8GB 카드 = 8.59 decimal GB)이라 여유가 있어 OOM 위험이 낮다.
  - **통합 메모리(맥)는 파일 전체**(Metal mmap 범위, §2.4-1) — 32GB 맥의 Qwen3.5/3.6-35B-A3B 는 여전히 cpu-only(보수).
  - **partial-offload gpuFrac 분모는 파일 전체**(§3.4 주의 — 층별 임베딩 표가 있는 모델만 파일 − 표) — 경계 바로 바깥이 B 로 떨어지는 절벽.
  - **속도는 여전히 파일 바이트**(§3.1 `bytesPerToken = fileGB`) — MTP 블록이 있는 dense 모델(Qwen3.5-9B/27B, Qwen3.8-27B, EXAONE 4.5)은 토큰마다 읽지 않는 MTP 바이트만큼 과소 추정(보수). `mtpGB` 를 쓰는 후속 과제.
  - 실측(llama-server 로그의 `CPU_Mapped model buffer` 에 token_embd, MTP `unused tensor … ignoring` 경고)으로는 아직 대조하지 못했다(하드웨어 없음 — PROGRESS §5).
- **압축 어텐션·하이퍼 커넥션(DeepSeek V4 Flash 0731, 10-22 D115)**: ① **과대 추정 경향** — 지금 빌드 공개 실측 1점(M2 Ultra Metal)이 추정보다 25% 느리다(§7). 층마다 mHC 혼합(sinkhorn 20회 × 2)·압축기·라이트닝 인덱서 연산이 MoE 고정 시간 식에 없다. 점이 다섯 개 이상·백엔드 둘 이상 모이면 층당 고정 시간 항(PLE 선례)을 검토한다 ② **긴 문맥 감쇠 과소** — 인덱서가 토큰마다 CSA 키 전체(ctx/4)를 훑어 llama.cpp 는 30k 에서 −19% 느려지는데 엔진은 KV 읽기 몫만 세서 −1.6% 다. 최대 컨텍스트 표의 긴 칸이 낙관적이다(옛 빌드 30k 점은 표시 범위 밑). **pp 는 더 크게 떨어진다** — 같은 실측(-ub 2048)의 pp2048 이 깊이 10k·20k·30k 에서 d0 의 0.52·0.35·0.26배다(https://github.com/ggml-org/llama.cpp/pull/25893#issuecomment-5162332599 — 인덱서·압축 경로). 엔진 pp 는 깊이와 무관하고 라벨은 rough ±40% 라 긴 프롬프트에서는 범위를 크게 벗어난다(일반 한계의 긴 문맥 pp 감쇠보다 훨씬 크다). 반대로 읽기 바이트는 `kvBytesPerToken × ctx` 전체로 세는데 CSA 는 top-512 블록만 읽는다 — 8k 에서 0.06GB 라 무시할 크기 ③ **연산 버퍼** — #27680 로그의 CUDA 연산 버퍼는 64k·-ub 4096 에서 2.48GB(2,366.28 MiB — 엔진 근사 1.09GB 의 두 배 이상, b10568 은 2,570.28 MiB = 2.70GB). 기본 ubatch 512 의 값은 공개 로그를 찾지 못했다 — 24GB 카드의 MoE 전문가 RAM 배치 경계 셀이 빠듯할 수 있다. raw SWA 창 캐시(기본 ubatch 34MB, -ub 4096 192MB)·압축기 상태(12MB)도 따로 세지 않는다. KV 산식은 `-np 1` 기준이다 — llama-server 기본 4슬롯이면 압축 KV·raw SWA·상태가 슬롯마다 붙어 4배라 사이트 명령은 `-np 1` 을 붙인다(§2.2) ④ **빌드 민감도** — #25893 본문의 M1 Ultra 는 07월 master 8.91 tok/s, 하이퍼 커넥션 등 Metal 개선을 모은 브랜치 23.59 tok/s 였고, CUDA sparse FA(#27970)는 131k~1M 문맥 pp 를 1.5~2.2배로 올렸다. 2026-08 이전 빌드는 추정보다 훨씬 느리다 ⑤ **MTP·DSpark 미계상** — config 의 MTP 1층은 본 GGUF 에 없고(변환기가 뺀다), DSpark 초안(`dspark-*.gguf`, 약 11GB)을 `--spec-type draft-dspark` 로 함께 쓰면 그만큼 메모리가 더 든다 ⑥ **DGX Spark** — sm_121(GB10) 출력 손상 보고(#28132)가 10-18 not planned 로 닫혔다(원인 미해결). CUDA·Metal·ROCm 에서 반복 블록을 두 번 읽는 비용이 같은지는 보지 못했다. 반복 경계의 노름 한 번·논리 층마다 따로 도는 어텐션(KV 는 이미 논리 층 값으로 읽기에 들어 있다)의 고정 시간은 따로 세지 않는다 ② **여러 장 층 분할**(§6): llama.cpp 는 논리 층 44개(+ 출력층)를 카드마다 남은 메모리 비율로 나누지만(src/llama-model.cpp#L1670-L1695) 물리 가중치는 텐서의 블록 번호(0~21 — 첫 반복)로 장치를 고른다(`dev_layer.at(tn.bid)` — https://github.com/ggml-org/llama.cpp/blob/0a1ef309cdbb9f2024f58a38fb4c42352c5db569/src/llama-model.cpp#L2378-L2386, nanbeige 는 blk.0~21 만 만든다 — 같은 커밋 src/models/nanbeige.cpp#L48-L73). 코드로 확인한 배치라 같은 카드 2장이면 블록 전부(Q4_K_M 1.97GB)가 1번 카드(논리 0~22층)에, 2번 카드에는 출력층과 KV 만 간다. 엔진은 합산 풀로 판정해(§6) 이 쏠림을 모른다 — `-ngl all`(그러면 `--fit` 도 꺼진다 — common/fit.cpp#L463-L464)로 기본 분할을 쓰면 긴 컨텍스트에서 1번 카드가 넘친다: 2× RTX 4060 의 full-gpu 최대 ctx 60k 에서 1번 카드 약 9.3 / 8GB, 2× RTX 3060 12GB 100k 약 13.4 / 12GB, 2× RTX 5060 Ti 16GB 140k 약 17.6 / 16GB(1~1.6GB 초과). 계산기 2~4장 × dGPU × 양자화 × ctx 8k~256k × KV 3종 시뮬레이션(10-22 리뷰)에서 엔진 full-gpu 15,112셀 중 반복 때문에 넘치는 셀은 206개(전부 ctx 64k 이상 — 가중치를 논리 층에 고르게 둔 반사실도 넘치는 165셀은 합산 판정 일반의 근사)다. 그래서 **GPU 여러 장의 반복 모델 명령은 `-ngl` 을 빼고 `--fit` 에 맡긴다**(10-22 D114 리뷰 — `CommandPlan` ngl 'auto', 계산기 각주 `fitAutoNoteLoops`). `--fit` 은 후보 배치마다 장치별 할당량을 실제로 재서 나누므로(common/fit.cpp#L588-L600) 쏠림을 피하지만, 장치마다 1GiB 여유를 두어 엔진이 빠듯하게 full-gpu 로 본 셀에서는 층 일부를 CPU 로 보내 추정보다 느릴 수 있다. 판정은 합산 그대로(카드별 몫을 fit 에 넣는 일은 PROGRESS §2 엔진 후속 ⑦-a). 반복 모델은 모든 구성에서 이론 추정이다 ③ `--fit` 이 반복 모델의 논리 층을 어떤 순서로 채우는지(뒤쪽 반복 층은 KV 만 있어 층마다 크기가 다르다)는 실행해 보지 못했다 — 단일 GPU 부분 오프로드는 `-ngl` 을 명시한다(§3.4). Ollama(0.30+, -ngl 을 넘기지 않는다)는 늘 `--fit` 배치다 ④ 계산기 "HF 에서 불러오기"(카탈로그 밖)는 반복 모델을 받지 않는다 — 행마다 헤더 실측 반복 블록(loopGB)과 헤더 `num_loops` 대조가 필요하다 ⑤ Ouro(`total_ut_steps` 4 — 본선 PR #29823 미머지)는 같은 필드(`arch.loops` 4)로 표현되지만 머지 전에는 넣지 않는다 — MHA(kv 16)라 KV 가 24 × 4 × 16 × 128 × 4 = 786,432 B/tok(8k 6.4GB)로 가중치보다 먼저 문제다.
- **값 전문가(MoVA — K2-Horizon MoVA 36B-A4B, 10-21 D113 · 엔진 0.11.0)**: 값 전문가 텐서(`attn_v_exps`, Q4_K_M 4.25GB — 파일의 19%)는 llama.cpp 가 어느 배치에서도 그래픽카드에 두므로 비전문가로 센다(§3.3 — 배치·VRAM 판정은 llama.cpp 와 같다). 토큰마다 64개 중 4개만 곱하므로(§3.1) 읽기 바이트는 행 실측 `valueExpertGB` 중 그 몫만 센다(Q4_K_M 가중치 읽기 3.30GB). 남은 한계: ① 값 전문가 라우팅·작은 행렬곱의 고정 시간은 더하지 않는다 — FFN 전문가 하나와 같은 값으로 쳐도 2~17% 낮아질 뿐(RTX 5090 full-gpu −17%)이라 이론 추정 ±30% 안이지만, 빠른 카드일수록 실제보다 높게 볼 수 있다. ② 공개 실측(tg, 빌드 명시)이 없어 모델 전체가 이론 추정이다(§4 ⑧). ③ pp 실효 파라미터는 카드의 활성 4B(값 전문가를 고른 몫만 센 값 — 헤더로 세면 입출력 임베딩을 빼고 4.66B)와 FFN 전문가 비율 8/100 으로 셈한다 — 값 전문가는 전문가당 토큰이 32(ub512 × 4/64)라 FFN 전문가(41)보다 조금 더 느릴 수 있다(pp 는 rough ±40%). ④ 행에 값 전문가 실측이 없으면 모델 수준 유도 비전문가(0.65 — 값 전문가를 FFN 전문가처럼 나눈 값)로 떨어져 VRAM 을 약 5GB 적게 세므로, 이 모델의 행은 모두 헤더 분할·`valueExpertGB` 를 갖게 강제한다(validateAll, sync-models·add-model 은 실측이 없으면 행을 넣지 않는다). 계산기 HF 불러오기는 MoVA 모델을 받지 않는다(그 경로의 행은 값 전문가 실측을 싣지 않고, 헤더로 센 활성 파라미터가 값 전문가를 전부 활성으로 센다). 이력: 엔진 0.10.0(같은 날 첫 추가)은 값 전문가를 토큰마다 전부 읽는다고 봐 8k 추정이 지금 값의 0.49~0.69배(full-gpu)·0.57~0.84배(cpu-moe)·0.58~0.77배(통합 메모리 cpu-only)였다(데스크톱 cpu-only 는 그대로).
- **층별 임베딩 표·KV 공유 층(Gemma 4 E2B·E4B, 10-21 D112)**: ① 속도의 E 계열 고유 지연(층별 입력의 CPU→GPU 전송·동기화와 작은 층별 연산 — 같은 카드의 다른 dense 모델보다 토큰당 1ms 쯤 길다)은 백엔드별 고정 시간 하나로 둔다(§3.1 — CUDA 1.35·Vulkan 1.75ms). 근거가 카드 6장·백엔드 둘뿐이다 — Metal(맥)·AMD 는 실측이 없어 Vulkan 값을 쓰고, ROCm·SYCL 은 따로 보지 않는다(B580 SYCL 은 Vulkan 값으로 −3.3%). 대역폭이 작은 카드는 클래스 계수 0.70 이 낮아(4070 Ti 504 GB/s) 고정 시간을 더하면 −11% 쯤 낮게 본다. CUDA 근거 4점이 ubatch 1 pp(출력층을 마지막 토큰만 읽는다)라 tg 그 자체가 아니고, 그 점의 파일(ggml-org Q4_0 — token_embd Q8_0)은 가정이다(token_embd 가 Q6_K 였다면 CUDA 값이 0.1ms 쯤 작다). dense 모델 공통 고정 시간(PROGRESS §2 엔진 후속 ⑭)이 들어오면 이 값에서 그만큼 빼야 한다(겹치지 않게). A770 Vulkan +78% 는 intel-arc 계수 문제로 남는다. ② KV 는 **저장 KV** 로 센다 — 메모리는 정확하지만 읽기는 공유 층이 저장 KV 를 다시 읽어 실제보다 작게 본다(8k f16 에서 E4B 0.13 vs 0.23GB, E2B 0.05 vs 0.11GB — 가중치 읽기 3.0·1.5GB 에 비해 작다). ③ 시스템 RAM 검사는 offGpuGB(표 + 헤더)만 센다 — 임베딩 공유라 GPU 출력층 사본과 따로 CPU 에 남는 token_embd 입력 사본(0.23~0.71GB)은 빠져 있다(OS 예약 4GB 안). mmap 이라 실제 RAM 은 읽은 쪽만큼일 수 있다(보수). ④ 4GiB 를 넘는 표(BF16 파일 등)는 기본 lazy 모드에서 디스크에서 행만 읽어 RAM 에 두지 않는다 — 엔진은 모르고 RAM 몫으로 센다(PROGRESS §2 엔진 후속 ⑥). ⑤ pp 실효 파라미터는 paramsB(표 2.3~2.8B 와 비전·오디오 인코더 약 0.47B 포함)라 pp 를 낮게 볼 수 있다(rough ±40%). ⑥ 통합 메모리(맥)는 다른 모델처럼 파일 전체를 통합 풀로 센다(표는 CPU 버퍼지만 같은 RAM — 보수).
- cpu-moe 의 `--n-cpu-moe` 는 층 평균 전문가 크기로 정한다 — Q4_K_M 류 혼합 레시피는 층마다 ffn_down 정밀도가 달라 층 크기가 최대 ~1.15× 차이(GPU 에 남는 뒤쪽 층이 무겁다) → 여유 1층(`CPU_MOE_GPU_LAYER_MARGIN`). 앞쪽 dense 층이 있는 기존 MoE(`arch.expertLayers` 미기록)는 전문가 층 수를 전체 층으로 근사한다 — 10-03 이후 추가 모델은 config 가 층 지도를 주면 기록한다(D63).
